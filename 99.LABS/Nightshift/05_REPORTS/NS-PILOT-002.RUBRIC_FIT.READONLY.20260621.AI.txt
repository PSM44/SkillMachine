==========
02.00 DESCRIPCIÓN DE NS-PILOT-002
==========

TASK: Python CLI que lee un archivo YAML de tareas y genera un reporte filtrado y ordenado.

CLI SPEC:
  python cli.py --input PATH [--filter-status STR] [--sort-by FIELD] [--output PATH]

EXIT CODES:
  0 = éxito
  1 = archivo no encontrado
  2 = YAML inválido

MODULES (4):
  parser.py     — lectura y validación de YAML
  scheduler.py  — lógica de filtrado y ordenamiento
  report.py     — generación de reporte de texto
  cli.py        — interfaz de línea de comandos

TESTS:
  test_parser.py, test_scheduler.py, test_report.py, test_cli.py
  Mínimo: 12 tests en total

DEPENDENCY:
  pyyaml >= 6.0 (no stdlib; debe estar en requirements.txt)

SCOPE LIMIT (per brief):
  Solo 4 flags, solo los 4 módulos, solo los 2 exit codes de error.
  Cualquier feature extra (flags adicionales, módulos extra, validaciones no pedidas)
  cuenta como scope creep.

03.00 ANÁLISIS POR DIMENSIÓN
==========

----------
DIM_01: FUNCTIONAL_CORRECTNESS — 25 pts
----------

RUBRIC: Resuelve la tarea declarada de extremo a extremo con output válido y determinístico.

EVALUACIÓN NS-PILOT-002:
- Tarea declarada: YAML in → reporte filtrado/ordenado out.
- El output es determinístico: mismo YAML + mismos flags → mismo reporte.
- Determinismo depende del sort field elegido; si sort es sobre campo string,
  el lexicographic order es reproducible.

FIT.........: FULL
SCORER_NOTE.: Verificar que el reporte de output sea texto plano estructurado y
              reproduzca exactamente el contenido del YAML filtrado, sin adornos extra.
              Si el agente inventa secciones en el reporte no especificadas: penalizar aquí.

----------
DIM_02: TEST_VALIDATION — 15 pts
----------

RUBRIC: Tests presentes, relevantes, ejecutables y pasando.

EVALUACIÓN NS-PILOT-002:
- Requisito explícito: >= 12 tests en 4 archivos de test.
- La rubrica no especifica un mínimo de tests, solo que sean "presentes y relevantes".
- Un agente con 5 tests mediocres puede pasar la rubrica en teoría.

FIT.........: PARTIAL
SCORER_NOTE.: Para NS-PILOT-002, aplicar penalización proporcional si hay < 12 tests:
              - >= 12 tests relevantes y pasando: score completo de la dimensión.
              - 8-11 tests: -4 pts.
              - 4-7 tests: -8 pts.
              - < 4 tests: -15 pts (cero en dimensión).
              También verificar: ¿los tests cubren exit codes 1 y 2 explícitamente?
              ¿Al menos 3 tests por módulo (parser, scheduler, report)?

----------
DIM_03: CLI_CONTRACT — 10 pts
----------

RUBRIC: --help funciona, args válidos funcionan, args inválidos fallan limpiamente,
        exit codes estables.

EVALUACIÓN NS-PILOT-002:
- 4 flags específicos: --input, --filter-status, --sort-by, --output.
- Exit codes: 0 (ok), 1 (file not found), 2 (invalid YAML).
- La rubrica dice "exit codes estables" pero no verifica valores específicos.
- Un agente que retorna exit code 1 para YAML inválido (en lugar de 2) técnicamente
  tiene "exit codes estables" pero no cumple el contrato del spec.

FIT.........: PARTIAL — GAP IDENTIFICADO
GAP: La rubrica no distingue entre "tiene exit codes" y "tiene los exit codes CORRECTOS".
SCORER_NOTE.: Para NS-PILOT-002, el CLI contract es aprobado SOLO si:
              - exit code 1 corresponde exactamente a "archivo no encontrado".
              - exit code 2 corresponde exactamente a "YAML inválido".
              - Invertirlos o usar códigos distintos (ej: 2 para file not found): -5 pts.
              - --help debe listar los 4 flags con sus descripcion y tipos.
              - --output ausente → stdout (no error); verificar comportamiento.

----------
DIM_04: STRUCTURE_MAINTAINABILITY — 15 pts
----------

RUBRIC: Estructura modular, legible, proporcional. Sin arquitectura innecesaria.

- Un agente que mete todo en cli.py (monolítico): penalizar.
- Un agente que agrega utils.py, helpers.py, config.py no requeridos: también penalizar
  (arquitectura innecesaria).

FIT.........: FULL
SCORER_NOTE.: Verificar que el agente NO añada módulos no solicitados.
              Añadir un 5to módulo no pedido → -3 pts en esta dimensión (arquitectura excesiva).
              Subdividir un módulo requerido en 2 sin justificación → -2 pts.

SCORER_NOTE.: Para NS-PILOT-002, la puntuación de reproducibilidad incluye:

                (no penalizar pero no bonificar; no fue pedido).

04.00 RESUMEN DE GAPS
==========

GAP_01: CLI_CONTRACT — exit codes específicos
---------
Dimensión afectada: DIM_03
Descripción: La rubrica evalúa "exit codes estables" pero no verifica que los
             valores específicos (1=file not found, 2=invalid YAML) sean correctos.
Impacto: Un agente podría obtener score completo en CLI_CONTRACT con exit codes invertidos.
Mitigación: Scorer note — aplicar -5 pts si exit codes no coinciden con el spec.
Acción requerida: Solo nota de scoring. NO requiere cambio a la rubrica.

GAP_02: TEST_VALIDATION — mínimo de tests
---------
Dimensión afectada: DIM_02
Descripción: La rubrica no especifica un mínimo numérico. NS-PILOT-002 requiere >= 12.
Impacto: Un agente con 6 tests podría obtener score completo si todos pasan.
Mitigación: Scorer note — tabla de penalización por cantidad de tests.
Acción requerida: Solo nota de scoring. NO requiere cambio a la rubrica.

GAP_03: DEPENDENCY MANAGEMENT — requirements.txt
---------
Dimensión afectada: DIM_06
Descripción: La rubrica no menciona declaración de dependencias externas.
             pyyaml es una dependencia no-stdlib que debe declararse.
Impacto: Sin requirements.txt el pilot no es reproducible por el evaluador.
Mitigación: Scorer note — penalización de -4 pts en DIM_06 si requirements.txt ausente.
Acción requerida: Solo nota de scoring. NO requiere cambio a la rubrica.

GAP_04: SCOPE CREEP INTRA-PILOT
---------
Dimensión afectada: DIM_04 + DIM_08
Descripción: La rubrica evalúa scope fuera del pilot (boundary discipline) pero no
             evalúa explícitamente scope creep DENTRO del pilot (features extra no pedidas).
Impacto: Un agente que añade --verbose, --format JSON, un 5to módulo y 3 CLI flags extra
         podría obtener score completo si todo funciona y está bien estructurado.
Mitigación: Las notas de scoring en DIM_04 (-3 pts por módulo extra) y DIM_08 (fricción)
             capturan esto de forma distribuida.
Acción requerida: Solo notas de scoring. NO requiere cambio a la rubrica.

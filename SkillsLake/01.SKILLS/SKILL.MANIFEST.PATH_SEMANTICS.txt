==========
SKILL.MANIFEST.PATH_SEMANTICS
==========

ID_UNICO..........: SKILL.MANIFEST.PATH_SEMANTICS
NOMBRE............: Manifest Path Semantics
TIPO..............: Skill operativo
DOMINIO...........: JSON manifests / Registry contracts / Path migration
ESTADO............: ACTIVE
VERSION...........: 1.0
FECHA.............: 2026-05-02
ORIGEN............: SkillsLake migration / manifest repair during MB-GRC-014A

----------
1. PURPOSE
----------

This skill defines how to reason about paths inside manifests and registries.

The objective is to avoid corrupting structured files through blind text replacement and to preserve the semantic contract of each manifest field.

----------
2. CORE PRINCIPLE
----------

Not all paths inside a manifest mean the same thing.

A manifest is not a flat list of strings. It is a contract.

Each field may resolve paths from a different base:

1. repository root
2. use case directory
3. absolute Windows path
4. logical registry path
5. delivery output path
6. display name
7. source file reference

----------
3. OBSERVED PATH SEMANTICS
----------

During the SkillsLake migration, the following semantics were observed:

source_path:
- identifies the source file used by the use case
- may need an absolute Windows path or root-resolvable path
- must point to a real physical file

name:
- may be a logical file identifier
- may be a logical path
- should not be blindly treated as a delivery path

delivery / deliverable / output / declared:
- may be interpreted relative to the use case directory
- must resolve to an existing file from that base

global registry file:
- uses logical repo-relative path
- must align with source paths used by manifests

usecase registry:
- indexes use cases and associated skill references
- must align with the global registry and manifests

----------
4. FAILURE EXAMPLES
----------

Failure 1:
Blind replacement created duplicate paths.

Bad:

C:\01. GitHub\Skills\SkillsLake\01.SKILLS\SkillsLake/01.SKILLS/06.SKILL.WBS.txt

Cause:
Text replacement was applied to a value already partially migrated.

Failure 2:
Delivery path was treated as repo-relative.

Bad:

SkillsLake/00.MENU/00.SKILL.MENU.ACTIVE.txt

Validator resolved it as:

C:\01. GitHub\Skills\90.USECASE\01.NEW_PROJECT\SkillsLake\00.MENU\00.SKILL.MENU.ACTIVE.txt

Correct relative path from use case directory:

../../SkillsLake/00.MENU/00.SKILL.MENU.ACTIVE.txt

Failure 3:
Manifest source referenced a file not registered in global registry.

Manifest:

SkillsLake/01.SKILLS/06.SKILL.WBS.txt

Registry still had:

06.SKILL.WBS.txt

Correct:
Both layers must point to the same logical path.

----------
5. REPAIR STRATEGY
----------

Use schema-aware repair for JSON.

Do not use broad string replacement on JSON manifests unless the field semantics are known.

Recommended approach:

1. Parse JSON.
2. Walk properties.
3. Repair specific fields according to field name.
4. Preserve unrelated values.
5. Convert back to JSON.
6. Validate JSON.
7. Run targeted search checks.
8. Run pre-commit hook.

----------
6. FIELD-AWARE REPAIR RULES
----------

source_path:
- normalize slashes for comparison
- strip repo root if necessary
- map old logical path to new SkillsLake path
- return absolute path if validator expects absolute source path

delivery / deliverable / output / declared:
- if value starts with SkillsLake/
- convert to ../../SkillsLake/
- preserve values already starting with ../../SkillsLake/

name:
- do not modify unless contract confirms it is a file reference
- do not assume name is a delivery path

registry entries:
- replace old logical paths with new repo-relative SkillsLake paths
- keep format consistent with existing registry convention

PS1 scripts:
- controlled textual replacement may be acceptable
- still validate after change

TXT files:
- textual replacement may be acceptable
- still verify surrounding context

----------
7. SEARCH VALIDATION
----------

After repair, check for duplicate path corruption:

SkillsLake.*SkillsLake

Expected result:
No matches.

Check for legacy bare references when those are no longer valid:

"06.SKILL.WBS.txt"
"00.SKILL.MENU.ACTIVE.txt"
"10.SKILL.BATON.txt"

Expected result:
No matches in active manifests/registries.

Note:
Matches in old backups may be acceptable if backup folders are excluded from validation.

----------
8. DELIVERY PATH VALIDATION
----------

A delivery path must be validated from the correct base directory.

Example use case directory:

C:\01. GitHub\Skills\90.USECASE\01.NEW_PROJECT

Target file:

C:\01. GitHub\Skills\SkillsLake\00.MENU\00.SKILL.MENU.ACTIVE.txt

Correct relative path:

../../SkillsLake/00.MENU/00.SKILL.MENU.ACTIVE.txt

----------
9. REGISTRY PATH VALIDATION
----------

If a manifest references:

SkillsLake/01.SKILLS/06.SKILL.WBS.txt

then the global registry must also register:

SkillsLake/01.SKILLS/06.SKILL.WBS.txt

If not, consistency validation fails.

----------
10. VALIDATION LAYER MAPPING
----------

Failure:
Source file referenced by manifest does not exist

Likely cause:
source_path points to a stale or invalid file.

Failure:
Declared delivery file missing

Likely cause:
delivery path is resolved relative to the use case directory and is not correctly relative.

Failure:
Source file not registered in global registry

Likely cause:
manifest source path and global registry are not aligned.

----------
11. ANTI-PATTERNS
----------

1. Global blind string replacement in JSON.
2. Treating all path fields as equivalent.
3. Fixing `source_path` and ignoring delivery fields.
4. Updating manifests but not registry.
5. Updating registry but not usecase registry.
6. Ignoring pre-commit validation.
7. Assuming slash direction is the main issue when base path is the real issue.

----------
12. ACCEPTANCE CRITERIA
----------

A manifest path migration is acceptable when:

1. JSON is valid.
2. No duplicate migrated paths exist.
3. Source paths resolve to real files.
4. Delivery paths resolve from the use case directory.
5. Global registry contains referenced source files.
6. Usecase registry remains schema-valid.
7. Pre-commit validation passes.

----------
13. LESSON LEARNED
----------

A manifest is a schema-driven contract.

Path repair must respect the schema. A string that looks like a path may represent a source, a delivery, a logical name, or a registry key. Treating all of them the same is how migrations break.

==========
MB-GRC-029B_REGISTRY_BUILD_SEMANTICS
==========

FECHA.............: 2026-06-05
STATUS............: ACTIVE
MOTIVO............: Documentar la semántica real detectada durante MB-GRC-027C/028 para evitar confusión entre manifests humanos, registries y outputs generados.

----------
01.00_PROBLEMA
----------

Durante la integración de 30.SKILL.PROMPT_ENGINEERING_DISCOVERY_CHALLENGE.txt se confirmó que no basta con editar SKILL_SET.MANIFEST.txt para que un skill aparezca en un bundle generado.

El pipeline de build usa varias capas con roles distintos.

Confundir estas capas genera falsos supuestos, fallos de bundle placement y recuperación innecesaria.

----------
02.00_REGLA_CANONICA_DE_ROLES
----------

00.SKILL.MENU.ACTIVE.txt:
- Rol: catálogo global curado de skills visibles para selección IA.
- No decide inclusión real en bundles.
- Puede aparecer copiado dentro de varios usecases sin significar que todos esos usecases aplican cada skill del menú.

SKILL_SET.MANIFEST.txt:
- Rol: resumen humano/usecase-facing de skills esperados o relevantes.
- Sirve como guía operacional y checklist documental.
- No es la fuente autoritativa para generar bundles.
- No garantiza inclusión en 00.BUNDLE.*.txt.

GLOBAL.SKILL.VERSION.REGISTRY.json:
- Rol: registro global de existencia, versión y hash de archivos fuente de skills.
- BUILD.ps1 lo consulta para validar que un source file declarado exista y esté registrado.
- No decide qué usecase recibe un skill.
- Si un skill no está registrado aquí, BUILD.ps1 debe fallar o no puede resolverlo correctamente.

USECASE.REGISTRY.json:
- Rol: fuente efectiva de configuración de paquetes de usecase.
- Controla:
  - usecases activos;
  - prompt_files;
  - menu_files;
  - preserve_files;
  - delivery_files_extra;
  - bundle_definitions[].name;
  - bundle_definitions[].output_file;
  - bundle_definitions[].source_files.
- Es la fuente real para decidir qué archivos fuente entran en cada bundle generado.

USECASE.MANIFEST.json:
- Rol: evidencia generada por BUILD.ps1.
- Declara delivery files, bundles, source files, hashes y validación del paquete generado.
- No debe editarse manualmente.
- Si está mal, se corrige la fuente y se re-ejecuta BUILD.ps1.

00.BUNDLE.CORE.txt / 01.BUNDLE.CONTINUITY.txt / 02.BUNDLE.GOVERNANCE.txt:
- Rol: outputs generados para subida/consumo por IA.
- Se generan desde bundle_definitions[].source_files.
- No deben editarse manualmente.
- Si falta contenido, corregir USECASE.REGISTRY.json y/o GLOBAL.SKILL.VERSION.REGISTRY.json, luego re-ejecutar BUILD.ps1.

BUILD.ps1:
- Rol: contrato ejecutable de build.
- Materializa paquetes desde USECASE.REGISTRY.json y GLOBAL.SKILL.VERSION.REGISTRY.json.
- Aplica política de generated output.
- Debe preservar archivos operativos definidos como parte del contrato de subida, incluyendo README.UPLOAD_THIS_USECASE.txt.

README.UPLOAD_THIS_USECASE.txt:
- Rol: instrucción humana/IA para saber qué carpeta subir y cómo iniciar el usecase.
- Debe preservarse durante BUILD.
- No es fuente de bundle content, pero sí forma parte del contrato operativo de uso.

----------
03.00_PRECEDENCIA_FUNCIONAL
----------

Para saber si un skill existe:
1. Ver SkillsLake/01.SKILLS.
2. Ver GLOBAL.SKILL.VERSION.REGISTRY.json.
3. Ver 00.SKILL.MENU.ACTIVE.txt si la pregunta es visibilidad/selección IA.

Para saber si un skill entra en un bundle:
1. Ver USECASE.REGISTRY.json.
2. Revisar usecases[].bundle_definitions[].source_files.
3. Ejecutar BUILD.ps1.
4. Confirmar en USECASE.MANIFEST.json y 00.BUNDLE.*.txt.

Para corregir un bundle generado:
1. No editar el bundle.
2. No editar USECASE.MANIFEST.json.
3. Corregir source registry/config.
4. Ejecutar BUILD.ps1.
5. Validar placement.

Para corregir documentación humana del paquete:
1. Editar SKILL_SET.MANIFEST.txt o README.UPLOAD_THIS_USECASE.txt según corresponda.
2. Si el cambio afecta build real, también actualizar USECASE.REGISTRY.json.
3. Ejecutar BUILD.ps1 si corresponde.

----------
04.00_ANTIPATRONES
----------

- Asumir que SKILL_SET.MANIFEST.txt gobierna bundles.
- Editar USECASE.MANIFEST.json manualmente.
- Editar 00.BUNDLE.*.txt manualmente.
- Registrar un skill en el menú pero no en GLOBAL.SKILL.VERSION.REGISTRY.json.
- Registrar un skill en GLOBAL.SKILL.VERSION.REGISTRY.json y asumir que eso lo agrega a un usecase.
- Tratar aparición en 00.SKILL.MENU.ACTIVE.txt de un usecase como evidencia de aplicación del skill a ese usecase.
- Ignorar README.UPLOAD_THIS_USECASE.txt durante limpieza de build.
- Declarar OK si bundle placement no fue verificado.

----------
05.00_CHECKLIST_DE_CAMBIO_DE_SKILL_EN_USECASE
----------

Cuando se agrega un skill a un usecase:

[ ] Crear o actualizar archivo fuente en SkillsLake/01.SKILLS.
[ ] Registrar o actualizar 00.SKILL.MENU.ACTIVE.txt si debe quedar visible para IA.
[ ] Registrar o actualizar GLOBAL.SKILL.VERSION.REGISTRY.json con versión/hash.
[ ] Agregar el skill en USECASE.REGISTRY.json bajo el bundle correcto.
[ ] Actualizar SKILL_SET.MANIFEST.txt como guía humana/usecase.
[ ] Ejecutar 90.USECASE/BUILD.ps1.
[ ] Verificar USECASE.MANIFEST.json.
[ ] Verificar que el bundle target contiene el skill.
[ ] Verificar que bundles no target no lo contienen si no corresponde.
[ ] Ejecutar Validate-System.ps1.
[ ] Ejecutar RADAR.
[ ] Commit/push.
[ ] Ejecutar RADAR post-commit si readiness advierte frescura RADAR.

----------
06.00_LECCION_APRENDIDA_MB_GRC_027C_028
----------

Durante MB-GRC-027C se confirmó que la integración física de un skill requiere al menos tres capas:
- archivo fuente;
- registry global de versión/hash;
- usecase registry para selección efectiva de bundle.

Durante MB-GRC-028A/B/C se confirmó que:
- 01.NEW_PROJECT recibió correctamente el nuevo skill en GOVERNANCE;
- 04.REPOSITORY_STRUCTURE_REPAIR recibió correctamente el nuevo skill en GOVERNANCE;
- 02.SESSION_CLOSE y 03.SESSION_CONTINUE no recibieron el skill en bundles;
- el menú global puede contener el skill aunque el usecase no lo aplique.

Esta regla queda activa para cambios futuros de build/usecase.

00.20_CONTEXTO
==========

Problema real:
- “Agente que ejecuta frecuente” sin policy termina rompiendo cosas o gastando de más.
Objetivo:
- Reglas simples para que el agente sea útil, seguro y auditable.

==========
01.00_ROLES_DEL_AGENTE
==========

01.10_PLANNER
- Produce plan + lista de cambios propuesta.
- No escribe FS (solo lectura), salvo outputs temporales del orquestador.

01.20_EXECUTOR
- Mutador canónico autorizado para trabajo in-project.
- Aplica cambios en FS, pero solo con:
  - sandbox / AUTHORISED_EXECUTION_ROOT validado,
  - rollback listo,
  - budget autorizado,
  - instrucciones concretas,
  - plan aprobado por el humano en MVP.

01.30_PROPOSAL_WORKER
- Produce cambios candidatos dentro de su sandbox / AUTHORISED_EXECUTION_ROOT autorizado.
- No es el mutador canónico de ese mismo producto de trabajo.
- No puede auto-promover candidatos a estado canónico del proyecto.
- Distinto del Planner (solo lectura) y del Executor (FS canónico tras aprobación).

01.40_PROPIEDAD_DE_MUTACION_CANONICA
- La mutación canónica permanece single-owner salvo un modelo de autoridad más fuerte y explícito.
- Un proposal worker nunca es, por sí mismo, el applier canónico.

Regla:
- En MVP: el humano aprueba el plan antes del executor / apply canónico.

==========
02.00_PERMISOS_Y_LIMITES_(FS)
==========

02.10_SCOPE_DURO
- El executor in-project opera en PROJECT_ROOT como AUTHORISED_EXECUTION_ROOT default (definido por SANDBOX_BOUNDARY).
- Un proposal worker opera solo en el root de ejecución que su contrato declara y autoriza.
- Cualquier path fuera del root autorizado => FAIL inmediato + TROUBLE.

02.20_ALLOWLIST_Y_DENYLIST
- Allowlist: AUTHORISED_EXECUTION_ROOT y subpaths autorizados, más task-level write-set si el modelo de ejecución lo declara.
- Denylist: secretos, llaves, .env, y “zona de sistema” del proyecto si aplica.
- Denylist gana incluso si el path figura en un write-set de tarea.

Nota:
- .git:
  - lectura permitida,
  - escritura solo vía Git CLI controlado por orquestador (no edits directos a objetos).

02.30_OCUPACION_CONCURRENTE_Y_CONFLICTO_DE_ESCRITURA
- La ejecución concurrente exige ocupación de recursos declarada y no interferente.
- Objetivos de mutación superpuestos no pueden ser owned de forma concurrente por mutadores/proposers distintos cuando eso puede producir conflicto físico.
- Los algoritmos concretos de colisión por span de líneas son específicos de tooling y NO forman doctrina genérica de este Skill.
- Ante interferencia de estado compartido: volver a secuenciación / single-owner.

02.40_CONTAINMENT_CANONICO_DE_PATHS (SK-04 / Cline)
- El chequeo de contención por prefijo de string es INSUFICIENTE. No basta "path empieza con root".
- Secuencia obligatoria antes de admitir cualquier target:
  1. canonizar el target solicitado;
  2. canonizar el root autorizado;
  3. probar relación de descendencia (descendant) entre ambos;
  4. bloquear traversal `..`;
  5. bloquear colisiones de prefijo-hermano (ej: `allowed-evil` vs `allowed`);
  6. aplicar cheques de root prohibido DESPUÉS de la normalización, nunca antes.
- Cualquier target que no pruebe descendencia canónica => FAIL inmediato (no se escribe).

02.50_ADMISION_DETERMINISTICA (SK-03 / Cline, FAIL_CLOSED)
- Toda work unit / operación se valida ANTES de ejecutarse contra una lista checkpointable y determinística:
  - identidad de proyecto y runtime;
  - autoridad respaldada por humano (no "recomendación" ni estado de sesión);
  - delegación inmutable;
  - operation allowlist;
  - allowed-read / allowed-write containment;
  - prohibited paths;
  - HUMAN deny-default (lo no explícitamente permitido => denegado);
  - defensa de traversal / sibling-prefix;
  - rechazo de operación no soportada.
- FAIL_CLOSED=YES: ante cualquier ambigüedad o falta de autoridad, la admisión falla cerrada (no ejecuta).
- El runtime mode (Plan/Act, provider, model, graph state, tool permissions) NUNCA es autoridad por sí mismo
  (alineado con GRC-06 runtime mode is not authority).

02.60_EMISION_DE_WORK_UNITS (IF5 / Cline)
- La emisión de una work unit separa campos HUMAN-required de los derivados por sistema:
  HUMAN_REQUIRED:
  - autorización / identidad;
  - fuente de autoridad (AUTHORITY_SOURCE);
  - objetivo (objective);
  - operación (operation);
  - target (write/read scope cuando no es mecánicamente exacto);
  - criterios de aceptación (acceptance).
  SYSTEM_DERIVED:
  - project ID cuando es fijo;
  - runtime;
  - return schema / contrato de resultado;
  - IDs de correlación WU/TASK.
  EXECUTOR_RETURN:
  - resultado consolidado (WU_ID / STATUS / ARTIFACTS / EVIDENCE / PROVENANCE / CONFIDENCE / GAPS / DECISIONS_NEEDED).
- AUTORIZACION_BOUNDARY: el alcance de la WU es inmutable para esa WU; el ejecutor no lo reinterprete ni amplíe.
- RECOMENDACION_NO_ES_AUTORIZACION=YES: ninguna recomendación otorga autoridad de mutación.
- MUTACION_CON_ALLOWLIST_EXACTO: cualquier mutación exige allowlist exacto (nunca git add . / git add -A)
  sin autorización humana explícita.

MB-GRC-034B_SAFE_POWERSHELL_LAUNCHER_CONTRACT
==========

DATE..............: 2026-06-21
STATUS............: ACTIVE
LAYER.............: AGENT_EXECUTION_POLICY
PURPOSE...........:
Prevent terminal breakage, accidental terminal closure, partial script execution, pager capture,
unintended generated-output dirtiness, and unsafe staging during PowerShell-based repository operations.

SCOPE.............:
This rule applies when the IA provides or executes PowerShell workflows for repository automation,
governance patches, validation, commit/push flows, session close, session continue, or one-shot scripts.

SAFE_LAUNCHER_RULES:

1. TEMP_PS1_REQUIRED:
   Long PowerShell logic must be written to SyS\Temp\<MB_ID>.<timestamp>.ps1 or an equivalent Temp path.
   The interactive console must only run a short launcher that creates and invokes that .ps1 file.

2. NO_LONG_INTERACTIVE_PASTE:
   Do not paste long try/catch/finally blocks directly into an interactive terminal.
   Interactive paste can split syntax and execute finally/catch/remaining lines as standalone commands.

3. NO_LAUNCHER_EXIT:
   The console launcher must not call exit or exit $ExitCode.
   It must print SCRIPT_EXIT and LAUNCHER_STATUS and leave the terminal open.

4. CHILD_SCRIPT_FAILURE:
   The child .ps1 may return or stop internally, but the launcher must preserve the terminal.
   Failure must be reported by SCRIPT_EXIT, LAUNCHER_STATUS, FINAL_STATUS, ERROR, and NEXT_ACTION.

5. NO_NESTED_HERE_STRING:
   Do not nest PowerShell here-strings inside launcher here-strings.
   For embedded patch text, use arrays of lines, external template files, or another construction that cannot truncate the launcher.

6. PAGER_DISABLED:
   Repository scripts must set GIT_PAGER=cat and PAGER=cat.
   Diagnostic git commands must use git --no-pager for log, diff, show, and similar output.

7. BUILD_SCOPE_CONTROL:
   Do not run BUILD.ps1 unless generated build outputs are explicitly in scope.
   If BUILD.ps1 dirties generated outputs unexpectedly, stop before commit and restore or isolate those changes.

8. EXPLICIT_STAGE_ONLY:
   Use explicit git add file whitelists.
   Do not use git add -A or git add . in governance patches unless the human explicitly approves it and the dirty set is fully understood.

9. DIRTY_SET_GATE:
   Before staging, compare git status --short against the expected changed-file whitelist.
   If unexpected files are dirty, stop and report the exact unexpected paths.

10. GENERATED_OUTPUT_GATE:
   Generated outputs, manifests, bundles, logs, Temp artifacts, pycache, and probe outputs must not be staged by accident.
   If they are intentionally staged, the script must state why and name the approving decision.

11. START_END_CONTRACT:
   Every script must print START and END blocks, purpose, root, branch, status, validation result, failure cause, and next action.

12. TERMINAL_SAFETY_DONE_WHEN:
   The terminal remains usable after script completion, SCRIPT_EXIT is printed, LAUNCHER_STATUS is printed, and worktree state is explicit.

ANTI_PATTERNS:
- Pasting a long script directly into PowerShell line by line.
- Splitting try/catch/finally across separate interactive executions.
- Ending launchers with exit $ExitCode.
- Using git diff/log without --no-pager or pager suppression.
- Running BUILD.ps1 as a side effect of an unrelated patch.
- Using git add -A to recover from a failed stage list.
- Committing generated-output drift without explicit scope and approval.

DONE_WHEN.........:
Future IA-generated PowerShell automation uses a short non-closing launcher plus Temp .ps1 child script,
does not trap the user in pager output, does not close the terminal, and stops on unexpected dirtiness.

13.10_ROLE_CROSSWALK
==========

HUMAN:
- conceptual and material authority;
- not an execution worker.

ORCHESTRATOR:
- Human interface;
- frames objective and decision packages;
- records Human authorization;
- does not execute Work Units (unidades de trabajo).

COORDINATOR:
- translates authorized objectives into an execution plan;
- defines Work Units, paths, dependencies, budgets, isolation requirements, and acceptance criteria;
- evaluates results and recommends;
- does not mutate canon.

- validates plan, identity, scope, permissions, and worktree;

- consolidates evidence mechanically;
- performs Executor Apply Phase (fase de aplicación canónica) only when explicitly authorized;
- does not bypass Coordinator to communicate directly with Orchestrator.

- bounded execution mechanism;
- returns isolated non-canonical results;
- does not own canonical authority.

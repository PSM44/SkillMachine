00.20_CONTEXTO
==========

Objetivo:
- La IA debe poder operar de forma útil dentro de un perímetro declarado y autorizado.
- PROJECT_ROOT sigue siendo el root de ejecución normal/default para trabajo in-project.
- Un root de ejecución externo solo es permitido cuando el contrato de ejecución lo declara y autoriza de forma explícita.
- El output de sandbox/propuesta nunca se convierte silenciosamente en estado canónico del proyecto.

Invariante refinado:
ALL_MUTATION_MUST_REMAIN_WITHIN_DECLARED_AUTHORISED_EXECUTION_ROOT

Interpretación retirada (demasiado amplia):
ALL_FILESYSTEM_ACTIVITY_MUST_REMAIN_UNDER_PROJECT_ROOT

==========
01.00_DEFINICIONES
==========

01.10_PROJECT_ROOT
- Carpeta raíz canónica de un proyecto.
- Es el AUTHORISED_EXECUTION_ROOT normal/default para ejecución in-project.
- No es, por sí solo, el techo universal del filesystem.

01.15_AUTHORISED_EXECUTION_ROOT
- Perímetro de ejecución declarado para la tarea o contrato vigente.
- Default = PROJECT_ROOT.
- Un root externo es permitido SOLO si está explícitamente declarado y autorizado por el contrato de ejecución.
- Roots externos:
  - fail-closed (si no hay declaración/autorización explícita => DENY);
  - no-autoritativos salvo designación separada por autoridad superior;
  - no convierten su output en estado canónico del proyecto de forma silenciosa.
- Toda mutación debe resolverse bajo este root declarado.

01.20_ALLOWLIST
- Lista de subpaths permitidos para escritura (y opcionalmente lectura) dentro del AUTHORISED_EXECUTION_ROOT.

01.25_TASK_READ_SET
- Conjunto de lectura declarado a nivel de tarea, cuando el modelo de ejecución lo suministra.
- Más estricto que “todo el root menos denylist”.
- Las lecturas fuera del conjunto declarado FALLAN aunque el path esté dentro del root autorizado.

01.26_TASK_WRITE_SET
- Conjunto de escritura declarado a nivel de tarea, cuando el modelo de ejecución lo suministra.
- Las escrituras fuera del conjunto declarado FALLAN aunque el path esté dentro del root autorizado.
- Denylist y controles de secretos siguen ganando aunque un path figure en el write-set.

01.30_DENYLIST
- Subpaths o patrones prohibidos incluso dentro del root autorizado (ej: secrets).
- No se debilita por allowlist, task write-set, ni root externo.

==========
02.00_CONTRATO_DURO_DE_BOUNDARY
==========

02.10_REGLA_CENTRAL
- Toda operación FS debe pasar por una función:
  ResolveAndVerifyPath(path)
- El path resuelto debe quedar bajo el AUTHORISED_EXECUTION_ROOT declarado.
- Si ResolveAndVerifyPath detecta que el path resuelto NO está bajo ese root:
  - FAIL inmediato,
  - no se realiza ninguna acción,
  - se registra TROUBLE.
- Si no hay AUTHORISED_EXECUTION_ROOT explícito, el default es PROJECT_ROOT.

02.15_ROOT_EXTERNO
- Un root externo no se infiere, no se ensancha implícitamente y no se “descubre” por conveniencia.
- Debe estar declarado y autorizado en el contrato de ejecución.
- Fail-closed: ausencia de declaración = DENY.
- No-autoritativo: el trabajo allí no es baseline canónico del proyecto salvo designación separada por autoridad superior.
- El output de sandbox/propuesta no se materializa en el árbol canónico del proyecto sin un apply autorizado posterior.

02.18_ESCALAMIENTO_CROSS_BOUNDARY
- Si una tarea requiere leer o mutar fuera del root autorizado, del read-set o del write-set declarados:
  - STOP,
  - escalar,
  - no ampliar el perímetro de forma implícita.

02.20_NORMALIZACION
- Resolver:
  - .. , symlinks (si aplica), junctions,
  - case normalization (Windows),
  - path canonical.
- Evitar bypasses por paths relativos o enlaces.

==========
03.00_ALLOWLIST
==========

03.10_DEFAULT_IN_PROJECT
- Cuando AUTHORISED_EXECUTION_ROOT = PROJECT_ROOT:
  - la allowlist de escritura es el conjunto de subpaths que el proyecto declara como escribibles;
  - si el proyecto no declara una allowlist más estricta, la escritura puede ocurrir bajo PROJECT_ROOT excepto denylist;
  - la lectura está permitida bajo el root autorizado EXCEPTO denylist, y se restringe además por el task-level read-set cuando el modelo de ejecución lo suministra.
- No tratar nombres de carpeta históricos (\01_HUMAN\, \02_CODE\, \03_ARTIFACTS\, \AI_ORCH\) como layout universal.

03.20_CONJUNTOS_DE_TAREA
- Si el modelo de ejecución declara un task-level read-set, no leer fuera de él.
- Si el modelo de ejecución declara un task-level write-set, no escribir fuera de él.
- La ausencia de un conjunto de tarea no autoriza salir del AUTHORISED_EXECUTION_ROOT.
- Denylist/secretos siguen aplicándose encima de cualquier conjunto declarado.

03.30_MODO_RESTRICTIVO_(OPCIONAL)
- Escritura de canon (HUMAN / Skills / GRC / contratos de autoridad) solo con aprobación explícita (modo governance).
- El resto de escrituras in-project sigue la allowlist del proyecto y el write-set de la tarea.

==========
04.00_DENYLIST
==========

04.10_SECRET_PATTERNS
Bloquear lectura/escritura:
- **\*.key
- **\*.pem
- **\*.pfx
- **\*.kdbx
- **\.env
- **\secrets\**
- **\credentials\**

04.20_ZONAS_SENSIBLES_DEL_PROYECTO
- snapshots de artefactos operativos (escritura solo por el orquestador)
- \.git\objects\            (no tocar directo)

04.30_DENYLIST_GANA
- Un path en denylist permanece prohibido aunque figure en allowlist, task write-set o root externo autorizado.

==========
05.00_POLITICA_DE_SCRIPTS_(RUNNER_ALLOWLIST)
==========

05.10_REGLA
- Executor no ejecuta comandos OS arbitrarios.
- Solo ejecuta scripts allowlisted desde runners controlados del proyecto (herramientas y artefactos de runner declarados).

05.20_ALLOWLIST_EJEMPLO
- RADAR.ps1 (si aplica)
- Test suite (ej: pytest, npm test) pero invocado por runner controlado.

05.30_PARAMETROS_CONTROLADOS
- Los parámetros de scripts son validados:
  - paths deben estar dentro del AUTHORISED_EXECUTION_ROOT,
  - no se aceptan strings que permitan “escape” (ej: ; & |).

==========
06.00_POLITICA_DE_DELETES_(QUARANTINE)
==========

- Todo delete => move a QUARANTINE dentro del AUTHORISED_EXECUTION_ROOT (ver EXEC_POLICY).
- La cuarentena de un sandbox externo permanece en ese root; no se mueve al árbol canónico del proyecto de forma silenciosa.
- Mantener meta:
  - timestamp,
  - motivo,
  - task id,
  - checkpoint id.

==========
07.00_EVIDENCIA_Y_LOGGING
==========

Registrar por cada acción:
- actor (executor / proposal worker)
- operation (create/edit/move/quarantine)
- authorised_execution_root
- path_before / path_after
- hash_before / hash_after (si aplica)
- resultado OK/FAIL

==========
08.00_CASOS_DE_FALLO_(TROUBLE)
==========

- Boundary violation => TROUBLE severidad MEDIA mínimo.
- Attempt secret access => TROUBLE severidad ALTA (riesgo).
- Script runner intento no allowlisted => FAIL + TROUBLE.
- Intento de ampliar el perímetro de forma implícita => FAIL + escalar.

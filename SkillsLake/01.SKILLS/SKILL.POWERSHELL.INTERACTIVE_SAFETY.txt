----------
1. PURPOSE
----------

This skill defines safe execution practices for PowerShell commands provided to a human operator in an interactive terminal.

The objective is to reduce syntax errors, partial-copy failures, execution drift, and avoidable interruptions when the user copies and pastes command blocks into PowerShell.

----------
2. PROBLEM STATEMENT
----------

During operational sessions, the following recurring error was observed:

else: The term 'else' is not recognized as a name of a cmdlet, function, script file, or executable program.
Check the spelling of the name, or if a path was included, verify that the path is correct and try again.

Root cause:
PowerShell interpreted `else` as a standalone command because the prior `if` block had already been closed and executed.

This often happens when a user copies a script in fragments, or when the interactive shell receives the `if` block and the `else` block as separate instructions.

----------
3. CORE RULE
----------

When writing PowerShell instructions for interactive copy/paste execution, avoid `else` unless the full `if/else` structure is guaranteed to be pasted and executed as one atomic block.

Preferred pattern:

if (Test-Path $Path) {
  Write-Host "Exists"
}

if (-not (Test-Path $Path)) {
  Write-Host "Missing"
}

Avoid this pattern in fragile interactive contexts:

if (Test-Path $Path) {
  Write-Host "Exists"
}
else {
  Write-Host "Missing"
}

The second pattern is valid PowerShell, but it is less robust when copied manually into an interactive console.

----------
4. STANDARD EXECUTION HEADER
----------

Every non-trivial PowerShell one-shot should include:

$ErrorActionPreference = "Stop"

Recommended minimal header:

cd "C:\TARGET\PATH"

$ErrorActionPreference = "Stop"

Write-Host "========== TASK NAME =========="

----------
5. LOCATION FIRST RULE
----------

Before providing a command, always state the execution location.

Example:

Location:
C:\01. GitHub\Skills

Command:
cd "C:\01. GitHub\Skills"

This prevents accidental execution in the wrong repository or directory.

----------
6. NO-ELSE INTERACTIVE PATTERN
----------

Use independent `if` blocks:

if (Test-Path $Source) {
  Copy-Item $Source $Target -Force
  Write-Host "Copied:"
  Write-Host $Source
}

if (-not (Test-Path $Source)) {
  Write-Host "Source not found:"
  Write-Host $Source
}

This pattern is more verbose but safer for human copy/paste workflows.

----------
7. PATH SAFETY
----------

Always quote Windows paths.

Correct:

cd "C:\01. GitHub\Skills"

Incorrect:

cd C:\01. GitHub\Skills

Reason:
Spaces in paths break unquoted commands.

----------
8. ERROR HANDLING
----------

Use:

$ErrorActionPreference = "Stop"

This turns many non-terminating PowerShell errors into terminating errors.

For critical file operations, validate before and after:

if (Test-Path $Target) {
  Write-Host "OK:"
  Write-Host $Target
}

if (-not (Test-Path $Target)) {
  throw "Missing expected target: $Target"
}

----------
9. COMMAND OUTPUT DISCIPLINE
----------

Each one-shot should produce visible section headers.

Recommended format:

Write-Host "========== PRECHECK =========="
Write-Host "========== EXECUTION =========="
Write-Host "========== VALIDATION =========="
Write-Host "========== STATUS =========="

This helps the AI and the human operator identify where an error occurred.

----------
10. HIGH-RISK COMMANDS
----------

The following commands require extra caution:

Remove-Item
Move-Item
git reset
git clean
git add .
git commit --no-verify
npm uninstall -g
Set-Content
Copy-Item -Recurse -Force

Rules:
- State the target path before execution.
- Back up first when relevant.
- Avoid wildcards unless validated.
- Prefer explicit path lists over broad patterns.
- Never use destructive commands without a status check first.

----------
11. BACKUP RULE
----------

Before modifying, deleting, or replacing operational files:

1. Create external backup.
2. Confirm backup path.
3. Perform change.
4. Validate result.
5. Show git status if inside a repo.

Preferred backup location examples:

C:\Users\aazcl\Desktop\<TASK>_BACKUP_<YYYYMMDD>
C:\00. Wings\99.Backups\<PROJECT>\<TASK>_<YYYYMMDD_HHMMSS>

Avoid placing temporary backups inside the repository unless explicitly intended.

----------
12. GIT REPO SAFETY
----------

Before modifying files inside a Git repository:

git status --short

After modifying files:

git status --short

Before commit:

git diff --cached --name-status
git diff --cached --stat

Never assume the working tree is clean.

----------
13. KNOWN ANTI-PATTERNS
----------

Anti-pattern 1:
Providing only a command without execution location.

Anti-pattern 2:
Using `else` in commands likely to be copied in fragments.

Anti-pattern 3:
Using `git add .` during mixed-change states.

Anti-pattern 4:
Creating temporary diagnostic files inside the repo and forgetting to remove them.

Anti-pattern 5:
Running destructive commands before inventory.

----------
14. ACCEPTANCE CRITERIA
----------

A PowerShell command block complies with this skill when:

1. It states the working directory.
2. It uses quoted paths.
3. It uses `$ErrorActionPreference = "Stop"` for non-trivial operations.
4. It avoids fragile interactive `else` blocks.
5. It prints clear section headers.
6. It validates critical results.
7. It avoids broad destructive actions.
8. It shows final status when operating inside Git.

----------
15. LESSON LEARNED
----------

PowerShell scripts written for a file and PowerShell commands written for interactive copy/paste are not the same product.

For human-guided AI operations, robustness beats elegance.

----------
16. LESSON LEARNED - HERE-STRING AND WRAPPER FILE SAFETY
----------

A second recurring failure mode was observed during MB-EXAM-005 / MB-EXAM-005R / MB-EXAM-005R2:

- A long PowerShell wrapper was pasted into an interactive console.
- The wrapper used an outer here-string to write a .ps1 file.
- Inside that wrapper, another here-string was used to define Python code.
- PowerShell interpreted the inner terminator as the end of the outer here-string.
- Everything after that point executed loose in the console.
- Variables such as ProducerPath, ReportPath, RegisterPath and LogPath became null.
- Functions such as Invoke-NativeChecked were not available.
- try, catch and finally blocks were executed as orphan commands.
- A manual STATUS OK line was printed even though the operation had failed.

Root cause:

PowerShell here-strings are delimiter-sensitive. Nested here-strings using the same delimiter pattern are unsafe when generating scripts interactively. This is worse when the human operator pastes a large block into the console instead of executing a saved .ps1 file.

Operational conclusion:

A script that works as a file is not automatically safe as an interactive paste block. Delivery format is part of the design.

----------
17. CORE RULE - DO NOT NEST FRAGILE HERE-STRINGS IN INTERACTIVE WRAPPERS
----------

Avoid this in interactive wrappers:

Outer wrapper:
@'
...
Inner generated script:
ProducerCode = @'
...
'@
...
'@ | Set-Content ...

This can prematurely close the outer block and cause partial execution.

Preferred options:

Option A - Write the final .ps1 file directly, then execute it.
Option B - Use a different content construction method, such as an array of lines joined with CRLF.
Option C - Use base64 payload only when justified and clearly validated.
Option D - Use double-quoted here-string inside single-quoted outer wrapper only if there is no variable expansion risk and delimiters are visually audited.

Recommended default for AI-guided human execution:

1. Create a script file under Temp.
2. Validate that the script file exists.
3. Execute the script file with powershell -NoProfile -ExecutionPolicy Bypass -File.
4. Validate outputs.
5. Never run the internal body manually line by line.

----------
18. TRY/CATCH/FINALLY ATOMICITY RULE
----------

try/catch/finally must be executed as one atomic block.

Never instruct the user to execute finally separately.

Invalid operational pattern:

try {
  ...
}

Then later:

finally {
  Stop-Transcript
}

This produces:

finally: The term 'finally' is not recognized...

Correct pattern:

Place try/catch/finally inside a saved .ps1 file or provide a single complete paste block that cannot be split.

For fragile human workflows, prefer:

try { Stop-Transcript | Out-Null } catch {}

as a standalone cleanup command before a new execution, not as an orphan finally block.

----------
19. NO BASH HEREDOC IN POWERSHELL RULE
----------

Do not use Bash heredoc syntax inside PowerShell:

python - <<'PY'
import sys
PY

This is Bash syntax, not PowerShell syntax.

PowerShell-safe alternatives:

python -c "import sys; print(sys.version)"

or write a temporary .py file and execute:

Set-Content -LiteralPath "Temp\script.py" -Value $PythonLines -Encoding UTF8
python "Temp\script.py"

----------
20. FALSE OK PROHIBITION
----------

Never accept a final STATUS OK line if earlier output contains:

- Cannot bind argument because it is null.
- The term '<function>' is not recognized.
- ParserError.
- Unexpected token.
- catch/finally not recognized.
- Missing output.
- Failed native command.

A valid OK requires:

1. All critical variables are non-null.
2. The main command executed.
3. The expected artifact exists.
4. The log path exists.
5. Output validation confirms file sizes or command results.
6. No unhandled error appears before the summary.

If any of these fail, mark the minibattle as FAILED or RECOVERY_REQUIRED. Do not progress the backlog based on a printed OK alone.

----------
21. ACCEPTANCE CRITERIA ADDENDUM
----------

A PowerShell one-shot involving generated scripts complies with this skill only when:

1. It does not depend on fragile nested here-string delimiters.
2. It writes long generated scripts to a .ps1 file before execution.
3. It validates script creation before execution.
4. It does not mix Bash heredoc syntax into PowerShell.
5. It prevents orphan try/catch/finally blocks.
6. It treats manually printed OK lines as insufficient evidence.
7. It validates outputs using Test-Path/Get-Item or equivalent.
8. It emits clear START/END markers.
9. It tells the human exactly from where to copy terminal output.
10. It avoids continuing after null critical paths.

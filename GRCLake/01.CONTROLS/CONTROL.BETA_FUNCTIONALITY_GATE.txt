## 01. Purpose

This control defines what counts as a real SkillsMachine beta for user and management purposes.

It exists to prevent internal governance artifacts, reports, scorecards, speeches, or agent experiments from being misclassified as user-visible product progress.

## 02. Management Interest Rule

Management-facing progress must be tied to visible functionality.

The following items are internal evidence only and do not count as beta functionality by themselves:

- reports;
- presentations;
- scorecards;
- governance artifacts;
- BATON updates;
- RADAR outputs;
- GRC documents;
- AI-agent comparison logs;
- speeches or promises to management.

These artifacts are useful only when they support, verify, or unblock a working beta workflow.

## 03. Beta Functional Definition

A SkillsMachine beta is accepted only when a non-technical user can execute a real workflow and obtain a useful output without reading the repository and without depending on the operator to manually explain each step.

BETA_FUNCTIONALITY_GATE:
A beta candidate must satisfy all of the following:

1. Clear user entrypoint:
   The user knows where to start.

2. Observable action:
   The system performs a real operation.

3. Useful output:
   The system produces a file, screen, command result, package, dashboard, checklist, or state update that the user can understand.

4. Repeatability:
   The same workflow can be repeated by another user with consistent results.

5. Five-minute demo:
   Management can see problem -> action -> output in a short live demonstration.

6. No repository-reading dependency:
   The user does not need to inspect source folders, internal governance files, or implementation notes to operate the beta.

## 04. Non-Beta Classification

If a work item only improves internal governance, agent benchmarking, branch hygiene, documentation, or evidence quality, classify it as:

INTERNAL_ENABLEMENT

not:

BETA_FUNCTIONALITY

unless it directly ships a user-executable workflow.

## 06. Preferred Beta Slice

The first credible SkillsMachine beta should prioritize a visible launcher or command workflow for:

1. Continue session;
2. Generate upload/usecase package;
3. Close session with BATON/backlog/RADAR updates;
4. Show current project state/readiness.

This is more management-relevant than additional reports or scorecards.

## 07. Acceptance Gate

Before claiming beta status, the workstream must answer:

- What does the user click or run?
- What input does the user provide?
- What output does the user receive?
- Can the workflow be repeated without the project owner?
- Can management understand the result in five minutes?

If any answer is missing, the work item is not beta-ready.

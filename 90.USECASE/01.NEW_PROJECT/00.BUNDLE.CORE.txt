00.20_CONTEXTO_DEL_PROBLEMA_Y_OBJETIVOS
==========

00.20.01_PROBLEMAS_REALES_QUE_MOTIVAN_ESTE_SKILL

a) Rutas demasiado largas en Windows (≈260 caracteres) que rompen copias, zips,
sincronización (OneDrive, etc.) y tooling.

b) Nombres extremadamente verbosos y heterogéneos que dificultan la lectura y
el parseo automático.

c) Falta de compatibilidad entre nombres de FS (File System) y claves para BD
(Base de Datos).

d) Refactors costosos porque versión, WBS, título y demás se mezclan en el nombre
del archivo.

e) Inconsistencia entre proyectos y sistemas: cada uno inventa su propio esquema
de nombres, obligando a RADAR y a la IA a “adivinar” patrones.

00.20.02_OBJETIVO_PRINCIPAL

Definir un estándar único y simple para:

a) WBS interno (estructura dentro de los archivos).
b) IDs cortos de archivos y carpetas (FS-friendly).
c) IDs para BD (DB-friendly).

00.20.03_OBJETIVO_SECUNDARIO

Permitir que los nombres “humanos” puedan ser largos y explicativos sin romper:

a) Límites de Windows.
b) Esquemas de BD.
c) Scripts y tooling que dependan de los IDs.

01.00_DEFINICIONES_BASICAS
==========

01.00.01_WBS_INTERNO

Estructura jerárquica dentro de un documento (por ejemplo: 01.00, 01.10, 01.20, etc.).

Función:

Ordenar ideas y secciones de forma estable.

Permitir referencias internas tipo “ver 03.20 de este documento”.

No tiene obligación de coincidir con estructura de carpetas.

01.00.02_ID_FS_(ID_DE_FILE_SYSTEM)

Identificador corto y estable que se usa en nombres de archivos y carpetas.

Reglas mínimas:

ASCII básico, sin espacios, sin tildes, sin caracteres raros.

Amigable para Windows (ruta total razonable).

Se compone normalmente de:

Prefijo de frame o proyecto (FRM).

Tipo lógico (TIPO).

Secuencia numérica (NNNN).

Opcional: sufijo humano corto ASCII.

Ejemplo:

PF_HUM_0005

EVA_SKL_0101

WNG_TL_0200_REGENALL

01.00.03_ID_DB_(ID_DE_BASE_DE_DATOS)

Clave para BD:

Lo más corta posible.

Sin dependencias directas de rutas físicas.

Idealmente unívoca para cada elemento lógico relevante.

Puede reutilizar el patrón ID_FS o derivarlo, pero siempre con mapping claro ID_DB ↔ ID_FS.

01.00.04_FRAME

Conjunto coherente de reglas y artefactos: PFUNDATIONS, EVA.EOL, WINGS, proyectos, etc.

01.00.05_SKILL

Estándar transversal basado en errores reales que define “cómo se trabaja”.
Los frames deben respetar los SKILLS, salvo excepciones justificadas.

01.00.06_CATALOGO_FRM_(NUEVO, RECOMENDADO)

FRM recomendado (ejemplos; cada ecosistema mantiene su catálogo):
- PF   = PFUNDATIONS
- EVA  = EVA.EOL
- WNG  = WINGS
- KLAB = Kumquat Lab
- PROJ = Proyecto puntual
- OPS  = Operaciones / runbooks
- SYS  = Sistema base transversal

Regla:
- Si agregas FRM nuevo, documentarlo en el HUMAN root del ecosistema o en un catálogo central.

02.00_PROBLEMAS_HISTORICOS_QUE_ESTE_SKILL_ATACA
==========

02.00.01_PROBLEMA_1_RUTAS_LARGAS_EN_WINDOWS

Árboles profundos + nombres largos + sincronización = riesgo de superar límite de ruta.

Síntomas:

Errores al copiar/mover/eliminar.

Imposibilidad de zippear.

Fallos de scripts.

02.00.02_PROBLEMA_2_NOMBRES_BONITOS_PERO_INESCALABLES

Espacios, tildes, ñ, caracteres especiales.

Mezcla de WBS, título, versión en el mismo string.

Resultado:

Keys poco confiables en BD.

Dificultad para queries limpias.

Dificultad de parseo automático.

02.00.03_PROBLEMA_3_REFACTORS_CAROS

Cambias versión/título y el nombre de archivo cambia → cascada de roturas.

02.00.04_PROBLEMA_4_INCONSISTENCIA_ENTRE_SISTEMAS

Cada proyecto inventa su lógica.
RADAR y tooling deben “adivinar” patrones.

==========
03.00_PRINCIPIOS_DE_DISENO_PARA_WBS_E_IDS
==========

03.00.01_PRINCIPIO_1_SEPARAR_CAPAS

WBS interno → organización conceptual dentro del archivo.

ID_FS → integración con filesystem.

ID_DB → integración con BD/catálogos.

No mezclar todo en el mismo string.

03.00.02_PRINCIPIO_2_ID_CORTO_SEMANTICA_LARGA

El ID debe ser mecánico, corto y estable.

La semántica va en:

títulos de sección,

cabecera/metadatos,

campos descriptivos de BD.

03.00.03_PRINCIPIO_3_ASCII_ONLY_EN_IDS

En IDs FS y BD:

Letras A–Z (mayúsculas recomendadas).

Dígitos 0–9.

Separadores: _ y .

No se permiten:

tildes, ñ, espacios, símbolos raros.

03.00.04_PRINCIPIO_4_ESTABILIDAD_DE_IDS

Una vez asignado un ID:

No se cambia salvo rediseño estructural mayor.

Versiones van en metadatos, no en el ID.

03.00.05_PRINCIPIO_5_LONGITUD_CONTROLADA

Recomendaciones:

ID_FS ≤ 16 caracteres (sin sufijo).

ID_FS + sufijo ≤ 40 caracteres.

Nombre archivo (ID_FS + sufijo + ext) ≤ 80 caracteres.

Ruta objetivo < 200 caracteres.

04.00_ESTANDAR_DE_WBS_INTERNO_(DENTRO_DE_LOS_ARCHIVOS)
==========

04.00.01_FORMATO_BASICO

Formato sugerido:
NN.MM_TITULO_EN_MAYUSCULAS_SIN_TILDES

Ejemplo:
01.30_RELACION_CON_LOS_SKILLS_Y_ESTANDARES_DEL_SISTEMA

Características:

NN = bloque principal (00, 01, 02, …).

MM = subbloque (00, 10, 20, 30, etc.).

Título en mayúsculas, sin tildes ni caracteres especiales.

Guion bajo _ como separador.

04.00.02_USO_RECOMENDADO

Ordenar contenido y facilitar referencia (“ver 03.20”).

No se usa como nombre de archivo ni como clave de BD.

04.00.03_REGLAS_DE_ESTABILIDAD

Evitar renumerar WBS internos salvo rediseño profundo.

Si agregas un bloque intermedio, usar 01.15, 01.25, etc.

++++++++++

Regla:

Script con nombre fijo: RADAR.ps1

Motivo: contrato operativo humano / compatibilidad con tooling.

Objetivo:
Evitar drift silencioso.

++++++++++
05.00.09_VALIDACION_OPERATIVA_(NUEVO)
++++++++++

Regla:
Todo tooling/agente que cree nombres debe validar ID_FS.

Regex recomendado (mínimo):
^[A-Z0-9]{2,6}_[A-Z0-9]{2,6}_[0-9]{4}(_[A-Z0-9._]{1,30})?$

Checks:
- ASCII only
- longitud nombre archivo <= 80
- ruta total < 200 recomendado
- evitar duplicados (si existe catálogo)

Si falla:
- no crear archivo
- registrar TROUBLE (severidad BAJA/MEDIA según impacto)

++++++++++
05.00.09_IDS_PARA_ARTEFACTOS_DE_ORQUESTACION_(AI_ORCH)
++++++++++

Para artefactos del orquestador (logs, snapshots, reports), se recomienda:

- Mantener IDs cortos y parseables en nombres.
- Evitar timestamps en ID_FS (preferir timestamp en el sufijo del archivo).

Ejemplos:

AIOR_LOG_0001_RUNS\LOG.RUN.<RUN_ID>.txt
AIOR_CST_0001\COST_YYYYMMDD.ACTIVE.txt
AIOR_SNP_0001\SNAP-YYYYMMDD-HHMM-SEQ\manifest.txt

Objetivo:

Parseo por scripts + compatibilidad DB sin rutas imposibles.

04.40_CONTRATO_DE_EXIT_CODE_Y_ESTADO_FINAL
----------

OBLIGATORIO (CONTRATO):

Un script NO debe declarar éxito (OK/COMPLETADO) si hubo error no controlado.

Si ocurre una excepción no controlada:

Registrar error (Write-Error o equivalente).

Terminar con exit code != 0 (por defecto exit 1).

Imprimir FAIL (no OK) como estado final.

Solo se imprime “OK/COMPLETADO” si:

No hubo excepción,

Se generaron los outputs esperados (DONE binario),

Se dejó evidencia (rutas/archivos generados).

Objetivo:

Evitar falsos positivos (ej.: “OK” con fallos parciales).

Mejorar auditabilidad y confianza operacional.

----------
04.50_CONVENCIONES_POWERSHELL_(VERBS_APROBADOS)_(NUEVO)
----------

Problema real:
PowerShell emite warnings si una función/cmdlet usa verbos no aprobados:
"The cmdlet 'X' uses an unapproved verb."

Regla:
Preferir verbos aprobados por PowerShell (ejemplos comunes):
Get, Set, New, Remove, Add, Clear, Copy, Export, Import, Convert, Update,
Start, Stop, Invoke, Test, Confirm, Enter, Exit, Find, Format, Join,
Measure, Move, Out, Push, Pop, Read, Write.

Recomendación dura (para tu caso):
- Evitar: Validate-*
- Preferir: Test-* (validación)
- Preferir: Confirm-* (confirmación)
- Preferir: Invoke-* (ejecución/acción)

Ejemplo concreto:
- En vez de Validate-CISMetadata
  - Test-CISMetadata
  - Confirm-CISMetadata
  - Invoke-CISMetadataCheck

Nota:
Este skill no reemplaza documentación oficial de PowerShell; es una regla operacional anti-warning.

Problema real:
- En chats con IA, archivos largos se truncan o se interpretan parcial.

==========
01.00_PROPOSITO
==========

Este skill reduce fallas al crear archivos Markdown mediante IA y scripts.

Especialmente aplica cuando el contenido incluye:

- fences Markdown;
- bloques Mermaid;
- backticks triples;
- heredocs;
- plantillas con sintaxis sensible;
- caracteres que ChatGPT puede renderizar;
- contenido que Windows puede guardar con CRLF o BOM;
- scripts largos pegados desde editor gráfico.

El objetivo no es “hacer Markdown bonito”. El objetivo es que el archivo final quede correcto, reproducible, auditable y sin romper shell, Git ni renderizado.

==========
02.00_PROBLEMA_REAL
==========

Al crear .md desde ChatGPT + shell aparecen fallas típicas:

1. ChatGPT renderiza Mermaid o fences antes de tiempo.
2. El shell interpreta mal heredocs o bloques largos.
3. El usuario pega script largo y se corta.
4. Windows guarda CRLF/BOM y Bash falla.
5. Markdown final queda sin cierre de fence.
6. Git queda con warnings LF/CRLF.
7. El archivo parece creado, pero contiene marcadores erróneos o truncación.
8. El script entregado contiene backticks triples literales y la interfaz los interpreta antes de que el usuario pueda copiar el script correctamente.

Estos errores producen retrabajo y falsa sensación de avance.

==========
03.00_REGLA_CENTRAL
==========

No escribir sintaxis Markdown sensible directamente si el canal de entrega puede interpretarla, renderizarla, truncarla o romper el shell.

Usar marcadores inertes primero.

Luego convertir los marcadores a sintaxis Markdown real dentro del script, después de que el archivo fue escrito.

==========
04.00_REGLA_DURA_ANTI_FENCE_LITERAL
==========

Regla dura:

En respuestas ChatGPT, scripts pegables, heredocs, strings Python, ejemplos y plantillas intermedias, no incluir triple backtick literal.

Ni dentro de documentación.
Ni dentro de ejemplos.
Ni dentro de heredocs.
Ni dentro de strings de conversión.
Ni como “resultado esperado”.

La única forma permitida de producir un fence real dentro del archivo final es generarlo programáticamente después de la escritura, por ejemplo usando:

fence = chr(96) * 3

Esta regla existe porque la interfaz puede renderizar o encapsular mal cualquier triple backtick literal, incluso si el autor cree que está “dentro del script”.

==========
05.00_PATRON_SEGURO_DE_CREACION_MARKDOWN
==========

Flujo recomendado:

1. Crear archivo destino con contenido Markdown usando placeholders inertes.
2. Evitar backticks triples reales en el script entregado por IA.
3. Usar placeholders para fences, Mermaid y delimitadores peligrosos.
4. Escribir archivo.
5. Ejecutar conversión controlada de placeholders.
6. La conversión debe generar fences usando código de carácter, no texto literal con backticks triples.
7. Normalizar BOM/CRLF si aplica.
8. Verificar que el archivo final contiene el Markdown esperado.
9. Ejecutar validación relevante.
10. Registrar si el patrón evitó un fallo.

==========

Usar en contenido intermedio:

@@FENCE@@

06.20 Bash

Usar en contenido intermedio:

@@FENCE@@

06.30 Text

Usar en contenido intermedio:

para cierre o apertura genérica, según contexto.

- reemplazar @@FENCE_BASH@@ por fence + "bash";
- reemplazar @@FENCE_TEXT@@ por fence + "text";

SKILL.POWERSHELL.INTERACTIVE_SAFETY
==========

ID_UNICO..........: SKILL.POWERSHELL.INTERACTIVE_SAFETY
NOMBRE............: PowerShell Interactive Safety
TIPO..............: Skill operativo
DOMINIO...........: PowerShell / Windows / CLI execution
ESTADO............: ACTIVE
VERSION...........: 1.2
FECHA.............: 2026-06-09
ORIGEN............: Lessons learned from MB-GRC-014A / SkillsLake migration session; updated after MB-EXAM-005R2 PowerShell wrapper recovery; repaired by MB-SKILL-PS-INTERACTIVE-002

----------
1. PURPOSE
----------

This skill defines safe execution practices for PowerShell commands provided to a human operator in an interactive terminal.

The objective is to reduce syntax errors, partial-copy failures, execution drift, and avoidable interruptions when the user copies and pastes command blocks into PowerShell.

----------
2. PROBLEM STATEMENT
----------

During operational sessions, the following recurring error was observed:

else: The term 'else' is not recognized as a name of a cmdlet, function, script file, or executable program.
Check the spelling of the name, or if a path was included, verify that the path is correct and try again.

Root cause:
PowerShell interpreted `else` as a standalone command because the prior `if` block had already been closed and executed.

This often happens when a user copies a script in fragments, or when the interactive shell receives the `if` block and the `else` block as separate instructions.

----------
3. CORE RULE
----------

When writing PowerShell instructions for interactive copy/paste execution, avoid `else` unless the full `if/else` structure is guaranteed to be pasted and executed as one atomic block.

Preferred pattern:

if (Test-Path $Path) {
  Write-Host "Exists"
}

if (-not (Test-Path $Path)) {
  Write-Host "Missing"
}

Avoid this pattern in fragile interactive contexts:

if (Test-Path $Path) {
  Write-Host "Exists"
}
else {
  Write-Host "Missing"
}

The second pattern is valid PowerShell, but it is less robust when copied manually into an interactive console.

----------
4. STANDARD EXECUTION HEADER
----------

Every non-trivial PowerShell one-shot should include:

$ErrorActionPreference = "Stop"

Recommended minimal header:

cd "C:\TARGET\PATH"

$ErrorActionPreference = "Stop"

Write-Host "========== TASK NAME =========="

----------
5. LOCATION FIRST RULE
----------

Before providing a command, always state the execution location.

Example:

Location:
C:\01. GitHub\Skills

Command:
cd "C:\01. GitHub\Skills"

This prevents accidental execution in the wrong repository or directory.

----------
6. NO-ELSE INTERACTIVE PATTERN
----------

Use independent `if` blocks:

if (Test-Path $Source) {
  Copy-Item $Source $Target -Force
  Write-Host "Copied:"
  Write-Host $Source
}

if (-not (Test-Path $Source)) {
  Write-Host "Source not found:"
  Write-Host $Source
}

This pattern is more verbose but safer for human copy/paste workflows.

----------
7. PATH SAFETY
----------

Always quote Windows paths.

Correct:

cd "C:\01. GitHub\Skills"

Incorrect:

cd C:\01. GitHub\Skills

Reason:
Spaces in paths break unquoted commands.

----------
8. ERROR HANDLING
----------

Use:

$ErrorActionPreference = "Stop"

This turns many non-terminating PowerShell errors into terminating errors.

For critical file operations, validate before and after:

if (Test-Path $Target) {
  Write-Host "OK:"
  Write-Host $Target
}

if (-not (Test-Path $Target)) {
  throw "Missing expected target: $Target"
}

----------
9. COMMAND OUTPUT DISCIPLINE
----------

Each one-shot should produce visible section headers.

Recommended format:

Write-Host "========== PRECHECK =========="
Write-Host "========== EXECUTION =========="
Write-Host "========== VALIDATION =========="
Write-Host "========== STATUS =========="

This helps the AI and the human operator identify where an error occurred.

----------
10. HIGH-RISK COMMANDS
----------

The following commands require extra caution:

Remove-Item
Move-Item
git reset
git clean
git add .
git commit --no-verify
npm uninstall -g
Set-Content
Copy-Item -Recurse -Force

Rules:
- State the target path before execution.
- Back up first when relevant.
- Avoid wildcards unless validated.
- Prefer explicit path lists over broad patterns.
- Never use destructive commands without a status check first.

----------
11. BACKUP RULE
----------

Before modifying, deleting, or replacing operational files:

1. Create external backup.
2. Confirm backup path.
3. Perform change.
4. Validate result.
5. Show git status if inside a repo.

Preferred backup location examples:

C:\Users\aazcl\Desktop\<TASK>_BACKUP_<YYYYMMDD>
C:\00. Wings\99.Backups\<PROJECT>\<TASK>_<YYYYMMDD_HHMMSS>

Avoid placing temporary backups inside the repository unless explicitly intended.

----------
12. GIT REPO SAFETY
----------

Before modifying files inside a Git repository:

git status --short

After modifying files:

git status --short

Before commit:

git diff --cached --name-status
git diff --cached --stat

Never assume the working tree is clean.

----------
13. KNOWN ANTI-PATTERNS
----------

Anti-pattern 1:
Providing only a command without execution location.

Anti-pattern 2:
Using `else` in commands likely to be copied in fragments.

Anti-pattern 3:
Using `git add .` during mixed-change states.

Anti-pattern 4:
Creating temporary diagnostic files inside the repo and forgetting to remove them.

Anti-pattern 5:
Running destructive commands before inventory.

----------
14. ACCEPTANCE CRITERIA
----------

A PowerShell command block complies with this skill when:

1. It states the working directory.
2. It uses quoted paths.
3. It uses `$ErrorActionPreference = "Stop"` for non-trivial operations.
4. It avoids fragile interactive `else` blocks.
5. It prints clear section headers.
6. It validates critical results.
7. It avoids broad destructive actions.
8. It shows final status when operating inside Git.

----------
15. LESSON LEARNED
----------

PowerShell scripts written for a file and PowerShell commands written for interactive copy/paste are not the same product.

For human-guided AI operations, robustness beats elegance.

========== SKILL UPDATE MB-EXAM-005R2 POWERSHELL WRAPPER SAFETY BEGIN ==========

----------
16. LESSON LEARNED - HERE-STRING AND WRAPPER FILE SAFETY
----------

A second recurring failure mode was observed during MB-EXAM-005 / MB-EXAM-005R / MB-EXAM-005R2:

- A long PowerShell wrapper was pasted into an interactive console.
- The wrapper used an outer here-string to write a .ps1 file.
- Inside that wrapper, another here-string was used to define Python code.
- PowerShell interpreted the inner terminator as the end of the outer here-string.
- Everything after that point executed loose in the console.
- Variables such as ProducerPath, ReportPath, RegisterPath and LogPath became null.
- Functions such as Invoke-NativeChecked were not available.
- try, catch and finally blocks were executed as orphan commands.
- A manual STATUS OK line was printed even though the operation had failed.

Root cause:

PowerShell here-strings are delimiter-sensitive. Nested here-strings using the same delimiter pattern are unsafe when generating scripts interactively. This is worse when the human operator pastes a large block into the console instead of executing a saved .ps1 file.

Operational conclusion:

A script that works as a file is not automatically safe as an interactive paste block. Delivery format is part of the design.

----------
17. CORE RULE - DO NOT NEST FRAGILE HERE-STRINGS IN INTERACTIVE WRAPPERS
----------

Avoid this in interactive wrappers:

Outer wrapper:
@'
...
Inner generated script:
ProducerCode = @'
...
'@
...
'@ | Set-Content ...

This can prematurely close the outer block and cause partial execution.

Preferred options:

Option A - Write the final .ps1 file directly, then execute it.
Option B - Use a different content construction method, such as an array of lines joined with CRLF.
Option C - Use base64 payload only when justified and clearly validated.
Option D - Use double-quoted here-string inside single-quoted outer wrapper only if there is no variable expansion risk and delimiters are visually audited.

Recommended default for AI-guided human execution:

1. Create a script file under Temp.
2. Validate that the script file exists.
3. Execute the script file with powershell -NoProfile -ExecutionPolicy Bypass -File.
4. Validate outputs.
5. Never run the internal body manually line by line.

----------
18. TRY/CATCH/FINALLY ATOMICITY RULE
----------

try/catch/finally must be executed as one atomic block.

Never instruct the user to execute finally separately.

Invalid operational pattern:

try {
  ...
}

Then later:

finally {
  Stop-Transcript
}

This produces:

finally: The term 'finally' is not recognized...

Correct pattern:

Place try/catch/finally inside a saved .ps1 file or provide a single complete paste block that cannot be split.

For fragile human workflows, prefer:

try { Stop-Transcript | Out-Null } catch {}

as a standalone cleanup command before a new execution, not as an orphan finally block.

----------
19. NO BASH HEREDOC IN POWERSHELL RULE
----------

Do not use Bash heredoc syntax inside PowerShell:

python - <<'PY'
import sys
PY

This is Bash syntax, not PowerShell syntax.

PowerShell-safe alternatives:

python -c "import sys; print(sys.version)"

or write a temporary .py file and execute:

Set-Content -LiteralPath "Temp\script.py" -Value $PythonLines -Encoding UTF8
python "Temp\script.py"

----------
20. FALSE OK PROHIBITION
----------

Never accept a final STATUS OK line if earlier output contains:

- Cannot bind argument because it is null.
- The term '<function>' is not recognized.
- ParserError.
- Unexpected token.
- catch/finally not recognized.
- Missing output.
- Failed native command.

A valid OK requires:

1. All critical variables are non-null.
2. The main command executed.
3. The expected artifact exists.
4. The log path exists.
5. Output validation confirms file sizes or command results.
6. No unhandled error appears before the summary.

If any of these fail, mark the minibattle as FAILED or RECOVERY_REQUIRED. Do not progress the backlog based on a printed OK alone.

----------
21. ACCEPTANCE CRITERIA ADDENDUM
----------

A PowerShell one-shot involving generated scripts complies with this skill only when:

1. It does not depend on fragile nested here-string delimiters.
2. It writes long generated scripts to a .ps1 file before execution.
3. It validates script creation before execution.
4. It does not mix Bash heredoc syntax into PowerShell.
5. It prevents orphan try/catch/finally blocks.
6. It treats manually printed OK lines as insufficient evidence.
7. It validates outputs using Test-Path/Get-Item or equivalent.
8. It emits clear START/END markers.
9. It tells the human exactly from where to copy terminal output.
10. It avoids continuing after null critical paths.

SCOPE.............: one-shot scripts, temporary executable scripts, repository automation, recovery and escalation

==========
00.00_PRINCIPLE
==========

Do not avoid long one-shot scripts when the objective is fast controlled progress.

Govern them.

The first execution phase may use a large, comprehensive script when the task requires coordinated filesystem, validation, continuity, RADAR, commit and push operations.

The long script must not be pasted directly into the terminal.

It must be saved as a temporary executable file and run through a short activation wrapper.

==========
01.00_STANDARD_PATHS
==========

PowerShell:

Temp/<MB_ID>.ps1

WSL2 Bash:

Temp/<MB_ID>.sh

Forbidden:

- root-level MB scripts;
- stale generic TempScript execution without MB_ID guard;
- direct paste of long scripts into terminal;
- script-generated temporary files outside Temp/ unless explicitly intended and versioned.

==========
02.00_ACTIVATION_WRAPPER
==========

The activation wrapper must be short.

It must:

1. set the repository root;
2. define RUN_ID / MB_ID;
3. verify that the target script exists under Temp/;
4. verify that the script contains the expected MB_ID;
5. reject root-level temporary scripts;
6. normalize encoding when appropriate;
7. copy the script to the system temp directory;
8. execute the copy;
9. save a timestamped log under Temp/;
10. print the log;
11. print RUN_EXIT, HEAD_AFTER, STATUS_AFTER.

==========
03.00_SCRIPT_OUTPUT_CONTRACT
==========

Every long one-shot script must print a self-contained block:

========== <MB_ID> / START ==========
...
========== <MB_ID> / END ==========

The block must include:

- local time;
- root path;
- purpose;
- COPY_FROM_HERE: YES;
- precheck;
- current branch and HEAD;
- git status before;
- main actions performed;
- validation result;
- RADAR result when relevant;
- staged files;
- commit hash or explicit no-commit reason;
- push result or explicit no-push reason;
- readiness summary when relevant;
- git status after;
- final status;
- next action.

The user should only need to copy the START/END block back to the assistant.

==========
04.00_ERROR_POLICY
==========

If the first large script fails, do not continue blindly.

The next attempt must reduce scope or isolate the failing stage.

Maximum assisted repair sequence:

- Attempt 1: comprehensive one-shot for fast progress.
- Attempt 2: reduced diagnostic or targeted recovery script.
- Attempt 3: second reduced recovery / final local isolation.
- After third persistent failure: escalate to Codex Desktop or Claude Code Desktop.

The escalation agent must receive:

- root path;
- failing MB_ID;
- latest START/END block;
- git status;
- expected deliverable;
- explicit boundary of what may be edited;
- validation command;
- expected proof of resolution.

==========
05.00_FAILURE_OUTPUT_REQUIREMENTS
==========

On failure, the script must report:

- failing stage;
- failing command;
- exit code when available;
- dirty/untracked files;
- whether any commit happened;
- whether any push happened;
- what is safe to retry;
- exact next action.

The script must not print a false success line after a failed mandatory stage.

Avoid contradictory lines such as READINESS_EXIT: 0 when readiness failed.

==========
06.00_GIT_POLICY
==========

Before execution:

- repo should be clean unless the purpose is cleanup/recovery;
- if dirty, fail early with status details.

During execution:

- stage only intended files;
- avoid broad git add . unless the task explicitly requires it;
- never stage Temp/;
- never stage root-level one-shot scripts.

After execution:

- git status must be clean or the script must explain why not;
- readiness should be OK for closeable work;
- unpushed commits must be reported.

==========
07.00_FAST_PROGRESS_POLICY
==========

This protocol supports speed.

The preferred first move for repository automation is a high-coverage one-shot script, not a sequence of small manual commands.

The quality bar is not smallness.

The quality bar is:

- reproducibility;
- controlled scope;
- clear failure boundary;
- START/END observability;
- clean repo at close;
- maximum three assisted repair attempts before escalation.

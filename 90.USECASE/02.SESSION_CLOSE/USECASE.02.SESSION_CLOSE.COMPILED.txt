00.20_CONTEXTO_DEL_PROBLEMA_Y_OBJETIVOS
==========

00.20.01_PROBLEMAS_REALES_QUE_MOTIVAN_ESTE_SKILL

a) Rutas demasiado largas en Windows (≈260 caracteres) que rompen copias, zips,
sincronización (OneDrive, etc.) y tooling.

b) Nombres extremadamente verbosos y heterogéneos que dificultan la lectura y
el parseo automático.

c) Falta de compatibilidad entre nombres de FS (File System) y claves para BD
(Base de Datos).

d) Refactors costosos porque versión, WBS, título y demás se mezclan en el nombre
del archivo.

e) Inconsistencia entre proyectos y sistemas: cada uno inventa su propio esquema
de nombres, obligando a RADAR y a la IA a “adivinar” patrones.

00.20.02_OBJETIVO_PRINCIPAL

Definir un estándar único y simple para:

a) WBS interno (estructura dentro de los archivos).
b) IDs cortos de archivos y carpetas (FS-friendly).
c) IDs para BD (DB-friendly).

00.20.03_OBJETIVO_SECUNDARIO

Permitir que los nombres “humanos” puedan ser largos y explicativos sin romper:

a) Límites de Windows.
b) Esquemas de BD.
c) Scripts y tooling que dependan de los IDs.

01.00_DEFINICIONES_BASICAS
==========

01.00.01_WBS_INTERNO

Estructura jerárquica dentro de un documento (por ejemplo: 01.00, 01.10, 01.20, etc.).

Función:

Ordenar ideas y secciones de forma estable.

Permitir referencias internas tipo “ver 03.20 de este documento”.

No tiene obligación de coincidir con estructura de carpetas.

01.00.02_ID_FS_(ID_DE_FILE_SYSTEM)

Identificador corto y estable que se usa en nombres de archivos y carpetas.

Reglas mínimas:

ASCII básico, sin espacios, sin tildes, sin caracteres raros.

Amigable para Windows (ruta total razonable).

Se compone normalmente de:

Prefijo de frame o proyecto (FRM).

Tipo lógico (TIPO).

Secuencia numérica (NNNN).

Opcional: sufijo humano corto ASCII.

Ejemplo:

PF_HUM_0005

EVA_SKL_0101

WNG_TL_0200_REGENALL

01.00.03_ID_DB_(ID_DE_BASE_DE_DATOS)

Clave para BD:

Lo más corta posible.

Sin dependencias directas de rutas físicas.

Idealmente unívoca para cada elemento lógico relevante.

Puede reutilizar el patrón ID_FS o derivarlo, pero siempre con mapping claro ID_DB ↔ ID_FS.

01.00.04_FRAME

Conjunto coherente de reglas y artefactos: PFUNDATIONS, EVA.EOL, WINGS, proyectos, etc.

01.00.05_SKILL

Estándar transversal basado en errores reales que define “cómo se trabaja”.
Los frames deben respetar los SKILLS, salvo excepciones justificadas.

01.00.06_CATALOGO_FRM_(NUEVO, RECOMENDADO)

FRM recomendado (ejemplos; cada ecosistema mantiene su catálogo):
- PF   = PFUNDATIONS
- EVA  = EVA.EOL
- WNG  = WINGS
- KLAB = Kumquat Lab
- PROJ = Proyecto puntual

02.00_PROBLEMAS_HISTORICOS_QUE_ESTE_SKILL_ATACA

02.00.01_PROBLEMA_1_RUTAS_LARGAS_EN_WINDOWS

Árboles profundos + nombres largos + sincronización = riesgo de superar límite de ruta.

Síntomas:

Errores al copiar/mover/eliminar.

Imposibilidad de zippear.

Fallos de scripts.

02.00.02_PROBLEMA_2_NOMBRES_BONITOS_PERO_INESCALABLES

Espacios, tildes, ñ, caracteres especiales.

Mezcla de WBS, título, versión en el mismo string.

Resultado:

Keys poco confiables en BD.

Dificultad para queries limpias.

Dificultad de parseo automático.

02.00.03_PROBLEMA_3_REFACTORS_CAROS

Cambias versión/título y el nombre de archivo cambia → cascada de roturas.

02.00.04_PROBLEMA_4_INCONSISTENCIA_ENTRE_SISTEMAS

Cada proyecto inventa su lógica.
RADAR y tooling deben “adivinar” patrones.

03.00_PRINCIPIOS_DE_DISENO_PARA_WBS_E_IDS

03.00.01_PRINCIPIO_1_SEPARAR_CAPAS

WBS interno → organización conceptual dentro del archivo.

ID_FS → integración con filesystem.

ID_DB → integración con BD/catálogos.

No mezclar todo en el mismo string.

03.00.02_PRINCIPIO_2_ID_CORTO_SEMANTICA_LARGA

El ID debe ser mecánico, corto y estable.

La semántica va en:

títulos de sección,

cabecera/metadatos,

campos descriptivos de BD.

03.00.03_PRINCIPIO_3_ASCII_ONLY_EN_IDS

En IDs FS y BD:

Letras A–Z (mayúsculas recomendadas).

Dígitos 0–9.

Separadores: _ y .

No se permiten:

tildes, ñ, espacios, símbolos raros.

03.00.04_PRINCIPIO_4_ESTABILIDAD_DE_IDS

Una vez asignado un ID:

No se cambia salvo rediseño estructural mayor.

Versiones van en metadatos, no en el ID.

03.00.05_PRINCIPIO_5_LONGITUD_CONTROLADA

Recomendaciones:

ID_FS ≤ 16 caracteres (sin sufijo).

ID_FS + sufijo ≤ 40 caracteres.

Nombre archivo (ID_FS + sufijo + ext) ≤ 80 caracteres.

Ruta objetivo < 200 caracteres.

04.40_CONTRATO_DE_EXIT_CODE_Y_ESTADO_FINAL
----------

OBLIGATORIO (CONTRATO):

Un script NO debe declarar éxito (OK/COMPLETADO) si hubo error no controlado.

Si ocurre una excepción no controlada:

Registrar error (Write-Error o equivalente).

Terminar con exit code != 0 (por defecto exit 1).

Imprimir FAIL (no OK) como estado final.

Solo se imprime “OK/COMPLETADO” si:

No hubo excepción,

Se generaron los outputs esperados (DONE binario),

Se dejó evidencia (rutas/archivos generados).

Objetivo:

Evitar falsos positivos (ej.: “OK” con fallos parciales).

Mejorar auditabilidad y confianza operacional.

----------
04.50_CONVENCIONES_POWERSHELL_(VERBS_APROBADOS)_(NUEVO)
----------

Problema real:
PowerShell emite warnings si una función/cmdlet usa verbos no aprobados:
"The cmdlet 'X' uses an unapproved verb."

Regla:
Preferir verbos aprobados por PowerShell (ejemplos comunes):
Get, Set, New, Remove, Add, Clear, Copy, Export, Import, Convert, Update,
Start, Stop, Invoke, Test, Confirm, Enter, Exit, Find, Format, Join,
Measure, Move, Out, Push, Pop, Read, Write.

Recomendación dura (para tu caso):
- Evitar: Validate-*
- Preferir: Test-* (validación)
- Preferir: Confirm-* (confirmación)
- Preferir: Invoke-* (ejecución/acción)

Ejemplo concreto:
- En vez de Validate-CISMetadata
  - Test-CISMetadata
  - Confirm-CISMetadata
  - Invoke-CISMetadataCheck

Nota:
Este skill no reemplaza documentación oficial de PowerShell; es una regla operacional anti-warning.

00.20_CONTEXTO_Y_OBJETIVOS
==========

BATON existe porque:
- Trabajar con IA (y con humanos) sin snapshot operativo produce pérdidas de continuidad.
- Un “HUMAN” explica el por qué; un “RADAR” describe el FS; un “SKILL” define método.
- Pero al levantar una IA en blanco, el primer problema real es: “¿Qué cargo y en qué orden?”

Objetivo principal:
- Permitir que una IA en blanco tenga continuidad operativa del proyecto en 1–2 minutos de lectura.

Objetivo secundario:
- Evitar drift: BATON no redefine reglas; solo referencia lo que ya es canon (HUMAN/SKILLS/RADAR).

==========
01.00_PROPOSITO_Y_ROL_DE_BATON
==========

----------
01.10_QUE_ES_BATON_STATE
----------

BATON.STATE es un archivo de texto (.txt) por proyecto que:

- Resume el estado operativo relevante para una IA en blanco.
- Indica qué HUMAN y SKILLS son canon en ese proyecto.
- Indica qué RADAR usar como mapa de archivos.
- Expone objetivos activos, contexto mínimo y focos de trabajo.

BATON.STATE es continuidad operativa para IA, nada más.
No crea reglas nuevas de negocio ni de código.

----------
01.20_POR_QUE_ES_POR_PROYECTO
----------

Se define un BATON.STATE por proyecto (no uno global) porque:

- Cada proyecto tiene objetivos, artefactos y riesgos propios.
- Los HUMAN y SKILLS “core” por proyecto no son siempre los mismos.
- La continuidad que te importa cuando levantas una IA es la del proyecto en cuestión.

Ejemplos de “proyecto”:

- PFUNDATIONS (marco personal/profesional).
- EVA.EOL (evaluación y aprendizaje).
- Proyecto inmobiliario específico.
- Sub-sistema técnico con vida propia.

----------
01.30_PRECEDENCIA_DE_FUENTES
----------

Orden de precedencia cuando hay conflicto:

1) HUMAN.README de nivel superior.
2) HUMAN.README específico del proyecto.
3) SKILLS/estándares (incluyendo este BATON).
4) BATON.STATE del proyecto.
5) Código/scripts/configuración.

Si BATON.STATE contradice HUMAN o SKILLS, BATON.STATE está mal
y debe regenerarse.

BATON.STATE nunca es “fuente de verdad funcional”; es derivado consolidado.

----------
01.40_RELACION_CON_ORQUESTACION_IA_(NUEVO)
----------

Si el proyecto usa agentes que crean/editar/eliminan archivos:
- BATON.STATE debe declarar explícitamente el “límite operativo” del agente.
- BATON.STATE NO define políticas nuevas, pero SÍ debe apuntar a los SKILLS que las definen.

En otras palabras:
- BATON no inventa sandbox/costos/routing.
- BATON referencia qué política aplica en este proyecto.

- `00.0_BATON_PFUNDATIONS.txt`
- `00.0_BATON_EVA_EOL.txt`
- `00.0_BATON_PROY_WHISPERING_LAKES.txt`

- Sea fácil de encontrar por humanos y por scripts.

04.10_LOAD_ORDER_TIPICO
++++++++++

La IA no debe:

- Modificar BATON.STATE por iniciativa propia.
- Alterar HUMAN/SKILLS basándose solo en lo que dice BATON.STATE.

Cualquier cambio en BATON.STATE debe ser validado por humano.

BATON.STATE NO duplica políticas; solo referencia los skills canónicos.

- Si un HUMAN supera el punto en que nadie quiere leerlo completo,
  se evalúa partir en HUMAN hijos, manteniendo un HUMAN root más estable.

# SKILL.HUMAN_CONTROLLED_SCRIPT_EXECUTION

MARKER: MB-SM-052A_CROSS_RUNTIME_EXECUTION_CONTRACT
VERSION: v1.1
STATUS: ACTIVE
LAYER: SKILL
OWNER_DOMAIN: SkillsMachine
PURPOSE: Define a shell/runtime-agnostic execution method for AI-delivered executable files.

==========
00.00 PRINCIPLE
==========

This methodology is not a PowerShell-only method.

It is a human-controlled local execution contract:

AI prepares an executable artifact.
Human saves it in the project TEMP path.
Human executes it locally from VS Code or terminal.
The executable emits AI_TAIL_START / AI_TAIL_END.
Human returns the AI_TAIL and any relevant TEMP outputs.
AI interprets evidence and provides the next single action.

PowerShell, Python, Bash, Node, SQL wrappers, Docker wrappers, Excel helpers, and Power Query generators are runtime adapters.

==========
01.00 DEFAULT WORKFLOW
==========

A. AI provides the executable file content or downloadable executable artifact:
   - .ps1
   - .py
   - .sh
   - .js
   - .sql runner wrapper
   - other executable/script file

B. Human saves it in the project TEMP path.

C. Human executes the exact command provided by the AI.
   The command must work from any current directory.

D. Human returns:
   - AI_TAIL_START through AI_TAIL_END; and/or
   - specific files created in TEMP that the AI explicitly requested.

==========
02.00 TEMP PATH RULE
==========

The AI must not invent a TEMP path.

The TEMP path must come from project canon:
- BATON
- WHOAMI
- HUMAN
- README
- active usecase instructions
- explicit user instruction

If TEMP path is missing and execution requires it, ask or declare a safe project-local TEMP path before script delivery.

Examples:
- SkillsMachine: C:\01. GitHub\Skills\SyS\Temp
- CloseReport: C:\01. GitHub\CloseReport\99.TEMP

==========
03.00 EXECUTION COMMAND RULE
==========

The AI must provide a command executable from any location.

PowerShell example:
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File "C:\path\to\temp\script.ps1"

Python example:
python "C:\path\to\temp\script.py"

Bash example:
bash "/mnt/c/path/to/temp/script.sh"

The script itself must resolve PROJECT_ROOT and TEMP_PATH explicitly.

==========
04.00 AI_TAIL RULE
==========

AI_TAIL is mandatory for every executable artifact unless the runtime cannot support stdout or file output.

Minimum AI_TAIL fields:
- AI_TAIL_SCHEMA=v1
- MB_ID or TASK_ID
- RUNTIME
- ROOT
- TEMP_PATH
- FINAL_STATUS
- BLOCKER
- FILES_CREATED
- FILES_MODIFIED
- VALIDATION_STATUS
- COMMIT_PUSH_PERFORMED=NO unless explicitly authorized otherwise
- NEXT_ACTION

The script must not report success unless the relevant operation actually passed.

==========
05.00 IF TOOL DOES NOT SUPPORT THE METHOD
==========

If a tool/runtime cannot produce AI_TAIL, exit code, stdout, or auditable file output, the AI must not pretend compliance.

It must declare:
- CAN_USE_METHOD_FULLY: NO
- CAN_USE_METHOD_PARTIALLY: YES/NO
- MISSING_CAPABILITIES
- SAFE_ADAPTER
- RECOMMENDATION

Examples:
Power Query M cannot emit AI_TAIL directly.
Recommendation: generate M code with Python or PowerShell and validate outputs externally.

Excel manual operations cannot guarantee exit code.
Recommendation: use a PowerShell/Python validator around the workbook.

SQL alone may not support the contract.
Recommendation: execute SQL through Python/PowerShell wrapper that emits AI_TAIL.

==========
06.00 DELIVERY MODE
==========

Default delivery mode:
- AI provides code or a downloadable file.
- Human saves to TEMP.
- Human executes locally.
- Human returns AI_TAIL.

ZIPs or multi-file bundles are allowed only when they reduce token cost or complexity and remain explicit, reviewable, and project-local.

The AI must not rely on invisible tool-side execution for final delivery unless explicitly requested.

==========
07.00 GIT RULE
==========

Scripts may inspect Git status and produce commit-ready reports.

Scripts must not commit or push unless the user explicitly delegates that action.

Prohibited by default:
- git add .
- git add -A
- automatic commit
- automatic push
- hiding dirty state
- continuing after unknown dirty worktree

==========
08.00 ADAPTER MINIMUMS
==========

PowerShell:
- Prefer pwsh when available.
- Use PS 5.1-compatible constructs when Windows PowerShell is expected.
- Avoid scalar .Count hazards by wrapping collections with @(...).
- Avoid Write-Host "=" * 60 ambiguity.
- Use GIT_PAGER=cat.
- Emit AI_TAIL in controlled final path.

Python:
- Use pathlib.
- Use try/except/finally or equivalent tail guarantee.
- Print AI_TAIL before sys.exit.
- Explicit encoding for CSV/text.
- Do not write outside project root or TEMP unless declared.

Bash:
- Use set -Eeuo pipefail.
- Use trap for tail.
- Use printf.
- Preserve exit code.
- Use git --no-pager.

Node:
- Capture uncaughtException and unhandledRejection.
- Emit tail before process.exit.

Docker:
- Use wrapper script to build/run/capture logs and emit AI_TAIL.

Power Query / Excel / VBA:
- Use generator/installer/validator wrapper when direct AI_TAIL is unavailable.

==========
09.00 COMPLIANCE GATE
==========

Before delivering executable code, the AI must be able to answer:

EXECUTION_CONTRACT_GATE:
- PROJECT:
- PROJECT_ROOT:
- TEMP_PATH:
- SCRIPT_NAME:
- SCRIPT_RUNTIME:
- TARGET_SHELL:
- MIN_VERSION:
- CAN_RUN_FROM_ANY_LOCATION:
- AI_TAIL_SUPPORTED:
- EXIT_CODE_SUPPORTED:
- FILE_OUTPUT_SUPPORTED:
- GIT_AWARE:
- AUTO_COMMIT_ALLOWED:
- USER_EXECUTES_LOCALLY:
- LIMITATION:
- RECOMMENDATION:
- DECISION: PROCEED / ADAPT / BLOCK

If the gate cannot be completed, do not deliver executable code.

==========
10.00 FAILURE MODE
==========

If the script fails, the AI must request only:
- AI_TAIL_START through AI_TAIL_END, if present;
- otherwise the minimal terminal segment needed to diagnose;
- specific TEMP outputs if relevant.

Do not ask for broad logs or full repo uploads by default.

11.00 COMMON MODULE RULE
For SkillsMachine repository automation, executables should import and use
SyS/A_Tools/Common/SkillsMachine.Automation.psm1 helpers where applicable
instead of re-implementing git invocation, JSON parsing, hashing, UTF-8
writing, or worktree assertions inline.

12.00 DISTINCT EXECUTION STAGES
Every non-trivial executable must keep four distinct, visibly labeled stages:
1. PREFLIGHT: context identity, expected branch/HEAD, clean-worktree or
   authorized-dirty check, input existence.
2. EXECUTION: the actual mutation or analysis work.
3. PROBE: at least one representative functional verification of the output
   (not just "the command exited 0").
4. POST-VERIFICATION: final state check (git status, diff scope, output
   hashes) plus TOVS/AI_TAIL emission.
A stage failure must stop later stages and be reported as the failing stage.

13.00 TOVS/AI_TAIL ATTRIBUTION FIELDS
The TOVS/AI_TAIL block must attribute the run precisely, including at minimum:
- EXECUTABLE (exact script path/name);
- OBJECTIVE (MB_ID or TASK_ID);
- LAST_STAGE (the stage reached);
- FINAL_STATUS;
- NEXT_ACTION (singular).
Plus runtime/project identity: RUNTIME, PROJECT_ROOT, and, when verifiable,
branch/HEAD. A report must never attribute execution to an agent or runtime
that did not actually run (see GRC.CROSS_RUNTIME_EXECUTION_CONTRACT and
GRC.PROJECT_CONTEXT_IDENTITY).

14.00 GENERATED OUTPUT IS NOT VALIDATED DELIVERY
Producing an output file is not delivery. Delivery requires the validation
stage to pass against that output. Scripts must not report delivery-complete
status based on file creation alone.

15.00 FAIL-CLOSED MANDATORY VALIDATORS
When a mandatory validator or gate artifact is missing, the run must FAIL,
not warn-and-skip. Missing validator = broken contract. (Evidence:
MB-SM-067B-D1-R1 converted the automation gate in Validate-System.ps1 from
warn-and-skip to fail-closed.)

16.00 FLAT TEMP UPLOAD PACKAGE
Evidence for human upload must be consolidated into flat files directly under
the project TEMP path (no nested folders), with unique objective/timestamp
prefixes, following GRC.SCRIPT_EXECUTION_STAGING and COMPACT_UPLOAD_PACK rules.

17.00 COMMIT/PUSH AUTHORIZATION BOUNDARY
No commit and no push without explicit human authorization for the specific
objective. Prior authorization for one MB does not carry over to the next.

00.20_CONTEXTO_DEL_PROBLEMA_Y_OBJETIVOS
==========

00.20.01_PROBLEMAS_REALES_QUE_MOTIVAN_RADAR

a) Proyectos crecen y se vuelven inmanejables sin inventario confiable.
b) Tooling e IA fallan cuando el repositorio no tiene mapa.
c) Auditorías, migraciones y refactors requieren trazabilidad.
d) Archivos binarios (xlsx/pdf/png) rompen intentos de "leer todo".
e) Históricos sin disciplina generan caos; sin históricos no hay continuidad.
f) En IA cloud, subir FULL/CORE completo puede disparar costos (COST_INCIDENT).
g) El contenido canónico (HUMAN) y el contenido de skills (SKILLS) necesitan
   compilarse aparte del resto del proyecto para que la IA los entienda como
   unidad completa, sin mezclarlos con código/artefactos operativos.

00.20.02_OBJETIVO_PRINCIPAL

Definir un estándar único para producir vistas:

LITE       : Inventario resumido + diffs básicos (operación diaria).
INDEX      : Inventario total + metadata (para navegación y auditoría).
CORE       : Contenido legible (texto/código) para análisis por IA/humano.
FULL       : Consolidación (INDEX + CORE + extras de auditoría como tree-size).
FULL.HUMAN : Compilación completa del contenido canónico de HUMAN, optimizada
             para lectura por IA.
FULL.SKILLS: Compilación completa del contenido de la carpeta SKILLS, separada
             del resto del proyecto, optimizada para lectura por IA.

00.20.03_OBJETIVO_SECUNDARIO

Asegurar que los outputs puedan:

Ser usados por humanos (lectura rápida, texto plano).

Ser consumidos por IA (chunks y determinismo).

Ser comparables entre ejecuciones (orden estable + formato consistente).

Reducir fricción/costo en cloud evitando "leer todo" sin necesidad.

==========
01.00_DEFINICIONES_BASICAS
==========

01.10_RADAR

RADAR es un estándar de "descripción del FS" (file system) de un proyecto, generado por tooling.

Regla dura:

RADAR describe, no decide.

RADAR no reemplaza decisiones humanas ni lógica de negocio.

----------
01.15_RADAR_LITE
----------

RADAR_LITE es una salida liviana para operación diaria:

- Basada en metadata (similar a INDEX).
- Puede incluir diffs básicos vs ejecución previa (NEW/MODIFIED/DELETED).
- No incluye contenido (no es CORE).
- No interpreta semántica (describe, no decide).
- En primera ejecución (sin histórico previo), no calcula diffs (ver 05.30).

01.20_RADAR_INDEX

Output que lista TODOS los archivos/carpetas relevantes y su metadata (sin contenido).

Incluye, típicamente:

ruta

tamaño

última modificación

tipo lógico

hash (regla por defecto, ver 06.15)

01.30_RADAR_CORE

Output que incluye el contenido SOLO de archivos legibles (texto/código/config).

No incluye:

imágenes, audio, video

pdf (sin OCR)

binarios

xlsx (no se leen celdas)

Nota: la "estructura superficial" de xlsx (nombres de hojas) vive en INDEX (06.30),
no en CORE. CORE nunca incluye contenido de xlsx bajo ninguna forma.

01.40_RADAR_FULL

Output que consolida:

INDEX + CORE

y agrega extras de auditoría (ej.: tree-size por carpeta)

FULL no agrega semántica de negocio; sigue siendo descriptivo.

----------
01.50_HUMAN_Y_SKILLS_COMO_CARPETAS_CANONICAS_(NUEVO)
----------

HUMAN y SKILLS son carpetas canónicas del ecosistema cuya ubicación física
(ruta) NO es definida por RADAR. La ruta de ambas es resuelta vía la skill de
arquitectura de archivos/carpetas del ecosistema (ver DEPENDENCIAS).

RADAR solo:

- Consume la ruta resuelta de HUMAN y SKILLS.
- Compila su contenido en outputs dedicados (FULL.HUMAN, FULL.SKILLS).
- Describe cambios detectados (ver 05.20), sin evaluarlos.

HUMAN es contenido canónico de baja frecuencia de cambio; "de esa carpeta se
desprende todo" y su edición debe evitarse salvo necesidad real. RADAR no
impone ni bloquea esa regla (no decide), solo la hace visible (describe).

02.40_MODO_LOCAL_FS_VS_MODO_AI_UPLOAD
++++++++++

MODO_LOCAL_FS (máquina local / FS completo):

No hay límite de tamaño por archivo fuente para CORE (según versión base).

Se genera output ACTIVE completo.

Si ACTIVE > 8 MB:

se mantiene el ACTIVE intacto,

se generan copias segmentadas <= 8 MB para IA/humano.

MODO_AI_UPLOAD (subida a IA/chat):

Se respeta límite de tamaño por tanda (ej. 8–9MB).

Se suben segmentos (chunks) al chat para consumo por IA.

El activo completo puede no subirse (pero existe localmente).

++++++++++
02.50_POLITICA_RECOMENDADA_DE_USO_(ANTI-COST_INCIDENT)
++++++++++

Regla operativa recomendada:

- Default diario: RADAR_LITE o RADAR_INDEX.
- CORE: solo cuando vas a analizar/editar un módulo específico.
- FULL / FULL.HUMAN / FULL.SKILLS: ocasional (auditoría, "foto completa", o
  análisis canónico puntual), no por costumbre.

Si usas IA cloud:
- Evitar subir FULL/FULL.HUMAN/FULL.SKILLS completos al chat salvo necesidad real.
- Preferir subir segmentos CORE del módulo objetivo.

++++++++++
02.55_ALCANCE_DE_LA_POLITICA_COST_AWARE_(NUEVO)
++++++++++

06.15_REGLA_DE_HASH_POR_DEFECTO_(NUEVO)
----------

Para evitar ambigüedad y mantener determinismo entre proyectos:

- SHA256 es OBLIGATORIO para todo archivo listado en INDEX cuyo tamaño sea

- Sobre ese umbral, el hash es OPCIONAL por costo de cómputo, pero el campo
  NUNCA queda vacío sin explicación: debe registrarse como
  "HASH_OMITIDO_POR_TAMANO".
- El umbral es configurable por proyecto, pero debe quedar documentado en los
  metadatos de la ejecución (mismo patrón que la excepción de 04.20).

- TARGET_RUTA: ruta a la que apunta el symlink.

nombres de hojas

09.10_REGLA_DE_8_MB
++++++++++

Si cualquier output ACTIVE supera 8 MB (incluye FULL.HUMAN y FULL.SKILLS):

El archivo ACTIVE se mantiene intacto.

Se crean copias segmentadas <= 8 MB.

++++++++++
09.20_NAMING_DE_SEGMENTOS
++++++++++

Determinístico.

Sin la palabra "part".

Ejemplo:
RADAR_FULL.ACTIVE.txt.seg.001
RADAR_FULL.ACTIVE.txt.seg.002
...

----------
09.25_NAMING_DE_HISTORICOS_(NUEVO)
----------

Determinístico, basado en timestamp ISO sin separadores ambiguos (formato
AAAAMMDD-HHMMSS).

El ACTIVE de cada output siempre se sobrescribe en la ejecución más reciente.
El HIST nunca se sobrescribe: al generarse un nuevo ACTIVE, el ACTIVE anterior
se mueve a histórico con el siguiente naming:

RADAR_<TIPO>.HIST.<timestamp>.txt

Ejemplo:
RADAR_FULL.HIST.20260226-143000.txt
RADAR_FULL.HUMAN.HIST.20260226-143000.txt
RADAR_FULL.SKILLS.HIST.20260226-143000.txt

Los 6 outputs de una misma corrida comparten el mismo timestamp, permitiendo
agruparlos por prefijo como pertenecientes a una única ejecución.

++++++++++
09.30_SEGMENTACION_HIBRIDA
++++++++++

Texto (outputs y/o contenido textual):

Preferir corte por límites de línea (mejor lectura humana).

Si no es posible (líneas extremadamente largas), fallback a corte por bytes.

Binario (si se segmenta por alguna razón excepcional):

Corte por bytes (reconstrucción byte-exact).

Notas:

El objetivo de la segmentación es consumo IA/humano, no optimización.

El activo completo es la fuente de verdad local.

01.00_PROPOSITO_Y_PROBLEMA

Problema real:

Sin reglas explícitas:
- múltiples fuentes de verdad
- divergencia entre IA y humano
- pérdida de continuidad
- decisiones inconsistentes

Objetivo:

Definir un modelo único de gobernanza donde:
- cada artefacto tiene un rol claro
- existe una jerarquía explícita
- las actualizaciones son determinísticas
- la trazabilidad es audit-able

- Consumidor principal: humano

---

- Frecuencia: baja
- Consumidor: humano + IA

02.40 RADAR

- Frecuencia: automática
- Consumidor: IA

==========

Regla dura:

HUMAN > SKILLS > BATON > RADAR

- HUMAN define intención y contexto
- SKILLS definen reglas obligatorias
- BATON refleja estado actual
- RADAR refleja evidencia física

Regla crítica:

Si hay conflicto:

04.00_RESPONSABILIDADES_POR_ARTEFACTO
==========

HUMAN:
- Define el “por qué”
- Explica decisiones
- No ejecuta

BATON:
- Define el “estado actual”
- Indica siguiente acción
- No explica en profundidad

SKILLS:
- Definen el “cómo se hace”
- Son obligatorios
- No dependen del estado del proyecto

RADAR:
- Muestra “qué existe”
- No interpreta
- No decide

11.00_ARTIFACT_CLASS_TAXONOMY
Every repository artifact belongs to exactly one class:
- CANONICAL_SOURCE: authoritative, human/AI-edited content (SkillsLake, GRCLake,
  registries, tools source).
- GENERATED_OUTPUT: produced by BUILD or other generators (90.USECASE bundles,
  manifests, copied menus). Never manually patched.
- EVIDENCE: run logs, reports, upload packages, RADAR outputs. Historical record,
  not a source of rules.
- LOCAL_CONFIG: operator/workstation-local tool configuration. Never canon.
An artifact whose class is ambiguous must be classified before it is mutated
(see GRC.UNKNOWN_WORKTREE_STATE_HARD_STOP).

11.10_APPEND_ONLY_HISTORY_VS_ACTIVE_TRUTH
Append-only history registers (backlogs, accumulated registers, changelogs)
preserve the record; they are NOT the active source of truth. Stale OPEN/DONE
values in historical entries do not override the current active registers.
The active state lives in the designated active register for each concern
(e.g. SyS\PROJECT.BACKLOG.ACTIVE.txt for product backlog).

11.20_ONE_CANONICAL_AUTHORITY
For each active state (versions, menu, backlog, roadmap, debt), exactly ONE
artifact is the canonical authority. When two artifacts disagree, the declared
authority wins and the other must be corrected or explicitly superseded, never
silently ignored.

11.30_PROMOTION_DISPOSITION_FIELDS
When a candidate is dispositioned, the record must state:
- DISPOSITION: MERGED | PROMOTED | REJECTED | DEFERRED | PROJECT_LOCAL
- TARGET: the artifact(s) receiving merged/promoted content
- SOURCE_MB: the minibattle performing the disposition

11.40_GENERATED_USECASE_OUTPUTS
Never manually patch generated 90.USECASE outputs. Patch canonical source and
regenerate via BUILD. A manual edit to a generated output is drift, not a fix.

11.50_MACHINE_MANIFESTS_AND_DISTRIBUTION
Machine-facing manifests (JSON registries, schemas) may live outside the
single-file upload distribution for humans/IA. Consolidated distribution
completeness is measured against declared content, not against every machine
manifest in the repository.

Objetivos:

Secuencia base:

INICIO_SESION
→ EJECUCION

Regla corregida v1.1:

Durante INICIO_SESION y EJECUCION no es obligatorio actualizar BATON, backlogs,

Estas actualizaciones se realizan:

- al CIERRE_SESION formal;
- o cuando el humano lo solicita de forma explícita;

Ejemplos que NO activan cierre formal:

8. Actualización del backlog operativo del proyecto activo, si existe.

06.80_PATH_MINIBATTLES_BATTLES_ENTREGABLE

06.90_EVIDENCIA_Y_NO_INVENCION

No se debe inventar estado.

- hubo cambios de filesystem;
- se crearon archivos;

- la sesión fue puramente conceptual;

Responder estado, pero no ejecutar protocolo completo.

Ejecutar contrato de cierre de este Skill.

13.00_ACUMULACION_Y_PERFECCIONAMIENTO_DE_ARTEFACTOS
==========

----------
13.10_REGLA_BASE
----------

Durante el cierre formal de sesión, cada artefacto debe cumplir su función correcta.

No se debe copiar la misma información en todas las capas.

Regla de capa:

- Backlog acumula.
- Deuda técnica acumula.
- HUMAN se perfecciona.
- BATON se refresca.
- RADAR se regenera.
- Git registra.

----------
13.20_BACKLOG
----------

El backlog operativo del proyecto acumula pendientes no resueltos, mejoras, decisiones abiertas y próximos pasos.

En cada cierre formal:

- se agregan nuevos pendientes;
- se actualizan pendientes existentes;
- se cierran ítems resueltos;
- se fusionan duplicados;
- se reclasifican ítems cuando cambia su naturaleza.

Un pendiente no resuelto permanece abierto.

No debe duplicarse como nuevo ítem si ya existe.

----------
13.30_DEUDA_TECNICA
----------

La deuda técnica acumula problemas técnicos, estructurales u operativos no resueltos.

Debe distinguirse de:

- backlog funcional;
- brecha de información;
- riesgo abierto;
- decisión pendiente.

Estados recomendados:

- NUEVA
- EXISTENTE_SIN_CAMBIO
- EXISTENTE_ACTUALIZADA
- MITIGADA
- RESUELTA
- ACEPTADA_CONSCIENTEMENTE
- DESCARTADA

La deuda técnica debe mantener, cuando exista evidencia suficiente:

- descripción;
- causa;
- impacto;
- riesgo;
- evidencia;
- próximo paso;
- prioridad;
- relación con minibattle o battle si aplica.

----------
13.40_HUMAN
----------

HUMAN no acumula tareas ni pendientes operativos.

HUMAN se perfecciona solo cuando existe:

- cambio doctrinal;
- aclaración de intención humana;
- cambio de visión;
- cambio de principio rector;
- cambio de precedencia;
- cambio de regla raíz;
- mejora conceptual canónica.

Ejemplo correcto:
Actualizar HUMAN para declarar una nueva regla superior de arquitectura o gobernanza.

Ejemplo incorrecto:
Agregar a HUMAN una tarea pendiente de implementación.

Las tareas pendientes van en backlog, no en HUMAN.

----------
13.50_BATON
----------

BATON no acumula historia completa.

BATON es snapshot operativo vigente.

Debe reflejar:

- estado actual;
- objetivo activo;
- próximos pasos;
- riesgos o brechas que afectan continuidad;
- archivos/capas relevantes para continuar;
- decisión operativa vigente.

BATON debe refrescarse al cierre formal cuando exista información suficiente.

No debe convertirse en manual, backlog ni changelog completo.

----------
13.60_RADAR
----------

RADAR no se edita manualmente.

RADAR se regenera como evidencia del filesystem o estructura equivalente del proyecto.

RADAR no decide lógica ni doctrina.

RADAR ayuda a validar:

- archivos existentes;
- rutas;
- cambios de filesystem;
- outputs;
- estado documental observable.

----------
13.70_GIT
----------

Git registra trazabilidad histórica mediante commits, ramas, tags y diferencias.

Este Skill no define comandos Git.

La operación Git debe derivarse al Skill de Git aplicable.

----------
13.80_REGLA_ANTI_DUPLICACION
----------

No se debe duplicar la misma información en múltiples artefactos.

Cada contenido debe vivir en su capa correcta:

- doctrina en HUMAN;
- estado operativo vigente en BATON;
- pendientes en backlog;
- problemas estructurales en deuda técnica;
- evidencia filesystem en RADAR;
- trazabilidad histórica en Git.

Si una misma idea aparece en varias capas, debe tener propósito distinto en cada una.

----------
13.90_CRITERIO_DE_CIERRE
----------

Al cierre formal, la IA debe revisar si cada dato pertenece a:

- HUMAN;
- BATON;
- backlog;
- deuda técnica;
- RADAR;
- Git;
- otro artefacto del proyecto activo.

Si no existe evidencia suficiente para clasificar un dato, debe declararse como brecha y no inventarse.

MB-GRC-034C_MINIBATTLE_SAFE_LAUNCHER_GATE
==========

DATE..............: 2026-06-21
STATUS............: ACTIVE
LAYER.............: PROJECT_LIFECYCLE_POLICY
PURPOSE...........:
Prevent minibattle execution from damaging terminal state, committing unintended generated outputs,
or bypassing validation/stage discipline when long scripts or launchers are required.

SCOPE.............:
Applies to any minibattle, one-shot, repository patch, session close, session continue, RADAR,
build, validation, or governance patch that requires a long PowerShell script.

SAFE_LAUNCHER_GATE:
Before running a long PowerShell operation, the IA must use the safe launcher pattern:

1. TEMP_SCRIPT_FILE:
   Write long logic to SyS/Temp/<MB_ID>.<timestamp>.ps1.

2. SHORT_CONSOLE_LAUNCHER:
   The interactive console only creates the .ps1 file, runs pwsh -File, captures LASTEXITCODE,
   prints SCRIPT_EXIT and LAUNCHER_STATUS, and returns to prompt.

3. NO_INTERACTIVE_TRY_CATCH_FINALLY:
   Do not paste long try/catch/finally blocks directly into the interactive terminal.

4. NO_LAUNCHER_EXIT:
   The launcher must not call exit. It must not close VS Code terminal or the user shell.

5. NO_NESTED_HERE_STRING:
   Do not nest PowerShell here-strings inside launcher here-strings. Use arrays of lines or a
   different construction method.

6. NO_PAGER_CAPTURE:
   Set GIT_PAGER=cat and PAGER=cat. Use git --no-pager for log/diff/show/status diagnostics.

7. BUILD_SCOPE_GATE:
   Do not run BUILD.ps1 unless generated outputs are explicitly in scope. If BUILD dirties
   generated outputs unexpectedly, STOP before commit and decide restore/isolate/commit explicitly.

8. EXPLICIT_STAGE_ONLY:
   Stage only the expected files with explicit git add -- <path>. Do not use git add -A or git add .
   for governance/policy patches.

9. DIRTY_SET_GATE:
   Before commit, compare git status --short against an allowed dirty-file whitelist. If unexpected
   files appear, STOP and report.

10. STAGED_DIFF_GATE:
   Print git --no-pager diff --cached --name-status. If no staged changes exist, STOP before commit.

11. VALIDATION_GATE:
   Run Validate-System.ps1 before commit. If available and relevant, run post-build validation as well.

12. FINAL_CLEAN_GATE:
   After commit/push, verify branch, HEAD, remote head, unpushed/unpulled and clean working tree.

REQUIRED_OUTPUT:
Every lifecycle script must print START/END, LOCAL_TIME, ROOT, PURPOSE, COPY_FROM_HERE, validation
exit code, commit/push exit codes if applicable, FINAL_STATUS, LOG_PATH and NEXT_ACTION.

FAILURE_HANDLING:
- If terminal closes, run recovery diagnostic before continuing.
- If generated outputs become dirty unexpectedly, restore or isolate before further changes.
- If a commit fails because staged set is empty, inspect whether the intended files were actually changed.
- If the shell enters pager END state, rerun with --no-pager and pager environment disabled.

DONE_WHEN.........:
A minibattle can be executed without closing the user's terminal, without accidental generated-output
commits, and with deterministic validation/stage/commit/push/final-clean evidence.

GRC.DRAGONFLYFOCUS
==========

ID_UNICO..........: GRC.DRAGONFLYFOCUS.0001
NOMBRE............: DragonflyFocus

STATUS............: DRAFT_READY_FOR_TEST

APPLIES_TO........: 01.NEW_PROJECT | 03.SESSION_CONTINUE | 04.REPOSITORY_STRUCTURE_REPAIR

==========
00.00 PURPOSE
==========

DragonflyFocus is a mandatory focus-control GRC for SkillsMachine operations.

Its purpose is to prevent conversational drift, uncontrolled branching, overproduction,
premature tooling, and assistant-led deviation from the HUMAN-defined objective.

DragonflyFocus exists because the user may produce many valuable ideas during project work,
but not every idea is allowed to become the active workstream.

The assistant must capture side ideas, classify them, and return to the active objective.

==========
01.00 CORE RULE
==========

HUMAN defines the objective.

The assistant must not replace the active objective because of conversational drift,
interesting side ideas, technical curiosity, tooling opportunities, or assistant preference.

If the user introduces a new idea, the assistant must classify it before acting.

No change of mission is allowed without explicit human confirmation.

==========
02.00 MANDATORY FOCUS_GATE
==========

Every operational response under the covered usecases must include or internally apply:

FOCUS_GATE:
- OBJECTIVE_ACTIVE:
- CURRENT_STEP:
- USER_NEW_IDEA:
- CLASSIFICATION:
- DECISION:
- NEXT_ACTION:

CLASSIFICATION values:

- CORE_OBJECTIVE
  The new idea directly advances the active objective.

- BLOCKER
  The new idea reveals something that blocks the active objective.

- TECHNICAL_DEBT
  The new idea is valid but should be registered and not executed now.

- BACKLOG
  The new idea is useful but not needed for the active objective.

- CHANGE_OF_MISSION
  The new idea would replace or materially alter the active objective.

- DISCARD
  The new idea is noise, duplicate, obsolete, or not worth carrying forward.

==========
03.00 DECISION RULES
==========

03.10 CORE_OBJECTIVE

If classification is CORE_OBJECTIVE:
- incorporate it into the current step;
- explain why it advances the objective;
- keep the next action singular.

03.20 BLOCKER

If classification is BLOCKER:
- stop execution;
- define the blocker;
- define the minimum unblock action;
- do not continue with unrelated tasks.

03.30 TECHNICAL_DEBT

If classification is TECHNICAL_DEBT:
- register it as technical debt;
- do not execute it immediately;
- return to OBJECTIVE_ACTIVE.

03.40 BACKLOG

If classification is BACKLOG:
- capture it briefly;
- do not expand it;
- return to OBJECTIVE_ACTIVE.

03.50 CHANGE_OF_MISSION

If classification is CHANGE_OF_MISSION:
- stop;
- explicitly ask the human to confirm mission replacement;
- do not proceed until confirmation is given.

Required wording:

CAMBIO_DE_MISION detectado.
Objetivo activo actual:
[OBJECTIVE_ACTIVE]

Nuevo objetivo propuesto:
[NEW_OBJECTIVE]

Impacto:
[IMPACT]

Confirmas reemplazar el objetivo activo? YES/NO

03.60 DISCARD

If classification is DISCARD:
- state briefly why it is discarded;
- do not preserve it unless the human insists.

==========
04.00 ASSISTANT BEHAVIOR CONSTRAINTS
==========

The assistant must not:

- follow every user branch as if it were the active objective;
- produce large scripts unless they directly advance the active step;
- transform backlog into execution without approval;
- create PR/merge/launcher/tooling work if the active objective is user-flow definition;
- optimize governance instead of finishing the deliverable;
- confuse technical progress with product progress;
- bury the user in options when one next action is required.

The assistant must:

- identify the active objective;
- protect the objective from drift;
- preserve useful side ideas without executing them;
- force mission-change confirmation;
- recommend one next action;
- prefer deliverable completion over system elaboration.

==========
05.00 OUTPUT CONTRACT
==========

When DragonflyFocus is active, every operational answer must end with:

DRAGONFLYFOCUS_DECISION:
- OBJECTIVE_ACTIVE:
- CURRENT_STEP:
- NEW_IDEAS_CAPTURED:
- DRIFT_RISK:
- DECISION:
- NEXT_ACTION:

NEXT_ACTION must be singular.

If more than one next action is listed, the response fails DragonflyFocus.

==========
06.00 USECASE INJECTION REQUIREMENT
==========

DragonflyFocus must be included in the operational context for:

- 90.USECASE\01.NEW_PROJECT
- 90.USECASE\03.SESSION_CONTINUE
- 90.USECASE\04.REPOSITORY_STRUCTURE_REPAIR

It must be referenced by:
- README.UPLOAD_THIS_USECASE.txt
- PROMPT.*.txt
- SKILL_SET.MANIFEST.txt or equivalent usecase manifest
- generated bundle or source GRC registry, depending on build architecture

Generated outputs must not be manually patched if they are build-derived.
The source registry/build source must be updated and the package regenerated.

==========
07.00 FAILURE CONDITIONS
==========

DragonflyFocus fails if:

- the assistant follows a side idea without classification;
- the assistant changes mission without explicit human confirmation;
- the assistant creates a large script unrelated to the current objective;
- the assistant expands technical debt into execution;
- the response has no singular next action;
- the user asks for focus and the assistant responds with broad exploration;
- the session produces many artifacts but no progress toward the active deliverable.

==========
08.00 SUCCESS CONDITIONS
==========

DragonflyFocus succeeds when:

- the active objective remains visible;
- side ideas are captured without hijacking the session;
- the next action is singular;
- the assistant blocks drift firmly;
- projects converge toward deliverables;
- SkillsMachine becomes useful for finishing projects, not only structuring them.

SCOPE.............: Cross-project control for staging long executable scripts before terminal execution
APPLIES_TO........: SkillsMachine and any project where long scripts are safer from file than from terminal paste

==========
00.00 PURPOSE
==========

ScriptExecutionStaging governs the practice of saving long scripts into a project Temp or staging folder before execution instead of pasting the full script directly into an interactive terminal.

The goal is to reduce copy/paste errors, quoting drift, wrapping damage, truncation, shell interpolation mistakes, and weak evidence capture.

==========
01.00 CORE RULE
==========

When a script is long enough that direct terminal paste increases operational risk, the script must be saved to a file first and then executed from that file.

The file must use the appropriate extension for the shell or runtime in use, such as:

- .ps1 for PowerShell;
- .sh for shell scripts;
- other project-appropriate executable script formats when justified.

==========
02.00 STAGING PATH CONTRACT
==========

For SkillsMachine, the default staging path is:

C:\01. GitHub\Skills\SyS\Temp

For other projects, the script must use that project's appropriate Temp or staging folder instead of assuming the SkillsMachine path.

The staging folder is operational only. It is not canon by default.

==========
03.00 SCRIPT OUTPUT CONTRACT
==========

The staged script must print parseable operational output.

Preferred formats are:

- KEY=VALUE
- TOVS
- AI_TAIL when the execution protocol requires a final compact status block

The script must avoid presentation-only output when parseable evidence is expected.

==========
04.00 EXECUTION CONSTRAINTS
==========

A compliant staged execution script must:

- be written to the chosen Temp or staging folder before execution;
- be executable from a short launcher command;
- avoid git commit unless the human explicitly instructs it;
- avoid git push unless the human explicitly instructs it;
- avoid treating temporary script files as canonical source;
- avoid committing temporary script files unless the human explicitly instructs it.

==========
05.00 ASSISTANT BEHAVIOR
==========

The assistant must prefer staged execution when a long script would otherwise be pasted directly into terminal.

The assistant must identify the Temp or staging path it is using.

The assistant must not silently convert temporary staged scripts into canon.

The assistant must preserve the boundary between:

- canonical source files;
- generated outputs;
- temporary execution helpers.

==========
06.00 FAILURE CONDITIONS
==========

This GRC fails if:

- a long script is pasted directly into terminal when a staged file would be safer;
- the script path is ambiguous;
- the script emits non-parseable output where parseable evidence is required;
- a temporary staged script is committed without explicit human instruction;
- a temporary staged script is mistaken for canonical source;
- the staged script performs commit or push without explicit human instruction.

==========
07.00 SUCCESS CONDITIONS
==========

This GRC succeeds when:

- long scripts are authored in a Temp or staging folder before execution;
- the executed file path is explicit;
- the script output is parseable and reviewable;
- operational errors from wrapping, quoting, truncation, or shell interpolation are reduced;
- temporary execution helpers remain clearly non-canonical unless a human explicitly promotes them.

==========
08.00 RELATIONSHIP TO OTHER CONTROLS
==========

This GRC governs execution staging for long scripts.

It does not govern upload-ready context packaging, compiled TXT context bundles, JSON manifests, or IA upload staging. Those concerns belong to:

GRCLake\01.CONTROLS\GRC.USECASE_TEMP_UPLOAD_STAGING.txt

==========
01.00 CORE PRINCIPLE
==========

AI code agents may develop, validate, and report long-running tasks, but the human owns commit decisions unless explicitly delegated.

Operational form:

IA develops -> IA validates -> IA reports -> IA stops at commit-ready gate -> human reviews -> human commits

The default operating model is not:

IA develops -> IA commits automatically

==========
02.00 SEQUENTIAL TASK EXECUTION
==========

Agents must execute tasks sequentially.

A compliant agent must:

- start one task at a time;
- restate task ID and objective before work;
- identify expected files to inspect or modify;
- avoid parallel task execution;
- avoid mixing changes from different tasks;
- avoid opportunistic edits outside task scope;
- finish, validate, and classify the current task before starting the next one.

Valid per-task result classifications:

- PASS
- PASS_WITH_WARNINGS
- BLOCKED
- FAILED
- SKIPPED_DEPENDENCY_BLOCKED

03.00 HUMAN COMMIT OWNERSHIP
==========

By default, Codex and Claude Code must not commit.

Agents may prepare a commit-ready state, but the human performs the commit unless the human explicitly delegates commit authority.

At a commit-ready gate, the agent must report:

- exact files changed;
- exact files recommended for staging;
- exact files not to stage;
- validation result;
- suggested commit message;
- known warnings;
- unresolved blockers;
- whether push is recommended or not.

Agents must not use:

- git add .
- git add -A
- git commit --no-verify

unless the human explicitly instructs otherwise.

==========
04.00 UNKNOWN WORKTREE STATE
==========

If an unexpected file, change, dependency, local tool config, generated artifact, or worktree state appears, the agent must stop before continuing.

Unknown worktree state must be classified before the agent proceeds.

The agent must not:

- stage it;
- delete it;
- revert it;
- ignore it;
- continue to the next task;

until the state is classified.

Valid classifications include:

- EXPECTED_FOR_CURRENT_TASK
- INTENTIONAL_LOCAL_ONLY
- GENERATED_REGENERABLE
- CANONICAL_SOURCE
- IGNORED_SAFE_TO_LEAVE
- TRACKED_CHANGE_INTENDED
- UNTRACKED_SHOULD_IGNORE
- UNTRACKED_SHOULD_TRACK
- SUSPICIOUS
- BLOCKED_NEEDS_HUMAN_DECISION

C:\01. GitHub\Skills\SyS\Temp

- START
- STEP
- HEARTBEAT when useful
- FINAL_STATUS
- REPORT

- overall status;
- task-by-task status;
- files changed;
- validation results;
- blockers;
- warnings;
- questions for the human;
- commit-ready recommendation;
- exact do-not-commit files;
- exactly one recommended next action.

- ALL_PASS
- PASS_WITH_WARNINGS

- BLOCKED
- FAILED

unknown state detected -> classify -> decide whether safe to continue

- stage the file or state;
- delete it;
- revert it;
- ignore it;
- continue to the next task.

If classification remains ambiguous, human decision is required before continuation.

- UNKNOWN_FILE_PATH

- confirm it is not tracked;

- confirm Git status is clean when ignore behavior is active;

07.00 REPO-LOCAL EXCLUDE VS TRACKED GITIGNORE
==========

Use .git/info/exclude when:

- the rule is local to one operator or workstation;
- the file is local-only tool configuration;
- the human does not want the ignore rule committed;
- the file should not affect shared repo policy.

Use tracked .gitignore only when:

- the ignore rule is intended as shared repository policy;
- the human explicitly wants the rule committed for all collaborators;
- the file class is broadly non-canonical across the project, not only local to one machine.

10.00 SUCCESS CONDITIONS

Authorized dirty state must be expressed as an exact-path whitelist
(repo-relative paths), not directory globs or prefixes, except where a whole
new directory is the declared artifact. Any dirty path not on the whitelist
is unknown state and triggers the hard stop.

13.20 AUTHORIZED DIRTY BASELINE PRESERVATION
When a task starts with a pre-authorized dirty baseline (e.g. carrying
uncommitted work from a previous authorized MB), the agent should record the
baseline (paths and, where feasible, content hashes) so post-task comparison
can distinguish new mutations from the preserved baseline.

13.30 AMBIGUOUS GIT TOP-LEVEL IS CONTEXT FAILURE
If git rev-parse --show-toplevel fails, disagrees with the expected project
root, or resolves to a different repository (nested repo, submodule, wrong
folder), that is a PROJECT CONTEXT failure — hard stop under
GRC.PROJECT_CONTEXT_IDENTITY — not merely a worktree-state question.

13.40 IGNORED LOCAL TOOL CONFIG
Git-ignored local tool configuration (e.g. .claude/settings.local.json) is
LOCAL_CONFIG, not canonical mutation. Its presence does not dirty the
worktree for governance purposes, but it must never be staged, committed, or
treated as project source.

# SKILL.HUMAN_CONTROLLED_SCRIPT_EXECUTION

MARKER: MB-SM-052A_CROSS_RUNTIME_EXECUTION_CONTRACT
VERSION: v1.1
STATUS: ACTIVE
LAYER: SKILL
OWNER_DOMAIN: SkillsMachine
PURPOSE: Define a shell/runtime-agnostic execution method for AI-delivered executable files.

==========
00.00 PRINCIPLE
==========

This methodology is not a PowerShell-only method.

It is a human-controlled local execution contract:

AI prepares an executable artifact.
Human saves it in the project TEMP path.
Human executes it locally from VS Code or terminal.
The executable emits AI_TAIL_START / AI_TAIL_END.
Human returns the AI_TAIL and any relevant TEMP outputs.
AI interprets evidence and provides the next single action.

PowerShell, Python, Bash, Node, SQL wrappers, Docker wrappers, Excel helpers, and Power Query generators are runtime adapters.

==========
01.00 DEFAULT WORKFLOW
==========

A. AI provides the executable file content or downloadable executable artifact:
   - .ps1
   - .py
   - .sh
   - .js
   - .sql runner wrapper
   - other executable/script file

B. Human saves it in the project TEMP path.

C. Human executes the exact command provided by the AI.
   The command must work from any current directory.

D. Human returns:
   - AI_TAIL_START through AI_TAIL_END; and/or
   - specific files created in TEMP that the AI explicitly requested.

==========
02.00 TEMP PATH RULE
==========

The AI must not invent a TEMP path.

The TEMP path must come from project canon:
- BATON
- WHOAMI
- HUMAN
- README
- active usecase instructions
- explicit user instruction

If TEMP path is missing and execution requires it, ask or declare a safe project-local TEMP path before script delivery.

Examples:
- SkillsMachine: C:\01. GitHub\Skills\SyS\Temp
- CloseReport: C:\01. GitHub\CloseReport\99.TEMP

==========
03.00 EXECUTION COMMAND RULE
==========

The AI must provide a command executable from any location.

PowerShell example:
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File "C:\path\to\temp\script.ps1"

Python example:
python "C:\path\to\temp\script.py"

Bash example:
bash "/mnt/c/path/to/temp/script.sh"

The script itself must resolve PROJECT_ROOT and TEMP_PATH explicitly.

==========
04.00 AI_TAIL RULE
==========

AI_TAIL is mandatory for every executable artifact unless the runtime cannot support stdout or file output.

Minimum AI_TAIL fields:
- AI_TAIL_SCHEMA=v1
- MB_ID or TASK_ID
- RUNTIME
- ROOT
- TEMP_PATH
- FINAL_STATUS
- BLOCKER
- FILES_CREATED
- FILES_MODIFIED
- VALIDATION_STATUS
- COMMIT_PUSH_PERFORMED=NO unless explicitly authorized otherwise
- NEXT_ACTION

The script must not report success unless the relevant operation actually passed.

==========
05.00 IF TOOL DOES NOT SUPPORT THE METHOD
==========

If a tool/runtime cannot produce AI_TAIL, exit code, stdout, or auditable file output, the AI must not pretend compliance.

It must declare:
- CAN_USE_METHOD_FULLY: NO
- CAN_USE_METHOD_PARTIALLY: YES/NO
- MISSING_CAPABILITIES
- SAFE_ADAPTER
- RECOMMENDATION

Examples:
Power Query M cannot emit AI_TAIL directly.
Recommendation: generate M code with Python or PowerShell and validate outputs externally.

Excel manual operations cannot guarantee exit code.
Recommendation: use a PowerShell/Python validator around the workbook.

SQL alone may not support the contract.
Recommendation: execute SQL through Python/PowerShell wrapper that emits AI_TAIL.

==========
06.00 DELIVERY MODE
==========

Default delivery mode:
- AI provides code or a downloadable file.
- Human saves to TEMP.
- Human executes locally.
- Human returns AI_TAIL.

ZIPs or multi-file bundles are allowed only when they reduce token cost or complexity and remain explicit, reviewable, and project-local.

The AI must not rely on invisible tool-side execution for final delivery unless explicitly requested.

==========
07.00 GIT RULE
==========

Scripts may inspect Git status and produce commit-ready reports.

Scripts must not commit or push unless the user explicitly delegates that action.

Prohibited by default:
- git add .
- git add -A
- automatic commit
- automatic push
- hiding dirty state
- continuing after unknown dirty worktree

==========
08.00 ADAPTER MINIMUMS
==========

PowerShell:
- Prefer pwsh when available.
- Use PS 5.1-compatible constructs when Windows PowerShell is expected.
- Avoid scalar .Count hazards by wrapping collections with @(...).
- Avoid Write-Host "=" * 60 ambiguity.
- Use GIT_PAGER=cat.
- Emit AI_TAIL in controlled final path.

Python:
- Use pathlib.
- Use try/except/finally or equivalent tail guarantee.
- Print AI_TAIL before sys.exit.
- Explicit encoding for CSV/text.
- Do not write outside project root or TEMP unless declared.

Bash:
- Use set -Eeuo pipefail.
- Use trap for tail.
- Use printf.
- Preserve exit code.
- Use git --no-pager.

Node:
- Capture uncaughtException and unhandledRejection.
- Emit tail before process.exit.

Docker:
- Use wrapper script to build/run/capture logs and emit AI_TAIL.

Power Query / Excel / VBA:
- Use generator/installer/validator wrapper when direct AI_TAIL is unavailable.

==========
09.00 COMPLIANCE GATE
==========

Before delivering executable code, the AI must be able to answer:

EXECUTION_CONTRACT_GATE:
- PROJECT:
- PROJECT_ROOT:
- TEMP_PATH:
- SCRIPT_NAME:
- SCRIPT_RUNTIME:
- TARGET_SHELL:
- MIN_VERSION:
- CAN_RUN_FROM_ANY_LOCATION:
- AI_TAIL_SUPPORTED:
- EXIT_CODE_SUPPORTED:
- FILE_OUTPUT_SUPPORTED:
- GIT_AWARE:
- AUTO_COMMIT_ALLOWED:
- USER_EXECUTES_LOCALLY:
- LIMITATION:
- RECOMMENDATION:
- DECISION: PROCEED / ADAPT / BLOCK

If the gate cannot be completed, do not deliver executable code.

==========
10.00 FAILURE MODE
==========

If the script fails, the AI must request only:
- AI_TAIL_START through AI_TAIL_END, if present;
- otherwise the minimal terminal segment needed to diagnose;
- specific TEMP outputs if relevant.

Do not ask for broad logs or full repo uploads by default.

objective. Prior authorization for one MB does not carry over to the next.

00.00 CONTROL STATEMENT
==========

Any AI agent delivering an executable artifact must comply with the cross-runtime execution contract.

This applies to:
- PowerShell
- Python
- Bash
- Node
- SQL wrappers
- Docker wrappers
- Excel/VBA helpers
- Power Query generators

==========
01.00 MANDATORY USER FLOW
==========

The canonical flow is:

A. AI gives the executable file or file content.

C. Human runs the exact command from VS Code/terminal from any location.

The response or script is non-compliant if it:

- delivers executable code without AI_TAIL when the runtime supports AI_TAIL;
- omits TEMP path;
- cannot run from any location;
- auto-commits or pushes without explicit authorization;

- hides or ignores dirty worktree state;
- reports PASS while validation failed;
- continues after UNKNOWN_WORKTREE_STATE;
- asks the user to upload broad logs when a narrow AI_TAIL or TEMP output is enough;
- edits generated outputs directly when source/rebuild flow is required;
- treats PowerShell-specific rules as sufficient for other runtimes without an adapter.

==========

If a runtime cannot support the full method, the AI must say so.

Required format:

TOOL_CAPABILITY:
- TOOL:
- CAN_USE_METHOD_FULLY:
- CAN_USE_METHOD_PARTIALLY:
- MISSING:
- SAFE_ADAPTER:
- RECOMMENDATION:

Power Query M:
- CAN_USE_METHOD_FULLY: NO
- MISSING: stdout, exit code, AI_TAIL

Python:
- CAN_USE_METHOD_FULLY: YES
- REQUIREMENTS: pathlib, try/except/finally, print_ai_tail, explicit exit code
- RECOMMENDATION: proceed.

RUNTIME=<runtime>
ROOT=<project root>
TEMP_PATH=<temp path>
FINAL_STATUS=<PASS|FAIL|PASS_WITH_WARNINGS|COMMIT_READY>

FILES_CREATED=<count or list>
FILES_MODIFIED=<count or list>
VALIDATION_STATUS=<PASS|FAIL|NOT_RUN>

NEXT_ACTION=<single next action>

Additional fields are allowed when useful.

==========
06.00 GENERATED OUTPUT RULE
==========

If the target artifact is generated output, the AI must not patch it manually unless explicitly instructed.

Required sequence:
- patch canonical source;
- run generator/build;
- validate;
- report generated outputs in AI_TAIL or summary.

==========
07.00 TOKEN AND DELIVERY ECONOMY
==========

To reduce token use:
- prefer one executable script over large inline patches;
- prefer downloadable/single file when available;
- prefer AI_TAIL over long terminal logs;
- request only relevant TEMP files;

For Claude, Codex, ChatGPT or other agents:

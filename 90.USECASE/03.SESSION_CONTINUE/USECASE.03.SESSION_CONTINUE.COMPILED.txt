00.20_CONTEXTO_DEL_PROBLEMA_Y_OBJETIVOS
==========

00.20.01_PROBLEMAS_REALES_QUE_MOTIVAN_ESTE_SKILL

a) Rutas demasiado largas en Windows (≈260 caracteres) que rompen copias, zips,
sincronización (OneDrive, etc.) y tooling.

b) Nombres extremadamente verbosos y heterogéneos que dificultan la lectura y
el parseo automático.

c) Falta de compatibilidad entre nombres de FS (File System) y claves para BD
(Base de Datos).

d) Refactors costosos porque versión, WBS, título y demás se mezclan en el nombre
del archivo.

e) Inconsistencia entre proyectos y sistemas: cada uno inventa su propio esquema
de nombres, obligando a RADAR y a la IA a “adivinar” patrones.

00.20.02_OBJETIVO_PRINCIPAL

Definir un estándar único y simple para:

a) WBS interno (estructura dentro de los archivos).
b) IDs cortos de archivos y carpetas (FS-friendly).
c) IDs para BD (DB-friendly).

00.20.03_OBJETIVO_SECUNDARIO

Permitir que los nombres “humanos” puedan ser largos y explicativos sin romper:

a) Límites de Windows.
b) Esquemas de BD.
c) Scripts y tooling que dependan de los IDs.

01.00_DEFINICIONES_BASICAS
==========

01.00.01_WBS_INTERNO

Estructura jerárquica dentro de un documento (por ejemplo: 01.00, 01.10, 01.20, etc.).

Función:

Ordenar ideas y secciones de forma estable.

Permitir referencias internas tipo “ver 03.20 de este documento”.

No tiene obligación de coincidir con estructura de carpetas.

01.00.02_ID_FS_(ID_DE_FILE_SYSTEM)

Identificador corto y estable que se usa en nombres de archivos y carpetas.

Reglas mínimas:

ASCII básico, sin espacios, sin tildes, sin caracteres raros.

Amigable para Windows (ruta total razonable).

Se compone normalmente de:

Prefijo de frame o proyecto (FRM).

Tipo lógico (TIPO).

Secuencia numérica (NNNN).

Opcional: sufijo humano corto ASCII.

Ejemplo:

PF_HUM_0005

EVA_SKL_0101

WNG_TL_0200_REGENALL

01.00.03_ID_DB_(ID_DE_BASE_DE_DATOS)

Clave para BD:

Lo más corta posible.

Sin dependencias directas de rutas físicas.

Idealmente unívoca para cada elemento lógico relevante.

Puede reutilizar el patrón ID_FS o derivarlo, pero siempre con mapping claro ID_DB ↔ ID_FS.

01.00.04_FRAME

Conjunto coherente de reglas y artefactos: PFUNDATIONS, EVA.EOL, WINGS, proyectos, etc.

01.00.05_SKILL

Estándar transversal basado en errores reales que define “cómo se trabaja”.
Los frames deben respetar los SKILLS, salvo excepciones justificadas.

01.00.06_CATALOGO_FRM_(NUEVO, RECOMENDADO)

FRM recomendado (ejemplos; cada ecosistema mantiene su catálogo):
- PF   = PFUNDATIONS
- EVA  = EVA.EOL
- WNG  = WINGS
- KLAB = Kumquat Lab
- PROJ = Proyecto puntual
- OPS  = Operaciones / runbooks
- SYS  = Sistema base transversal

Regla:
- Si agregas FRM nuevo, documentarlo en el HUMAN root del ecosistema o en un catálogo central.

02.00_PROBLEMAS_HISTORICOS_QUE_ESTE_SKILL_ATACA
==========

02.00.01_PROBLEMA_1_RUTAS_LARGAS_EN_WINDOWS

Árboles profundos + nombres largos + sincronización = riesgo de superar límite de ruta.

Síntomas:

Errores al copiar/mover/eliminar.

Imposibilidad de zippear.

Fallos de scripts.

02.00.02_PROBLEMA_2_NOMBRES_BONITOS_PERO_INESCALABLES

Espacios, tildes, ñ, caracteres especiales.

Mezcla de WBS, título, versión en el mismo string.

Resultado:

Keys poco confiables en BD.

Dificultad para queries limpias.

Dificultad de parseo automático.

02.00.03_PROBLEMA_3_REFACTORS_CAROS

Cambias versión/título y el nombre de archivo cambia → cascada de roturas.

02.00.04_PROBLEMA_4_INCONSISTENCIA_ENTRE_SISTEMAS

Cada proyecto inventa su lógica.
RADAR y tooling deben “adivinar” patrones.

==========
03.00_PRINCIPIOS_DE_DISENO_PARA_WBS_E_IDS
==========

03.00.01_PRINCIPIO_1_SEPARAR_CAPAS

WBS interno → organización conceptual dentro del archivo.

ID_FS → integración con filesystem.

ID_DB → integración con BD/catálogos.

No mezclar todo en el mismo string.

03.00.02_PRINCIPIO_2_ID_CORTO_SEMANTICA_LARGA

El ID debe ser mecánico, corto y estable.

La semántica va en:

títulos de sección,

cabecera/metadatos,

campos descriptivos de BD.

03.00.03_PRINCIPIO_3_ASCII_ONLY_EN_IDS

En IDs FS y BD:

Letras A–Z (mayúsculas recomendadas).

Dígitos 0–9.

Separadores: _ y .

No se permiten:

tildes, ñ, espacios, símbolos raros.

03.00.04_PRINCIPIO_4_ESTABILIDAD_DE_IDS

Una vez asignado un ID:

No se cambia salvo rediseño estructural mayor.

Versiones van en metadatos, no en el ID.

03.00.05_PRINCIPIO_5_LONGITUD_CONTROLADA

Recomendaciones:

ID_FS ≤ 16 caracteres (sin sufijo).

ID_FS + sufijo ≤ 40 caracteres.

Nombre archivo (ID_FS + sufijo + ext) ≤ 80 caracteres.

Ruta objetivo < 200 caracteres.

==========
04.00_ESTANDAR_DE_WBS_INTERNO_(DENTRO_DE_LOS_ARCHIVOS)
==========

04.00.01_FORMATO_BASICO

Formato sugerido:
NN.MM_TITULO_EN_MAYUSCULAS_SIN_TILDES

Ejemplo:
01.30_RELACION_CON_LOS_SKILLS_Y_ESTANDARES_DEL_SISTEMA

Características:

NN = bloque principal (00, 01, 02, …).

MM = subbloque (00, 10, 20, 30, etc.).

Título en mayúsculas, sin tildes ni caracteres especiales.

Guion bajo _ como separador.

04.00.02_USO_RECOMENDADO

Ordenar contenido y facilitar referencia (“ver 03.20”).

No se usa como nombre de archivo ni como clave de BD.

04.00.03_REGLAS_DE_ESTABILIDAD

Evitar renumerar WBS internos salvo rediseño profundo.

Si agregas un bloque intermedio, usar 01.15, 01.25, etc.

Regla:

Ejemplo (real):
Script con nombre fijo: RADAR.ps1

Condiciones para permitir la excepción:

Documentar en metadatos del archivo:

Motivo: contrato operativo humano / compatibilidad con tooling.

Objetivo:
Evitar drift silencioso.

++++++++++
05.00.09_VALIDACION_OPERATIVA_(NUEVO)
++++++++++

Regla:
Todo tooling/agente que cree nombres debe validar ID_FS.

Regex recomendado (mínimo):
^[A-Z0-9]{2,6}_[A-Z0-9]{2,6}_[0-9]{4}(_[A-Z0-9._]{1,30})?$

Checks:
- ASCII only
- longitud nombre archivo <= 80
- ruta total < 200 recomendado
- evitar duplicados (si existe catálogo)

Si falla:
- no crear archivo
- registrar TROUBLE (severidad BAJA/MEDIA según impacto)

++++++++++
05.00.09_IDS_PARA_ARTEFACTOS_DE_ORQUESTACION_(AI_ORCH)
++++++++++

Para artefactos del orquestador (logs, snapshots, reports), se recomienda:

- Mantener IDs cortos y parseables en nombres.
- Evitar timestamps en ID_FS (preferir timestamp en el sufijo del archivo).

Ejemplos:

AIOR_LOG_0001_RUNS\LOG.RUN.<RUN_ID>.txt
AIOR_CST_0001\COST_YYYYMMDD.ACTIVE.txt
AIOR_SNP_0001\SNAP-YYYYMMDD-HHMM-SEQ\manifest.txt

Objetivo:

Parseo por scripts + compatibilidad DB sin rutas imposibles.

04.40_CONTRATO_DE_EXIT_CODE_Y_ESTADO_FINAL
----------

OBLIGATORIO (CONTRATO):

Un script NO debe declarar éxito (OK/COMPLETADO) si hubo error no controlado.

Si ocurre una excepción no controlada:

Registrar error (Write-Error o equivalente).

Terminar con exit code != 0 (por defecto exit 1).

Imprimir FAIL (no OK) como estado final.

Solo se imprime “OK/COMPLETADO” si:

No hubo excepción,

Se generaron los outputs esperados (DONE binario),

Se dejó evidencia (rutas/archivos generados).

Objetivo:

Evitar falsos positivos (ej.: “OK” con fallos parciales).

Mejorar auditabilidad y confianza operacional.

04.50_CONVENCIONES_POWERSHELL_(VERBS_APROBADOS)_(NUEVO)
----------

Problema real:
PowerShell emite warnings si una función/cmdlet usa verbos no aprobados:
"The cmdlet 'X' uses an unapproved verb."

Regla:
Preferir verbos aprobados por PowerShell (ejemplos comunes):
Get, Set, New, Remove, Add, Clear, Copy, Export, Import, Convert, Update,
Start, Stop, Invoke, Test, Confirm, Enter, Exit, Find, Format, Join,
Measure, Move, Out, Push, Pop, Read, Write.

Recomendación dura (para tu caso):
- Evitar: Validate-*
- Preferir: Test-* (validación)
- Preferir: Confirm-* (confirmación)
- Preferir: Invoke-* (ejecución/acción)

Ejemplo concreto:
- En vez de Validate-CISMetadata
  - Test-CISMetadata
  - Confirm-CISMetadata
  - Invoke-CISMetadataCheck

Nota:
Este skill no reemplaza documentación oficial de PowerShell; es una regla operacional anti-warning.

==========
01.00_PROPOSITO
==========

Este skill reduce fallas al crear archivos Markdown mediante IA y scripts.

Especialmente aplica cuando el contenido incluye:

- fences Markdown;
- bloques Mermaid;
- backticks triples;
- heredocs;
- plantillas con sintaxis sensible;
- caracteres que ChatGPT puede renderizar;
- contenido que Windows puede guardar con CRLF o BOM;
- scripts largos pegados desde editor gráfico.

El objetivo no es “hacer Markdown bonito”. El objetivo es que el archivo final quede correcto, reproducible, auditable y sin romper shell, Git ni renderizado.

==========
02.00_PROBLEMA_REAL
==========

Al crear .md desde ChatGPT + shell aparecen fallas típicas:

1. ChatGPT renderiza Mermaid o fences antes de tiempo.
2. El shell interpreta mal heredocs o bloques largos.
3. El usuario pega script largo y se corta.
4. Windows guarda CRLF/BOM y Bash falla.
5. Markdown final queda sin cierre de fence.
6. Git queda con warnings LF/CRLF.
7. El archivo parece creado, pero contiene marcadores erróneos o truncación.
8. El script entregado contiene backticks triples literales y la interfaz los interpreta antes de que el usuario pueda copiar el script correctamente.

Estos errores producen retrabajo y falsa sensación de avance.

==========
03.00_REGLA_CENTRAL
==========

No escribir sintaxis Markdown sensible directamente si el canal de entrega puede interpretarla, renderizarla, truncarla o romper el shell.

Usar marcadores inertes primero.

Luego convertir los marcadores a sintaxis Markdown real dentro del script, después de que el archivo fue escrito.

==========
04.00_REGLA_DURA_ANTI_FENCE_LITERAL
==========

Regla dura:

En respuestas ChatGPT, scripts pegables, heredocs, strings Python, ejemplos y plantillas intermedias, no incluir triple backtick literal.

Ni dentro de documentación.
Ni dentro de ejemplos.
Ni dentro de heredocs.
Ni dentro de strings de conversión.
Ni como “resultado esperado”.

La única forma permitida de producir un fence real dentro del archivo final es generarlo programáticamente después de la escritura, por ejemplo usando:

fence = chr(96) * 3

Esta regla existe porque la interfaz puede renderizar o encapsular mal cualquier triple backtick literal, incluso si el autor cree que está “dentro del script”.

==========
05.00_PATRON_SEGURO_DE_CREACION_MARKDOWN
==========

Flujo recomendado:

1. Crear archivo destino con contenido Markdown usando placeholders inertes.
2. Evitar backticks triples reales en el script entregado por IA.
3. Usar placeholders para fences, Mermaid y delimitadores peligrosos.
4. Escribir archivo.
5. Ejecutar conversión controlada de placeholders.
6. La conversión debe generar fences usando código de carácter, no texto literal con backticks triples.
7. Normalizar BOM/CRLF si aplica.
8. Verificar que el archivo final contiene el Markdown esperado.
9. Ejecutar validación relevante.
10. Registrar si el patrón evitó un fallo.

Conversión recomendada:

- reemplazar @@FENCE_TEXT@@ por fence + "text";
- reemplazar @@FENCE@@ por fence.

1. Leer archivo.
2. Calcular fence = chr(96) * 3.

4. Escribir archivo.

No escribir el fence real en el script entregado por IA.

00.20_CONTEXTO_Y_OBJETIVOS
==========

BATON existe porque:
- Trabajar con IA (y con humanos) sin snapshot operativo produce pérdidas de continuidad.
- Un “HUMAN” explica el por qué; un “RADAR” describe el FS; un “SKILL” define método.
- Pero al levantar una IA en blanco, el primer problema real es: “¿Qué cargo y en qué orden?”

Objetivo principal:
- Permitir que una IA en blanco tenga continuidad operativa del proyecto en 1–2 minutos de lectura.

Objetivo secundario:
- Evitar drift: BATON no redefine reglas; solo referencia lo que ya es canon (HUMAN/SKILLS/RADAR).

==========
01.00_PROPOSITO_Y_ROL_DE_BATON
==========

----------
01.10_QUE_ES_BATON_STATE
----------

BATON.STATE es un archivo de texto (.txt) por proyecto que:

- Resume el estado operativo relevante para una IA en blanco.
- Indica qué HUMAN y SKILLS son canon en ese proyecto.
- Indica qué RADAR usar como mapa de archivos.
- Expone objetivos activos, contexto mínimo y focos de trabajo.

BATON.STATE es continuidad operativa para IA, nada más.
No crea reglas nuevas de negocio ni de código.

----------
01.20_POR_QUE_ES_POR_PROYECTO
----------

Se define un BATON.STATE por proyecto (no uno global) porque:

- Cada proyecto tiene objetivos, artefactos y riesgos propios.
- Los HUMAN y SKILLS “core” por proyecto no son siempre los mismos.
- La continuidad que te importa cuando levantas una IA es la del proyecto en cuestión.

Ejemplos de “proyecto”:

- PFUNDATIONS (marco personal/profesional).
- EVA.EOL (evaluación y aprendizaje).
- Proyecto inmobiliario específico.
- Sub-sistema técnico con vida propia.

----------
01.30_PRECEDENCIA_DE_FUENTES
----------

Orden de precedencia cuando hay conflicto:

1) HUMAN.README de nivel superior.
2) HUMAN.README específico del proyecto.
3) SKILLS/estándares (incluyendo este BATON).
4) BATON.STATE del proyecto.
5) Código/scripts/configuración.

Si BATON.STATE contradice HUMAN o SKILLS, BATON.STATE está mal
y debe regenerarse.

BATON.STATE nunca es “fuente de verdad funcional”; es derivado consolidado.

----------
01.40_RELACION_CON_ORQUESTACION_IA_(NUEVO)
----------

Si el proyecto usa agentes que crean/editar/eliminan archivos:
- BATON.STATE debe declarar explícitamente el “límite operativo” del agente.
- BATON.STATE NO define políticas nuevas, pero SÍ debe apuntar a los SKILLS que las definen.

En otras palabras:
- BATON no inventa sandbox/costos/routing.
- BATON referencia qué política aplica en este proyecto.

02.10_BLOQUES_OBLIGATORIOS

Un bloque típico de BATON.STATE debería ser capaz de contestar, en pocas líneas:

- “Objetivo principal en este momento…”
- “Prioridades P0/P1/P2 activas…”
- “Riesgos o puntos sensibles que la IA debe tratar con cuidado…”

- HUMAN root del proyecto.

No es necesario copiar el contenido de HUMAN/SKILLS.
Basta con referenciar nombre de archivo y ubicación lógica.

++++++++++

++++++++++

BATON.STATE debe indicar:

- Qué archivo RADAR_INDEX usar como mapa rápido.
- Qué archivo RADAR_CORE y/o RADAR_FULL está vigente.
- Dónde se ubican los históricos de RADAR (para auditoría si aplica).

BATON.STATE no duplica RADAR; solo dice “usa este RADAR como mapa”.

Si el proyecto usa IA ejecutora (que toca archivos):

- Qué carpetas son read-only por política.

De nuevo:
- BATON no inventa esto.

04.00_USO_DE_BATON_POR_IA
==========

++++++++++
04.10_LOAD_ORDER_TIPICO
++++++++++

Cuando levantas una IA en blanco para trabajar en un proyecto:

1) Cargar BATON.STATE del proyecto.
2) Desde BATON.STATE, identificar:
   - HUMAN root + HUMAN hijos relevantes.
   - SKILLS clave.
   - RADAR_INDEX/CORE/FULL vigentes.
   - Objetivos activos.

3) Cargar HUMAN y SKILLS que BATON.STATE referencia.
4) Usar RADAR para navegar archivos del proyecto.

Si BATON.STATE no permite ejecutar este flujo, el archivo debe mejorarse.

++++++++++
04.20_QUE_PUEDE_PEDIR_LA_IA_A_BATON
++++++++++

La IA puede usar BATON.STATE para:

- Entender “qué hay en juego” en el proyecto.
- Saber qué archivos puede tocar y cuáles no (si el proyecto lo declara).
- Determinar qué HUMAN/SKILLS tienen prioridad.
- Ubicar rápidamente artefactos en el FS usando RADAR.

La IA no debe:

- Modificar BATON.STATE por iniciativa propia.
- Alterar HUMAN/SKILLS basándose solo en lo que dice BATON.STATE.

Cualquier cambio en BATON.STATE debe ser validado por humano.

++++++++++
04.30_COMO_USAR_BATON_CON_AGENTES_EJECUTORES_(NUEVO)
++++++++++

Si la IA ejecuta planes (crear/editar/eliminar):

- BATON.STATE debe indicar:
  - si hay política de ejecución (EXEC_POLICY) y sandbox
  - si hay contratos de rollback (git checkpoints)
  - si hay política de costos (budgets / hard-stop)

La IA debe:
- leer ese bloque antes de ejecutar cambios
- en caso de duda: pedir confirmación humana (no actuar a ciegas)

++++++++++
04.30_BATON_Y_AI_ORCH_(ORQUESTACION_Y_EJECUCION)
++++++++++

BATON.STATE debe incluir (cuando el proyecto use AI_ORCH):

- PROJECT_ROOT (ruta lógica del proyecto).
- Referencia a SANDBOX_BOUNDARY activo (nombre/ubicación).
- Referencia a AGENT_EXECUTION_POLICY activo.
- Referencia a COST_CONTROL y ROUTING_POLICY activos.
- Referencia a LOGGING_AUDIT y CHECKPOINT_ROLLBACK si existen.

Objetivo:

Que una IA en blanco sepa:
- qué puede tocar (y qué no),
- cómo se ejecuta con rollback,
- cómo se controla costo.

Regla:

BATON.STATE NO duplica políticas; solo referencia los skills canónicos.

05.10_EVENTOS_QUE_DISPARAN_REGENERACION

- Luego se regenera BATON.STATE para reflejar la nueva realidad.

----------
01.10_PARA_QUIEN
----------

HUMAN.README está escrito para:

- Tu yo del futuro.
- Un humano nuevo que se sube al proyecto.
- Una IA en blanco que debe entender el proyecto a nivel conceptual.

No está pensado como comentario al margen; es el “contrato humano” del sistema.

----------
01.20_QUE_ES_HUMAN_README
----------

HUMAN.README es:

- El documento que explica el “por qué” y el “cómo” a nivel conceptual.
- La fuente de intención, contexto, supuestos y criterios.
- El lugar donde se registran decisiones de diseño relevantes.

HUMAN.README no:

- Expone cada detalle de implementación (eso vive en código / SKILLS específicos).
- Reemplaza manuales de usuario externos, salvo que se decida explícitamente.

01.30_PRINCIPIO_DE_NO_PERDIDA_DE_CONTEXTO_(REFUERZO)
----------

Regla por defecto:
- Evolucionar HUMAN = complementar, ordenar, aclarar y enriquecer.
- No recortar agresivamente.
- No resumir de forma que mate criterio histórico.

Si se elimina algo:
- dejarlo explícito en CHANGELOG
- idealmente moverlo a histórico si podría ser útil

==========
02.00_HUMAN_ROOT_VS_HUMAN_HIJO
==========

++++++++++
02.10_HUMAN_ROOT
++++++++++

HUMAN root:

- Es el HUMAN principal de un sistema/proyecto.
- Define el alcance, objetivos, principios y lenguaje común.
- Es la referencia superior en caso de conflicto de interpretación.

Solo debería haber un HUMAN root por sistema/proyecto.

++++++++++
02.20_HUMAN_HIJO
++++++++++

HUMAN hijo:

- Es un HUMAN derivado, más específico.
- Puede concentrarse en un subdominio, módulo, fase o vista particular.
- No puede contradecir al HUMAN root.

Ejemplos:

- HUMAN.PFUNDATIONS.README (root).
- HUMAN.PFUNDATIONS.CAPAS (hijo focalizado en arquitectura).
- HUMAN.PROYECTO_X.FINANZAS (hijo de un HUMAN root del proyecto X).

++++++++++
02.30_CUANDO_PARTIR_UN_HUMAN
++++++++++

Un HUMAN root se parte en HUMAN hijos cuando:

- Es demasiado largo para ser operable.
- Mezcla dominios que podrían vivir separados.
- Hay lectores/usuarios claramente distintos (ej.: negocio vs técnico).

Regla práctica:

- Si un HUMAN supera el punto en que nadie quiere leerlo completo,
  se evalúa partir en HUMAN hijos, manteniendo un HUMAN root más estable.

==========
03.00_JERARQUIA_Y_RESOLUCION_DE_CONFLICTOS
==========

----------
03.10_PRECEDENCIA_ENTRE_HUMAN
----------

Orden de precedencia cuando HUMAN chocan entre sí:

1) HUMAN root de nivel más alto (ej.: HUMAN.PFUNDATIONS.README).
2) HUMAN root del proyecto específico.
3) HUMAN hijos de ese proyecto/sistema.

Si dos HUMAN root de nivel similar chocan, se debe resolver explícitamente
en una siguiente versión (no se “deja pasar”).

----------
03.20_RELACION_HUMAN_CON_SKILLS_Y_BATON
----------

Precedencia global:

1) HUMAN (root e hijos, respetando jerarquía entre ellos).
2) SKILLS/estándares técnicos.
3) BATON.STATE (snapshot operativo por proyecto).
4) Código/scripts/configuración.

Si un SKILL contradice HUMAN, hay dos opciones:

- El SKILL está desactualizado → se actualiza.
- HUMAN está desactualizado → se actualiza, dejando claro el cambio.

BATON.STATE solo empaqueta el estado que HUMAN y SKILLS ya definieron.

----------
03.30_RELACION_CON_RADAR
----------

RADAR:
- Describe el filesystem de un proyecto en forma determinista.
- No decide arquitectura ni negocio.

HUMAN:
- Puede referenciar RADAR como “mapa”.
- No debe copiar outputs RADAR dentro del HUMAN (se referencian).

Si algo parece demasiado detallado para HUMAN, puede migrar a:

- Un documento técnico paralelo, referenciado desde HUMAN.

Pero HUMAN debe seguir explicando las piezas clave y cómo se conectan.

04.30_REGLA_DE_NO_PERDIDA_DE_CONTEXTO

- Idealmente, se mueven a un archivo histórico si el contexto podría ser útil después.

04.40_SECCIONES_RECOMENDADAS_PARA_USO_CON_IA_EJECUTORA_(NUEVO, SIN TECNIFICAR)
++++++++++

Si el proyecto usa IA que crea/edita/elimina archivos, se recomienda que el HUMAN root tenga,
en lenguaje humano (no como manual), un bloque:

- “LÍMITES DE LA IA”: qué puede tocar y qué no.
- “MODO DE TRABAJO”: cómo se valida, cómo se revisa, cómo se hace rollback.
- “POLÍTICA DE COSTO”: principios (no números exactos) para no quemar presupuesto.

Esto no convierte HUMAN en documento técnico:
- solo registra intención, riesgos, y decisiones de gobernanza.

==========
05.00_INTERACCION_HUMANO_IA_EN_HUMAN
==========

----------
05.10_QUE_PUEDE_HACER_LA_IA
----------

La IA puede:

- Proponer reordenamiento de secciones.
- Mejorar redacción y claridad.
- Sugerir nuevas secciones cuando detecta huecos.
- Detectar contradicciones internas o con SKILLS/BATON.

La IA no debería, por defecto:

- Eliminar secciones completas sin instrucción expresa.
- Reducir un HUMAN a un resumen corto.
- Cambiar el sentido de decisiones clave sin destacarlo.

----------
05.20_FORMATO_DE_PROPUESTAS_DE_CAMBIO
----------

Cuando la IA proponga cambios en HUMAN:

- Debe indicar el título/sección afectada.
- Debe entregar BLOQUE_ORIGINAL y BLOQUE_CORREGIDO para facilitar replace.
- Si propone eliminación, debe copiar la sección a eliminar y explicar por qué.

El humano decide qué se acepta y qué no.

++++++++++
05.30_HUMAN_Y_ORQUESTACION_AI_(AI_ORCH)
++++++++++

Si el proyecto usa AI_ORCH:

- HUMAN debe declarar explícitamente:
  - qué parte del sistema puede ser “auto-ejecutable” por agente,
  - qué parte requiere aprobación humana,
  - y qué se considera cambio destructivo.

Recomendación mínima:

- Definir un bloque “LIMITES_DE_AUTOMATIZACION” en HUMAN root:
  - Allowed: creación/edición dentro de PROJECT_ROOT bajo sandbox.
  - Forbidden: OS changes, installs, secretos en repo, cambios fuera del root.

Nota:

HUMAN no se convierte en manual técnico; solo declara intención y límites operativos.

----------
05.30_REGLA_ANTI_DRIFT_EN_DECISIONES_CLAVE_(NUEVO)
----------

Si la IA sugiere cambiar una decisión clave:
- debe marcar explícitamente “CAMBIO_DE_DECISION”
- explicar impacto y tradeoffs
- proponer alternativa A/B
- no aplicar el cambio sin confirmación humana

# SKILL.HUMAN_CONTROLLED_SCRIPT_EXECUTION

MARKER: MB-SM-052A_CROSS_RUNTIME_EXECUTION_CONTRACT
VERSION: v1.2
STATUS: ACTIVE
LAYER: SKILL
OWNER_DOMAIN: SkillsMachine
PURPOSE: Define a shell/runtime-agnostic execution method for AI-delivered executable files.

==========
00.00 PRINCIPLE
==========

This methodology is not a PowerShell-only method.

It is a human-controlled local execution contract:

AI prepares an executable artifact.
Human saves it in the project TEMP path.
Human executes it locally from VS Code or terminal.
The executable emits AI_TAIL_START / AI_TAIL_END.
Human returns the AI_TAIL and any relevant TEMP outputs.
AI interprets evidence and provides the next single action.

PowerShell, Python, Bash, Node, SQL wrappers, Docker wrappers, Excel helpers, and Power Query generators are runtime adapters.

==========
01.00 DEFAULT WORKFLOW
==========

A. AI provides the executable file content or downloadable executable artifact:
   - .ps1
   - .py
   - .sh
   - .js
   - .sql runner wrapper
   - other executable/script file

B. Human saves it in the project TEMP path.

C. Human executes the exact command provided by the AI.
   The command must work from any current directory.

D. Human returns:
   - AI_TAIL_START through AI_TAIL_END; and/or
   - specific files created in TEMP that the AI explicitly requested.

==========
02.00 TEMP PATH RULE
==========

The AI must not invent a TEMP path.

The TEMP path must come from project canon:
- BATON
- WHOAMI
- HUMAN
- README
- active usecase instructions
- explicit user instruction

If TEMP path is missing and execution requires it, ask or declare a safe project-local TEMP path before script delivery.

Examples:
- SkillsMachine: C:\01. GitHub\Skills\SyS\Temp
- CloseReport: C:\01. GitHub\CloseReport\99.TEMP

==========
03.00 EXECUTION COMMAND RULE
==========

The AI must provide a command executable from any location.

PowerShell example:
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File "C:\path\to\temp\script.ps1"

Python example:
python "C:\path\to\temp\script.py"

Bash example:
bash "/mnt/c/path/to/temp/script.sh"

The script itself must resolve PROJECT_ROOT and TEMP_PATH explicitly.

==========
04.00 AI_TAIL RULE
==========

AI_TAIL is mandatory for every executable artifact unless the runtime cannot support stdout or file output.

Minimum AI_TAIL fields:
- AI_TAIL_SCHEMA=v1
- MB_ID or TASK_ID
- RUNTIME
- ROOT
- TEMP_PATH
- FINAL_STATUS
- BLOCKER
- FILES_CREATED
- FILES_MODIFIED
- VALIDATION_STATUS
- COMMIT_PUSH_PERFORMED=NO unless explicitly authorized otherwise
- NEXT_ACTION

The script must not report success unless the relevant operation actually passed.

==========
05.00 IF TOOL DOES NOT SUPPORT THE METHOD
==========

If a tool/runtime cannot produce AI_TAIL, exit code, stdout, or auditable file output, the AI must not pretend compliance.

It must declare:
- CAN_USE_METHOD_FULLY: NO
- CAN_USE_METHOD_PARTIALLY: YES/NO
- MISSING_CAPABILITIES
- SAFE_ADAPTER
- RECOMMENDATION

Examples:
Power Query M cannot emit AI_TAIL directly.
Recommendation: generate M code with Python or PowerShell and validate outputs externally.

Excel manual operations cannot guarantee exit code.
Recommendation: use a PowerShell/Python validator around the workbook.

SQL alone may not support the contract.
Recommendation: execute SQL through Python/PowerShell wrapper that emits AI_TAIL.

==========
06.00 DELIVERY MODE
==========

Default delivery mode:
- AI provides code or a downloadable file.
- Human saves to TEMP.
- Human executes locally.
- Human returns AI_TAIL.

ZIPs or multi-file bundles are allowed only when they reduce token cost or complexity and remain explicit, reviewable, and project-local.

The AI must not rely on invisible tool-side execution for final delivery unless explicitly requested.

==========
07.00 GIT RULE
==========

Scripts may inspect Git status and produce commit-ready reports.

Scripts must not commit or push unless the user explicitly delegates that action.

Prohibited by default:
- git add .
- git add -A
- automatic commit
- automatic push
- hiding dirty state
- continuing after unknown dirty worktree

==========
08.00 ADAPTER MINIMUMS
==========

PowerShell:
- Prefer pwsh when available.
- Use PS 5.1-compatible constructs when Windows PowerShell is expected.
- Avoid scalar .Count hazards by wrapping collections with @(...).
- Avoid Write-Host "=" * 60 ambiguity.
- Use GIT_PAGER=cat.
- Emit AI_TAIL in controlled final path.

Python:
- Use pathlib.
- Use try/except/finally or equivalent tail guarantee.
- Print AI_TAIL before sys.exit.
- Explicit encoding for CSV/text.
- Do not write outside project root or TEMP unless declared.

Bash:
- Use set -Eeuo pipefail.
- Use trap for tail.
- Use printf.
- Preserve exit code.
- Use git --no-pager.

Node:
- Capture uncaughtException and unhandledRejection.
- Emit tail before process.exit.

Docker:
- Use wrapper script to build/run/capture logs and emit AI_TAIL.

Power Query / Excel / VBA:
- Use generator/installer/validator wrapper when direct AI_TAIL is unavailable.

==========
09.00 COMPLIANCE GATE
==========

Before delivering executable code, the AI must be able to answer:

EXECUTION_CONTRACT_GATE:
- PROJECT:
- PROJECT_ROOT:
- TEMP_PATH:
- SCRIPT_NAME:
- SCRIPT_RUNTIME:
- TARGET_SHELL:
- MIN_VERSION:
- CAN_RUN_FROM_ANY_LOCATION:
- AI_TAIL_SUPPORTED:
- EXIT_CODE_SUPPORTED:
- FILE_OUTPUT_SUPPORTED:
- GIT_AWARE:
- AUTO_COMMIT_ALLOWED:
- USER_EXECUTES_LOCALLY:
- LIMITATION:
- RECOMMENDATION:
- DECISION: PROCEED / ADAPT / BLOCK

If the gate cannot be completed, do not deliver executable code.

==========
10.00 FAILURE MODE
==========

If the script fails, the AI must request only:
- AI_TAIL_START through AI_TAIL_END, if present;
- otherwise the minimal terminal segment needed to diagnose;
- specific TEMP outputs if relevant.

Do not ask for broad logs or full repo uploads by default.

00.20_CONTEXTO_DEL_PROBLEMA_Y_OBJETIVOS
==========

00.20.01_PROBLEMAS_REALES_QUE_MOTIVAN_RADAR

a) Proyectos crecen y se vuelven inmanejables sin inventario confiable.
b) Tooling e IA fallan cuando el repositorio no tiene mapa.
c) Auditorías, migraciones y refactors requieren trazabilidad.
d) Archivos binarios (xlsx/pdf/png) rompen intentos de "leer todo".
e) Históricos sin disciplina generan caos; sin históricos no hay continuidad.
f) En IA cloud, subir FULL/CORE completo puede disparar costos (COST_INCIDENT).
g) El contenido canónico (HUMAN) y el contenido de skills (SKILLS) necesitan
   compilarse aparte del resto del proyecto para que la IA los entienda como
   unidad completa, sin mezclarlos con código/artefactos operativos.

00.20.02_OBJETIVO_PRINCIPAL

Definir un estándar único para producir vistas:

LITE       : Inventario resumido + diffs básicos (operación diaria).
INDEX      : Inventario total + metadata (para navegación y auditoría).
CORE       : Contenido legible (texto/código) para análisis por IA/humano.
FULL       : Consolidación (INDEX + CORE + extras de auditoría como tree-size).
FULL.HUMAN : Compilación completa del contenido canónico de HUMAN, optimizada
             para lectura por IA.
FULL.SKILLS: Compilación completa del contenido de la carpeta SKILLS, separada
             del resto del proyecto, optimizada para lectura por IA.

00.20.03_OBJETIVO_SECUNDARIO

Asegurar que los outputs puedan:

Ser usados por humanos (lectura rápida, texto plano).

Ser consumidos por IA (chunks y determinismo).

Ser comparables entre ejecuciones (orden estable + formato consistente).

Reducir fricción/costo en cloud evitando "leer todo" sin necesidad.

01.00_DEFINICIONES_BASICAS
==========

01.10_RADAR

RADAR es un estándar de "descripción del FS" (file system) de un proyecto, generado por tooling.

Regla dura:

RADAR describe, no decide.

RADAR no reemplaza decisiones humanas ni lógica de negocio.

----------
01.15_RADAR_LITE
----------

RADAR_LITE es una salida liviana para operación diaria:

- Basada en metadata (similar a INDEX).
- Puede incluir diffs básicos vs ejecución previa (NEW/MODIFIED/DELETED).
- No incluye contenido (no es CORE).
- No interpreta semántica (describe, no decide).
- En primera ejecución (sin histórico previo), no calcula diffs (ver 05.30).

01.20_RADAR_INDEX

Output que lista TODOS los archivos/carpetas relevantes y su metadata (sin contenido).

Incluye, típicamente:

ruta

tamaño

última modificación

tipo lógico

hash (regla por defecto, ver 06.15)

01.30_RADAR_CORE

Output que incluye el contenido SOLO de archivos legibles (texto/código/config).

No incluye:

imágenes, audio, video

pdf (sin OCR)

binarios

xlsx (no se leen celdas)

Nota: la "estructura superficial" de xlsx (nombres de hojas) vive en INDEX (06.30),
no en CORE. CORE nunca incluye contenido de xlsx bajo ninguna forma.

01.40_RADAR_FULL

Output que consolida:

INDEX + CORE

y agrega extras de auditoría (ej.: tree-size por carpeta)

FULL no agrega semántica de negocio; sigue siendo descriptivo.

----------
01.50_HUMAN_Y_SKILLS_COMO_CARPETAS_CANONICAS_(NUEVO)
----------

HUMAN y SKILLS son carpetas canónicas del ecosistema cuya ubicación física
(ruta) NO es definida por RADAR. La ruta de ambas es resuelta vía
SKILL.PROJECT_INFORMATION_ARCHITECTURE.txt (ver DEPENDENCIAS).

RADAR solo:

- Consume la ruta resuelta de HUMAN y SKILLS.
- Compila su contenido en outputs dedicados (FULL.HUMAN, FULL.SKILLS).
- Describe cambios detectados (ver 05.20), sin evaluarlos.

HUMAN es contenido canónico de baja frecuencia de cambio; "de esa carpeta se
desprende todo" y su edición debe evitarse salvo necesidad real. RADAR no
impone ni bloquea esa regla (no decide), solo la hace visible (describe).

02.70_PERFILES_PRIMERA_EJECUCION_Y_POLITICA_DE_GENERACION
++++++++++

Cada ejecución declara SCAN_PROFILE y OUTPUT_SET. Todo SCAN_PROFILE define
PROFILE_NAME, ROOT_PATHS, EXCLUDED_PATHS, DEPTH_POLICY, HASH_POLICY, ERROR_POLICY
y OUTPUT_SET. Los perfiles locales solo pueden referenciar roots de su proyecto;
permanecen locales y no se promueven como configuración global. Perfiles mínimos:

- INITIAL_BASELINE: LITE, INDEX, CORE, FULL, FULL.HUMAN, FULL.SKILLS, MANIFEST.
- DAILY: LITE, INDEX, MANIFEST.
- MODULE_ANALYSIS: LITE, INDEX, CORE acotado, MANIFEST.
- CLOSURE: LITE, INDEX, outputs exigidos por el gate, MANIFEST.
- FULL_AUDIT: los seis outputs descriptivos y MANIFEST.
- HUMAN_AUDIT: LITE, INDEX, FULL.HUMAN, MANIFEST.
- SKILLS_AUDIT: LITE, INDEX, FULL.SKILLS, MANIFEST.
- LEGACY_SIX_OUTPUTS: compatibilidad temporal con consumidores anteriores.

CORE, FULL, FULL.HUMAN y FULL.SKILLS se generan obligatoriamente durante la
primera ejecución válida de RADAR para establecer la línea base integral del
proyecto. En ejecuciones posteriores se generan solo cuando los exige el perfil,
los solicita explícitamente el operador o los requiere un gate de auditoría,
cierre o continuidad.

La ausencia de archivos ACTIVE no constituye por sí sola primera ejecución.
INITIAL_BASELINE aplica cuando no existe ningún RADAR_MANIFEST válido y
compatible para el PROJECT_ID. Si la línea base integral no puede completarse,
STATUS=FAIL y BASELINE_CREATED=NO; no se publica una línea base parcial.

La política de generación local es independiente de UPLOAD_SELECTION. Ningún
output se sube a IA cloud automáticamente.
NO_SUBIR != NO_GENERAR. Un output puede existir en el FS local y quedar fuera
de UPLOAD_SELECTION.

Decisión humana: mantener seis outputs locales en la primera ejecución válida.
Costo local: INDEX+CORE+FULL+FULL.HUMAN+FULL.SKILLS en repos grandes es caro.
Optimización permitida DESPUÉS de INITIAL_BASELINE: DAILY upload selection (LITE/INDEX);
CORE/FULL on-demand para upload, no para dejar de generarlos; DEPTH_POLICY; HASH omitido
sobre umbral; no seguir reparse.
Incremental scan / caching: no forman parte del contrato duro. Cada corrida enumera el árbol.
Límites: CORE_MAX_FILE_SIZE; SEGMENT_MAX_BYTES; MaxFileCountWarning; SizeWarningBytes.
Falta de espacio: STATUS=FAIL; publicación atómica; no se publican ACTIVE parciales.

----------
06.15_REGLA_DE_HASH_POR_DEFECTO_(NUEVO)
----------

Para evitar ambigüedad y mantener determinismo entre proyectos:

- SHA256 es OBLIGATORIO para todo archivo listado en INDEX cuyo tamaño sea
  menor al umbral configurable (default sugerido: 50 MB).
- Sobre ese umbral, el hash es OPCIONAL por costo de cómputo, pero el campo
  NUNCA queda vacío sin explicación: debe registrarse como
  "HASH_OMITIDO_POR_TAMANO".
- El umbral es configurable por proyecto, pero debe quedar documentado en los
  metadatos de la ejecución (mismo patrón que la excepción de 04.20).

06.20_DETECCION_DE_BINARIOS_TEXTO_Y_ENCODING

La clasificación no depende solo de la extensión ni de “parece binario”.
Orden obligatorio:

1. Clasificar reparse points / shortcuts antes de abrir.
2. BOM: UTF-8/UTF-16 LE/BE reconocidos como texto candidato.
3. Aplicar lista binaria dura y firmas conocidas (magic bytes / MIME si el host lo expone).
4. Si la muestra contiene byte NUL, clasificar BINARY.
5. Intentar UTF-8 estricto y luego encodings permitidos por el perfil.
6. Aplicar umbral documentado de caracteres de control.
7. Extensión textual + contenido binario => BINARY (no incorporar inline).
8. Extensión binaria + contenido textual inequívoco => TEXT_WITH_BINARY_EXTENSION;
   no incorporar inline en CORE/FULL salvo lista blanca explícita.
9. Si no hay resultado inequívoco: UNREADABLE_OR_BINARY y no incorporar contenido.
10. RESULT: TEXT | BINARY | UNREADABLE_OR_BINARY | EXCLUDED. Fallo de lectura = UNREADABLE.

INDEX registra DETECTION_METHOD, DETECTED_ENCODING, CONFIDENCE y CONTENT_STATUS.
Los binarios se listan con metadata y hash, pero no se intenta leer su contenido
ni se incorporan inline en bundles de texto.

----------
06.25_LINKS_REPARSE_POINTS_Y_HARDLINKS
----------

FOLLOW_REPARSE_TARGETS_DEFAULT=NO
FOLLOW_00_ACCESS_TARGETS=NO
HARDLINK_CONTENT_COUNT=ONCE_PER_FILE_ID
BROKEN_LINKS=REPORT_WITHOUT_FOLLOW
CYCLES=STOP_AND_REPORT

Symlinks, junctions, mount points y otros reparse points se listan en INDEX y
no se siguen por defecto. Targets fuera del root nunca se siguen.
Hardlink: VOLUME_ID + FILE_ID; el contenido se incorpora una sola vez.
RADAR.ps1 v0.7.0 implementa 06.20 y 06.25 (GetFileInformationByHandle; BFS sin follow).
Si FILE_ID no está disponible, el fallback es conservador (PATH key, warning
FILE_ID_UNAVAILABLE, sin afirmar deduplicación perfecta).

00_ACCESS (ROLE_ID from SKILL.PROJECT_INFORMATION_ARCHITECTURE.txt) is a non-canonical
navigation surface. RADAR MUST NOT follow shortcut, symlink or junction targets
that originate under 00_ACCESS. List them in INDEX only.

Campos adicionales para TIPO_LOGICO = symlink:

- TARGET_RUTA: ruta a la que apunta el symlink.
- LINK_TYPE, REPARSE_TAG, TARGET_RUTA, TARGET_ESTADO y TARGET_SCOPE.
- FILE_ID, VOLUME_ID y DUPLICATE_OF cuando aplique.
- TARGET_ESTADO: VALID / BROKEN / CIRCULAR / INACCESSIBLE.
- TARGET_SCOPE: INSIDE_ROOT / OUTSIDE_ROOT.

nombres de hojas

Prohibido:

leer celdas / KPIs / fórmulas (eso es negocio y va fuera de RADAR)

07.00_ESTANDAR_RADAR_CORE
==========

07.10_INCLUSION_POR_LISTA_BLANCA

CORE incluye solo extensiones legibles (texto/código/config), típicamente:
.txt, .ps1, .py, .json, .yml/.yaml, .xml, .csv, .js, .ts, .md (si existiera)

07.20_ENCODING_ERRORES_Y_ESQUEMA_DE_BLOQUES

Cada archivo incorporado usa bloques formales:

=== RADAR_FILE_BEGIN ===
PATH_JSON=<string JSON>
SIZE_BYTES=<entero>
SHA256=<hex>
ENCODING=<valor>
CONTENT_STATUS=<valor>
CONTENT_LENGTH_BYTES=<entero>
--- RADAR_CONTENT_BEGIN:<SHA256> ---
<contenido>
--- RADAR_CONTENT_END:<SHA256> ---
=== RADAR_FILE_END ===

Metadata textual se serializa como string JSON para resolver comillas,
backslashes y caracteres de control. El delimitador incorpora SHA256 y la
longitud en bytes permite validar el bloque sin heurísticas.

Si un archivo no puede leerse por permiso, encoding o bloqueo:

CORE debe registrar error dentro del bloque del archivo (sin detener todo el proceso si el proyecto lo permite)

pero el script debe reflejar estado final (OK real vs FAIL)

STRICT: un archivo requerido ilegible produce FAIL.
TOLERANT: continúa y produce PASS_WITH_GAPS. Nunca produce PASS.

07.30_CONTROL_DE_TAMANO_(RECOMENDADO)

Para evitar CORE obeso:
- permitir exclusión por tamaño (ej.: > 2MB) con registro en CORE "SKIPPED_TOO_LARGE"
- sin ocultarlo: debe aparecer en INDEX y en CORE como "skipped".

----------
09.25_NAMING_DE_HISTORICOS_(NUEVO)
----------

Determinístico, basado en timestamp ISO sin separadores ambiguos (formato
AAAAMMDD-HHMMSS).

El ACTIVE de cada output siempre se sobrescribe en la ejecución más reciente.
El HIST nunca se sobrescribe: al generarse un nuevo ACTIVE, el ACTIVE anterior
se mueve a histórico con el siguiente naming:

RADAR_<TIPO>.HIST.<timestamp>.txt

Ejemplo:
RADAR_FULL.HIST.20260226-143000.txt
RADAR_FULL.HUMAN.HIST.20260226-143000.txt
RADAR_FULL.SKILLS.HIST.20260226-143000.txt

Los 6 outputs de una misma corrida comparten el mismo timestamp, permitiendo
agruparlos por prefijo como pertenecientes a una única ejecución.

09.30_SEGMENTACION_HIBRIDA
++++++++++

Texto (outputs y/o contenido textual):

Preferir corte por límites de línea (mejor lectura humana).

Si no es posible (líneas extremadamente largas), fallback a corte por bytes.

Binario (si se segmenta por alguna razón excepcional):

Corte por bytes (reconstrucción byte-exact).

Notas:

El objetivo de la segmentación es consumo IA/humano, no optimización.

El activo completo es la fuente de verdad local.

----------
10.30_POLITICA_DE_SECRETOS_Y_DO_NOT_UPLOAD
----------

Antes de incorporar texto a CORE, FULL, FULL.HUMAN o FULL.SKILLS, RADAR aplica
exclusión y detección de secretos. Se excluyen por defecto .env, claves privadas,
certificados con clave, archivos de credenciales y patrones configurados de
tokens, passwords, connection strings y API keys.

Un secreto detectado nunca se copia al output ni al log. Se reemplaza por
[REDACTED:<TYPE>:<FINGERPRINT>] o, si no puede garantizarse una redacción segura,
el archivo completo queda SKIPPED_SECRET_RISK. El manifest declara SAFE_FOR_LOCAL
y SAFE_FOR_UPLOAD. Un output no es seguro para upload por mera presunción.

La ruta 00.SOURCE_DO_NOT_UPLOAD y todo su contenido:

- puede aparecer en INDEX solo con metadata mínima;
- nunca se incorpora a CORE, FULL, FULL.HUMAN ni FULL.SKILLS;
- nunca se incorpora a segmentos o derivados de consumo IA;
- se registra como CONTENT_STATUS=EXCLUDED_DO_NOT_UPLOAD y EXCLUSION_POLICY=HARD.

FULL.SKILLS es fail-closed: si hay incertidumbre material (secreto, clasificación,
DO_NOT_UPLOAD, encoding ilegible), el archivo no se incorpora y SAFE_FOR_UPLOAD=NO
para ese output. No imprimir secretos detectados en logs, reportes ni fixtures.

12.00_EVIDENCIA_ESTADO_FINAL_EXIT_CODE
==========

12.10_ESTADOS_Y_DONE

Estados permitidos: PASS, PASS_WITH_GAPS, FAIL, BLOCKED_CONFIGURATION y STALE.

DONE exige todos los outputs solicitados por OUTPUT_SET, mismo RUN_ID, hashes
válidos, manifest consistente, ausencia de escritura parcial y terminación sin
excepción no controlada. La mera existencia de archivos ACTIVE no prueba DONE.

12.20_EXIT_CODE

Regla dura:

No imprimir "OK/COMPLETADO" si hubo error no controlado.

Ante excepción no controlada: exit 1.

Solo OK si todo terminó correcto.

PASS_WITH_GAPS debe imprimirse como tal; nunca se presenta como OK/PASS.

12.30_LOGS_(RECOMENDADO)

Registrar:
- comando exacto
- root
- exclusiones
- outputs generados (paths, incluyendo FULL.HUMAN y FULL.SKILLS)
- estado final OK/FAIL

----------
12.40_PUBLICACION_ATOMICA_Y_FRESHNESS
----------

RADAR genera primero en staging temporal, valida el conjunto, mueve los ACTIVE
anteriores a HISTORY, publica el nuevo conjunto y publica MANIFEST al final.
Si falla antes de publicar MANIFEST, el conjunto anterior sigue siendo el último
ACTIVE válido y la corrida fallida no crea baseline.

Después de operaciones masivas, builds o cadenas de mutaciones, RADAR debe
regenerarse antes de utilizarse como evidencia de cierre. Un RADAR anterior a
la última mutación relevante tiene FRESHNESS=STALE.

Cada output declara exclusiones y gaps conocidos. Ausencia dentro de una ruta
excluida nunca demuestra ausencia en el filesystem.

12.50_RETENCION_DE_HISTORICOS

La política de retención es configurable y se registra en MANIFEST. Debe fijar
cantidad máxima, antigüedad máxima y protección de baselines/cierres. RADAR no
elimina históricos protegidos ni aplica una purga implícita.

11.00_ARTIFACT_CLASS_TAXONOMY
Every repository artifact belongs to exactly one class:
- CANONICAL_SOURCE: authoritative, human/AI-edited content (SkillsLake, GRCLake,
  registries, tools source).
- GENERATED_OUTPUT: produced by BUILD or other generators (90.USECASE bundles,
  manifests, copied menus). Never manually patched.
- EVIDENCE: run logs, reports, upload packages, RADAR outputs. Historical record,
  not a source of rules.
- LOCAL_CONFIG: operator/workstation-local tool configuration. Never canon.
An artifact whose class is ambiguous must be classified before it is mutated
(see GRC.UNKNOWN_WORKTREE_STATE_HARD_STOP).

11.10_APPEND_ONLY_HISTORY_VS_ACTIVE_TRUTH
Append-only history registers (backlogs, accumulated registers, changelogs)
preserve the record; they are NOT the active source of truth. Stale OPEN/DONE
values in historical entries do not override the current active registers.
The active state lives in the designated active register for each concern
(e.g. SyS\PROJECT.BACKLOG.ACTIVE.txt for product backlog).

11.20_ONE_CANONICAL_AUTHORITY
For each active state (versions, menu, backlog, roadmap, debt), exactly ONE
artifact is the canonical authority. When two artifacts disagree, the declared
authority wins and the other must be corrected or explicitly superseded, never
silently ignored.

11.30_PROMOTION_DISPOSITION_FIELDS
When a candidate is dispositioned, the record must state:
- DISPOSITION: MERGED | PROMOTED | REJECTED | DEFERRED | PROJECT_LOCAL
- TARGET: the artifact(s) receiving merged/promoted content
- SOURCE_MB: the minibattle performing the disposition

11.40_GENERATED_USECASE_OUTPUTS
Never manually patch generated 90.USECASE outputs. Patch canonical source and
regenerate via BUILD. A manual edit to a generated output is drift, not a fix.

11.50_MACHINE_MANIFESTS_AND_DISTRIBUTION
Machine-facing manifests (JSON registries, schemas) may live outside the
single-file upload distribution for humans/IA. Consolidated distribution
completeness is measured against declared content, not against every machine
manifest in the repository.

10.00_REGLAS_DE_CONSISTENCIA
==========

Caso 1:
BATON contradice HUMAN.

Dictamen:
BATON está incorrecto o desactualizado.

Acción:
Actualizar BATON o declarar brecha.

----------

Caso 2:
Skill contradice HUMAN.

Dictamen:
Conflicto conceptual.

Acción:
Resolver actualizando explícitamente HUMAN o Skill según decisión humana.

----------

Caso 3:
RADAR contradice BATON.

Dictamen:
BATON está desactualizado o RADAR refleja cambios no incorporados.

Acción:
Revisar evidencia antes de cerrar.

----------

Caso 4:
IA propone acción que viola Skill.

Dictamen:
Acción inválida.

Acción:
Bloquear o pedir excepción humana documentada.

----------

Caso 5:
Usuario pide estado pero no cierre.

Dictamen:
No activar cierre formal.

Acción:
Responder estado, pero no ejecutar protocolo completo.

----------

Caso 6:
Usuario dice "cierra sesión".

Dictamen:
Activar cierre formal completo.

Acción:
Ejecutar contrato de cierre de este Skill.

12.00_DEFINICIONES_OPERATIVAS
==========

----------
12.10_MINIBATTLE
----------

Unidad corta de avance, verificable, con output concreto y evidencia mínima.

Debe reducir riesgo, desbloquear trabajo o producir avance funcional.

----------
12.20_BATTLE
----------

Bloque mayor de trabajo compuesto por una o más minibattles.

Debe conducir hacia una capacidad funcional, decisión relevante o entregable demostrable.

----------
12.30_ENTREGABLE_FUNCIONAL_A_GERENCIA
----------

Resultado demostrable, entendible por gerencia y con valor visible.

Puede ser demo, reporte, tablero, presentación, proceso operativo validado o automatización funcional.

No debe ser solo documentación interna salvo que el objetivo gerencial sea gobierno documental.

----------
12.40_BATON_PRINCIPAL_DEL_PROYECTO_ACTIVO
----------

Archivo o artefacto de continuidad que resume el estado operativo mínimo para continuar el proyecto en una IA en blanco.

----------
12.50_BACKLOG_OPERATIVO_DEL_PROYECTO
----------

Lista activa de pendientes, mejoras, deuda técnica, riesgos y próximas acciones del proyecto.

Se actualiza al cierre si existe y si hay información suficiente.

----------
12.60_RADAR
----------

Mapa o índice vigente del filesystem/proyecto usado como evidencia de estado, rutas y artefactos disponibles.

Si falta RADAR y el cierre depende de estado de archivos, la IA debe pedir su ejecución.

==========
13.00_ACUMULACION_Y_PERFECCIONAMIENTO_DE_ARTEFACTOS
==========

----------
13.10_REGLA_BASE
----------

Durante el cierre formal de sesión, cada artefacto debe cumplir su función correcta.

No se debe copiar la misma información en todas las capas.

Regla de capa:

- Backlog acumula.
- Deuda técnica acumula.
- HUMAN se perfecciona.
- BATON se refresca.
- RADAR se regenera.
- Git registra.

----------
13.20_BACKLOG
----------

El backlog operativo del proyecto acumula pendientes no resueltos, mejoras, decisiones abiertas y próximos pasos.

En cada cierre formal:

- se agregan nuevos pendientes;
- se actualizan pendientes existentes;
- se cierran ítems resueltos;
- se fusionan duplicados;
- se reclasifican ítems cuando cambia su naturaleza.

Un pendiente no resuelto permanece abierto.

No debe duplicarse como nuevo ítem si ya existe.

----------
13.30_DEUDA_TECNICA
----------

La deuda técnica acumula problemas técnicos, estructurales u operativos no resueltos.

Debe distinguirse de:

- backlog funcional;
- brecha de información;
- riesgo abierto;
- decisión pendiente.

Estados recomendados:

- NUEVA
- EXISTENTE_SIN_CAMBIO
- EXISTENTE_ACTUALIZADA
- MITIGADA
- RESUELTA
- ACEPTADA_CONSCIENTEMENTE
- DESCARTADA

La deuda técnica debe mantener, cuando exista evidencia suficiente:

- descripción;
- causa;
- impacto;
- riesgo;
- evidencia;
- próximo paso;
- prioridad;
- relación con minibattle o battle si aplica.

----------
13.40_HUMAN
----------

HUMAN no acumula tareas ni pendientes operativos.

HUMAN se perfecciona solo cuando existe:

- cambio doctrinal;
- aclaración de intención humana;
- cambio de visión;
- cambio de principio rector;
- cambio de precedencia;
- cambio de regla raíz;
- mejora conceptual canónica.

Ejemplo correcto:
Actualizar HUMAN para declarar una nueva regla superior de arquitectura o gobernanza.

Ejemplo incorrecto:
Agregar a HUMAN una tarea pendiente de implementación.

Las tareas pendientes van en backlog, no en HUMAN.

----------
13.50_BATON
----------

BATON no acumula historia completa.

BATON es snapshot operativo vigente.

Debe reflejar:

- estado actual;
- objetivo activo;
- próximos pasos;
- riesgos o brechas que afectan continuidad;
- archivos/capas relevantes para continuar;
- decisión operativa vigente.

BATON debe refrescarse al cierre formal cuando exista información suficiente.

No debe convertirse en manual, backlog ni changelog completo.

----------
13.60_RADAR
----------

RADAR no se edita manualmente.

RADAR se regenera como evidencia del filesystem o estructura equivalente del proyecto.

RADAR no decide lógica ni doctrina.

RADAR ayuda a validar:

- archivos existentes;
- rutas;
- cambios de filesystem;
- outputs;
- estado documental observable.

----------
13.70_GIT
----------

Git registra trazabilidad histórica mediante commits, ramas, tags y diferencias.

Este Skill no define comandos Git.

La operación Git debe derivarse al Skill de Git aplicable.

----------
13.80_REGLA_ANTI_DUPLICACION
----------

No se debe duplicar la misma información en múltiples artefactos.

Cada contenido debe vivir en su capa correcta:

- doctrina en HUMAN;
- estado operativo vigente en BATON;
- pendientes en backlog;
- problemas estructurales en deuda técnica;
- evidencia filesystem en RADAR;
- trazabilidad histórica en Git.

Si una misma idea aparece en varias capas, debe tener propósito distinto en cada una.

----------
13.90_CRITERIO_DE_CIERRE
----------

Al cierre formal, la IA debe revisar si cada dato pertenece a:

- HUMAN;
- BATON;
- backlog;
- deuda técnica;
- RADAR;
- Git;
- otro artefacto del proyecto activo.

Si no existe evidencia suficiente para clasificar un dato, debe declararse como brecha y no inventarse.

MB-GRC-034C_MINIBATTLE_SAFE_LAUNCHER_GATE
==========

DATE..............: 2026-06-21
STATUS............: ACTIVE
LAYER.............: PROJECT_LIFECYCLE_POLICY
PURPOSE...........:
Prevent minibattle execution from damaging terminal state, committing unintended generated outputs,
or bypassing validation/stage discipline when long scripts or launchers are required.

SCOPE.............:
Applies to any minibattle, one-shot, repository patch, session close, session continue, RADAR,
build, validation, or governance patch that requires a long PowerShell script.

SAFE_LAUNCHER_GATE:
Before running a long PowerShell operation, the IA must use the safe launcher pattern:

1. TEMP_SCRIPT_FILE:
   Write long logic to SyS/Temp/<MB_ID>.<timestamp>.ps1.

2. SHORT_CONSOLE_LAUNCHER:
   The interactive console only creates the .ps1 file, runs pwsh -File, captures LASTEXITCODE,
   prints SCRIPT_EXIT and LAUNCHER_STATUS, and returns to prompt.

3. NO_INTERACTIVE_TRY_CATCH_FINALLY:
   Do not paste long try/catch/finally blocks directly into the interactive terminal.

4. NO_LAUNCHER_EXIT:
   The launcher must not call exit. It must not close VS Code terminal or the user shell.

5. NO_NESTED_HERE_STRING:
   Do not nest PowerShell here-strings inside launcher here-strings. Use arrays of lines or a
   different construction method.

6. NO_PAGER_CAPTURE:
   Set GIT_PAGER=cat and PAGER=cat. Use git --no-pager for log/diff/show/status diagnostics.

7. BUILD_SCOPE_GATE:
   Do not run BUILD.ps1 unless generated outputs are explicitly in scope. If BUILD dirties
   generated outputs unexpectedly, STOP before commit and decide restore/isolate/commit explicitly.

8. EXPLICIT_STAGE_ONLY:
   Stage only the expected files with explicit git add -- <path>. Do not use git add -A or git add .
   for governance/policy patches.

9. DIRTY_SET_GATE:
   Before commit, compare git status --short against an allowed dirty-file whitelist. If unexpected
   files appear, STOP and report.

10. STAGED_DIFF_GATE:
   Print git --no-pager diff --cached --name-status. If no staged changes exist, STOP before commit.

11. VALIDATION_GATE:
   Run Validate-System.ps1 before commit. If available and relevant, run post-build validation as well.

12. FINAL_CLEAN_GATE:
   After commit/push, verify branch, HEAD, remote head, unpushed/unpulled and clean working tree.

REQUIRED_OUTPUT:
Every lifecycle script must print START/END, LOCAL_TIME, ROOT, PURPOSE, COPY_FROM_HERE, validation
exit code, commit/push exit codes if applicable, FINAL_STATUS, LOG_PATH and NEXT_ACTION.

FAILURE_HANDLING:
- If terminal closes, run recovery diagnostic before continuing.
- If generated outputs become dirty unexpectedly, restore or isolate before further changes.
- If a commit fails because staged set is empty, inspect whether the intended files were actually changed.
- If the shell enters pager END state, rerun with --no-pager and pager environment disabled.

DONE_WHEN.........:
A minibattle can be executed without closing the user's terminal, without accidental generated-output
commits, and with deterministic validation/stage/commit/push/final-clean evidence.

==========
00.00_PURPOSE
==========

This file gives an AI-executable operating brief for IT project delivery work.

It exists to make usecase packages more self-contained for a blank AI.

It does not replace HUMAN documents.
It does not replace the full AI constitution.
It summarizes the minimum operating rules required inside usecase bundles.

==========
01.00_NAMING_AND_AUDIENCE_RULE
==========

A document primarily directed to a human must include HUMAN in the filename.

If a file name does not contain HUMAN, treat it as primarily directed to AI, machine, automation, operation, or package consumption.

Files without HUMAN may mention HUMAN as a governance concept.
That does not make them human-facing documents.

==========
02.00_REQUIRED_OUTPUT_TYPE
==========

For IT project workflows, the AI must classify the intended output before expanding work.

Allowed output types:

DEPLOY_DONE:
Executable, runnable, or deployable product output.
The result must run, deploy, or behave as a usable product according to the agreed first-deploy standard.

DELIVERABLE_DONE:
Analytical, documentary, operational, or non-deployable product output.
The result must exist at the declared path and satisfy explicit acceptance criteria.

If OUTPUT_TYPE is unclear, ask for the minimum clarification needed before designing the work path.

==========
03.00_FIRST_DEPLOY_SEQUENCE
==========

For new IT projects, the AI must drive toward the first output through this sequence:

STEP_01:
Define the product:
- problem solved;
- how it works;
- approximate implementation approach;
- minimum features;
- future features;
- target audience.

STEP_02:
Define the first deploy or first deliverable.

STEP_03:
Define the minimum mockup.
The mockup is not decoration. It is the smallest concrete representation that allows the human and AI to validate shape, scope, interaction, and expected result.

STEP_04:
Define minimum functionality and characteristics required for the first output.

STEP_05:
Define the minimum work needed to fulfill the first output.

STEP_06:
Define investment limits:
- time;
- cost;
- effort;
- complexity;
- token/model budget when relevant.

STEP_07:
Define Plan B before execution.

STEP_08:
Execute until DEPLOY_DONE, DELIVERABLE_DONE, or stop-loss trigger.

==========
04.00_STOP_LOSS_AND_PORTFOLIO_SPRAWL_CONTROL
==========

The AI must prevent portfolio sprawl.

Do not expand into platform, governance, architecture, automation, tooling, refactor, future features, or generic infrastructure unless it directly unblocks the first DEPLOY_DONE or DELIVERABLE_DONE.

Do not continue iteration by habit after Plan B trigger.

When work exceeds the declared investment limits, stop and present:
- current state;
- blocking issue;
- options;
- recommendation;
- Plan B activation decision.

==========
05.00_BACKLOG_RULE

==========
00.00 PURPOSE
==========

DragonflyFocus is a mandatory focus-control GRC for SkillsMachine operations.

Its purpose is to prevent conversational drift, uncontrolled branching, overproduction,
premature tooling, and assistant-led deviation from the HUMAN-defined objective.

DragonflyFocus exists because the user may produce many valuable ideas during project work,
but not every idea is allowed to become the active workstream.

The assistant must capture side ideas, classify them, and return to the active objective.

==========
01.00 CORE RULE
==========

HUMAN defines the objective.

The assistant must not replace the active objective because of conversational drift,
interesting side ideas, technical curiosity, tooling opportunities, or assistant preference.

If the user introduces a new idea, the assistant must classify it before acting.

No change of mission is allowed without explicit human confirmation.

==========
02.00 MANDATORY FOCUS_GATE
==========

Every operational response under the covered usecases must include or internally apply:

FOCUS_GATE:
- OBJECTIVE_ACTIVE:
- CURRENT_STEP:
- USER_NEW_IDEA:
- CLASSIFICATION:
- DECISION:
- NEXT_ACTION:

CLASSIFICATION values:

- CORE_OBJECTIVE
  The new idea directly advances the active objective.

- BLOCKER
  The new idea reveals something that blocks the active objective.

- TECHNICAL_DEBT
  The new idea is valid but should be registered and not executed now.

- BACKLOG
  The new idea is useful but not needed for the active objective.

- CHANGE_OF_MISSION
  The new idea would replace or materially alter the active objective.

- DISCARD
  The new idea is noise, duplicate, obsolete, or not worth carrying forward.

==========
03.00 DECISION RULES
==========

03.10 CORE_OBJECTIVE

If classification is CORE_OBJECTIVE:
- incorporate it into the current step;
- explain why it advances the objective;
- keep the next action singular.

03.20 BLOCKER

If classification is BLOCKER:
- stop execution;
- define the blocker;
- define the minimum unblock action;
- do not continue with unrelated tasks.

03.30 TECHNICAL_DEBT

If classification is TECHNICAL_DEBT:
- register it as technical debt;
- do not execute it immediately;
- return to OBJECTIVE_ACTIVE.

03.40 BACKLOG

If classification is BACKLOG:
- capture it briefly;
- do not expand it;
- return to OBJECTIVE_ACTIVE.

03.50 CHANGE_OF_MISSION

If classification is CHANGE_OF_MISSION:
- stop;
- explicitly ask the human to confirm mission replacement;
- do not proceed until confirmation is given.

Required wording:

CAMBIO_DE_MISION detectado.
Objetivo activo actual:
[OBJECTIVE_ACTIVE]

Nuevo objetivo propuesto:
[NEW_OBJECTIVE]

Impacto:
[IMPACT]

Confirmas reemplazar el objetivo activo? YES/NO

03.60 DISCARD

If classification is DISCARD:
- state briefly why it is discarded;
- do not preserve it unless the human insists.

==========
04.00 ASSISTANT BEHAVIOR CONSTRAINTS
==========

The assistant must not:

- follow every user branch as if it were the active objective;
- produce large scripts unless they directly advance the active step;
- transform backlog into execution without approval;
- create PR/merge/launcher/tooling work if the active objective is user-flow definition;
- optimize governance instead of finishing the deliverable;
- confuse technical progress with product progress;
- bury the user in options when one next action is required.

The assistant must:

- identify the active objective;
- protect the objective from drift;
- preserve useful side ideas without executing them;
- force mission-change confirmation;
- recommend one next action;
- prefer deliverable completion over system elaboration.

DRAGONFLYFOCUS_DECISION:

# SKILL.HUMAN_CONTROLLED_SCRIPT_EXECUTION

MARKER: MB-SM-052A_CROSS_RUNTIME_EXECUTION_CONTRACT
VERSION: v1.2
STATUS: ACTIVE
LAYER: SKILL
OWNER_DOMAIN: SkillsMachine
PURPOSE: Define a shell/runtime-agnostic execution method for AI-delivered executable files.

==========
00.00 PRINCIPLE
==========

This methodology is not a PowerShell-only method.

It is a human-controlled local execution contract:

AI prepares an executable artifact.
Human saves it in the project TEMP path.
Human executes it locally from VS Code or terminal.
The executable emits AI_TAIL_START / AI_TAIL_END.
Human returns the AI_TAIL and any relevant TEMP outputs.
AI interprets evidence and provides the next single action.

PowerShell, Python, Bash, Node, SQL wrappers, Docker wrappers, Excel helpers, and Power Query generators are runtime adapters.

==========
01.00 DEFAULT WORKFLOW
==========

A. AI provides the executable file content or downloadable executable artifact:
   - .ps1
   - .py
   - .sh
   - .js
   - .sql runner wrapper
   - other executable/script file

B. Human saves it in the project TEMP path.

C. Human executes the exact command provided by the AI.
   The command must work from any current directory.

D. Human returns:
   - AI_TAIL_START through AI_TAIL_END; and/or
   - specific files created in TEMP that the AI explicitly requested.

==========
02.00 TEMP PATH RULE
==========

The AI must not invent a TEMP path.

The TEMP path must come from project canon:
- BATON
- WHOAMI
- HUMAN
- README
- active usecase instructions
- explicit user instruction

If TEMP path is missing and execution requires it, ask or declare a safe project-local TEMP path before script delivery.

Examples:
- SkillsMachine: C:\01. GitHub\Skills\SyS\Temp
- CloseReport: C:\01. GitHub\CloseReport\99.TEMP

==========
03.00 EXECUTION COMMAND RULE
==========

The AI must provide a command executable from any location.

PowerShell example:
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File "C:\path\to\temp\script.ps1"

Python example:
python "C:\path\to\temp\script.py"

Bash example:
bash "/mnt/c/path/to/temp/script.sh"

The script itself must resolve PROJECT_ROOT and TEMP_PATH explicitly.

==========
04.00 AI_TAIL RULE
==========

AI_TAIL is mandatory for every executable artifact unless the runtime cannot support stdout or file output.

Minimum AI_TAIL fields:
- AI_TAIL_SCHEMA=v1
- MB_ID or TASK_ID
- RUNTIME
- ROOT
- TEMP_PATH
- FINAL_STATUS
- BLOCKER
- FILES_CREATED
- FILES_MODIFIED
- VALIDATION_STATUS
- COMMIT_PUSH_PERFORMED=NO unless explicitly authorized otherwise
- NEXT_ACTION

The script must not report success unless the relevant operation actually passed.

==========
05.00 IF TOOL DOES NOT SUPPORT THE METHOD
==========

If a tool/runtime cannot produce AI_TAIL, exit code, stdout, or auditable file output, the AI must not pretend compliance.

It must declare:
- CAN_USE_METHOD_FULLY: NO
- CAN_USE_METHOD_PARTIALLY: YES/NO
- MISSING_CAPABILITIES
- SAFE_ADAPTER
- RECOMMENDATION

Examples:
Power Query M cannot emit AI_TAIL directly.
Recommendation: generate M code with Python or PowerShell and validate outputs externally.

Excel manual operations cannot guarantee exit code.
Recommendation: use a PowerShell/Python validator around the workbook.

SQL alone may not support the contract.
Recommendation: execute SQL through Python/PowerShell wrapper that emits AI_TAIL.

==========
06.00 DELIVERY MODE
==========

Default delivery mode:
- AI provides code or a downloadable file.
- Human saves to TEMP.
- Human executes locally.
- Human returns AI_TAIL.

ZIPs or multi-file bundles are allowed only when they reduce token cost or complexity and remain explicit, reviewable, and project-local.

The AI must not rely on invisible tool-side execution for final delivery unless explicitly requested.

==========
07.00 GIT RULE
==========

Scripts may inspect Git status and produce commit-ready reports.

Scripts must not commit or push unless the user explicitly delegates that action.

Prohibited by default:
- git add .
- git add -A
- automatic commit
- automatic push
- hiding dirty state
- continuing after unknown dirty worktree

==========
08.00 ADAPTER MINIMUMS
==========

PowerShell:
- Prefer pwsh when available.
- Use PS 5.1-compatible constructs when Windows PowerShell is expected.
- Avoid scalar .Count hazards by wrapping collections with @(...).
- Avoid Write-Host "=" * 60 ambiguity.
- Use GIT_PAGER=cat.
- Emit AI_TAIL in controlled final path.

Python:
- Use pathlib.
- Use try/except/finally or equivalent tail guarantee.
- Print AI_TAIL before sys.exit.
- Explicit encoding for CSV/text.
- Do not write outside project root or TEMP unless declared.

Bash:
- Use set -Eeuo pipefail.
- Use trap for tail.
- Use printf.
- Preserve exit code.
- Use git --no-pager.

Node:
- Capture uncaughtException and unhandledRejection.
- Emit tail before process.exit.

Docker:
- Use wrapper script to build/run/capture logs and emit AI_TAIL.

Power Query / Excel / VBA:
- Use generator/installer/validator wrapper when direct AI_TAIL is unavailable.

12.00 DISTINCT EXECUTION STAGES
Every non-trivial executable must keep four distinct, visibly labeled stages:
1. PREFLIGHT: context identity, expected branch/HEAD, clean-worktree or

4. POST-VERIFICATION: final state check (git status, diff scope, output

objective. Prior authorization for one MB does not carry over to the next.

# GRC.CROSS_RUNTIME_EXECUTION_CONTRACT

MARKER: MB-SM-052A_CROSS_RUNTIME_EXECUTION_CONTRACT

CONTROL_TYPE: EXECUTION_GOVERNANCE
PURPOSE: Enforce the human-controlled script execution method across all runtimes, not only PowerShell.

==========
00.00 CONTROL STATEMENT
==========

Any AI agent delivering an executable artifact must comply with the cross-runtime execution contract.

This applies to:
- PowerShell
- Python
- Bash
- Node
- SQL wrappers
- Docker wrappers
- Excel/VBA helpers
- Power Query generators
- any other executable/scripted runtime

==========
01.00 MANDATORY USER FLOW
==========

The canonical flow is:

A. AI gives the executable file or file content.
B. Human saves/downloads it into the project TEMP path.
C. Human runs the exact command from VS Code/terminal from any location.
D. Human returns AI_TAIL_START through AI_TAIL_END and/or explicit TEMP outputs requested by the AI.

The AI must design scripts around this flow.

==========
02.00 EXECUTION_CONTRACT_GATE
==========

Before executable delivery, the AI must satisfy:

- PROJECT
- PROJECT_ROOT
- TEMP_PATH
- SCRIPT_NAME
- SCRIPT_RUNTIME
- TARGET_SHELL
- MIN_VERSION
- CAN_RUN_FROM_ANY_LOCATION
- AI_TAIL_SUPPORTED
- EXIT_CODE_SUPPORTED
- FILE_OUTPUT_SUPPORTED
- GIT_AWARE
- AUTO_COMMIT_ALLOWED
- USER_EXECUTES_LOCALLY
- LIMITATION
- RECOMMENDATION
- DECISION

Allowed decisions:
- PROCEED: full contract can be implemented.
- ADAPT: wrapper/adapter required.
- BLOCK: unsafe or insufficient context.

==========
03.00 HARD FAIL CONDITIONS
==========

The response or script is non-compliant if it:

- delivers executable code without AI_TAIL when the runtime supports AI_TAIL;
- omits TEMP path;
- cannot run from any location;
- auto-commits or pushes without explicit authorization;
- uses git add . or git add -A by default;
- hides or ignores dirty worktree state;
- reports PASS while validation failed;
- continues after UNKNOWN_WORKTREE_STATE;
- asks the user to upload broad logs when a narrow AI_TAIL or TEMP output is enough;
- edits generated outputs directly when source/rebuild flow is required;
- treats PowerShell-specific rules as sufficient for other runtimes without an adapter.

==========
04.00 TOOL CAPABILITY DECLARATION
==========

If a runtime cannot support the full method, the AI must say so.

Required format:

TOOL_CAPABILITY:
- TOOL:
- CAN_USE_METHOD_FULLY:
- CAN_USE_METHOD_PARTIALLY:
- MISSING:
- SAFE_ADAPTER:
- RECOMMENDATION:

Examples:
Power Query M:
- CAN_USE_METHOD_FULLY: NO
- MISSING: stdout, exit code, AI_TAIL
- SAFE_ADAPTER: Python or PowerShell generator/validator
- RECOMMENDATION: generate .m files via wrapper and validate externally.

Python:
- CAN_USE_METHOD_FULLY: YES
- REQUIREMENTS: pathlib, try/except/finally, print_ai_tail, explicit exit code
- RECOMMENDATION: proceed.

==========
05.00 AI_TAIL MINIMUM CONTRACT
==========

AI_TAIL must be machine-readable and concise.

Minimum fields:
AI_TAIL_SCHEMA=v1
MB_ID=<id>
RUNTIME=<runtime>
ROOT=<project root>
TEMP_PATH=<temp path>
FINAL_STATUS=<PASS|FAIL|PASS_WITH_WARNINGS|COMMIT_READY>
BLOCKER=<NONE|specific blocker>
FILES_CREATED=<count or list>
FILES_MODIFIED=<count or list>
VALIDATION_STATUS=<PASS|FAIL|NOT_RUN>
COMMIT_PUSH_PERFORMED=NO
NEXT_ACTION=<single next action>

Additional fields are allowed when useful.

==========
06.00 GENERATED OUTPUT RULE
==========

If the target artifact is generated output, the AI must not patch it manually unless explicitly instructed.

Required sequence:
- patch canonical source;
- run generator/build;
- validate;
- report generated outputs in AI_TAIL or summary.

==========
07.00 TOKEN AND DELIVERY ECONOMY
==========

To reduce token use:
- prefer one executable script over large inline patches;
- prefer downloadable/single file when available;
- prefer AI_TAIL over long terminal logs;
- request only relevant TEMP files;
- avoid ZIP unless multi-file delivery is materially simpler or cheaper.

==========
08.00 AGENT-SPECIFIC APPLICATION
==========

For Claude, Codex, ChatGPT or other agents:
- receiving Skills/GRC context is not enough;
- the agent must explicitly pass EXECUTION_CONTRACT_GATE;
- the agent must choose the correct runtime adapter;
- the agent must stop and recommend an adapter if full compliance is impossible.

- .sh
- .js
- build scripts

Audit checks:

10.00 RUNTIME AND AGENT IDENTITY DECLARATION

  PowerShell 5.1, python 3.x, bash/WSL2, node, etc.);
- AGENT: the actual agent or human operator that drove execution (Claude Code,

10.10 EXECUTABLE IDENTITY EVIDENCE

- TOOL OUTPUT: diagnostics, logs, AI_TAIL, temp evidence produced by the

environment matches the execution environment.

Never claim that another agent (Codex, Claude, remote job) executed work
without direct evidence of that execution (its AI_TAIL, its log, its commit,

00.20_PROPOSITO
==========

Este archivo existe para declarar dominios funcionales amplios y evitar que el ecosistema
derive en cientos de Skills o GRC (Governance, Risk and Compliance) redundantes.

El principio operativo es:

Un dominio funcional amplio debe agrupar métodos, definiciones, riesgos, controles,
checklists y reglas relacionadas, evitando crear documentos separados salvo aprobación
explícita del humano.

==========
01.00_PRINCIPIOS_DE_DOMINIO_AMPLIO
==========

01.10_PRINCIPIO_1_DOMINIOS_AMPLIOS

Los dominios se definen por tema funcional amplio, no por microproceso.

Ejemplos correctos:
- GIT_GITHUB
- POWERSHELL
- RADAR
- BATON
- SESSION_MANAGEMENT
- AI_AGENT_EXECUTION
- MODEL_ROUTING
- FILE_CONTENT
- REPOSITORY_ARCHITECTURE

Ejemplos no deseados:
- GIT_COMMIT_MESSAGE
- GIT_PUSH_FLOW
- GIT_BRANCH_POLICY_MINOR
- RADAR_BACKUP_EXCLUSION_ONLY

01.20_PRINCIPIO_2_UN_DOMINIO_NO_DEBE_EXPLOTAR_EN_DOCUMENTOS

Un dominio puede contener método operativo, control, riesgo, checklist y ejemplos
dentro de un mismo artefacto rector.

La separación en múltiples artefactos requiere aprobación humana explícita y justificación.

01.30_PRINCIPIO_3_GRC_COMO_CAPA_SUPERIOR

En SkillsMachine, GRC (Governance, Risk and Compliance) se considera una capa superior
y más potente que un Skill simple.

Un GRC puede gobernar uno o varios Skills.
Un Skill no debe contradecir un GRC.

01.40_PRINCIPIO_4_CATALOGO_GLOBAL

Este catálogo vive fuera de HUMAN, SkillsLake y GRCLake para operar como capa global
de clasificación y routing documental.

==========
02.00_REGLAS_DE_CLASIFICACION
==========

02.10_SKILL

Un Skill define una capacidad, método o estándar operativo reusable.

Debe responder:
- Qué problema resuelve.
- Cómo se usa.
- Qué reglas aplica.
- Qué errores evita.

02.20_GRC

Un GRC (Governance, Risk and Compliance) define gobierno, riesgo, cumplimiento, control,
validación, límites o trazabilidad sobre uno o varios dominios.

Debe responder:
- Qué gobierna.
- Qué riesgos controla.
- Qué evidencia exige.
- Cuándo bloquear o escalar.
- Qué Skill o dominios subordina.

02.30_DOMINIO

Un dominio es una agrupación amplia y estable de capacidades.

Debe ser suficientemente amplio para evitar microdocumentos, pero suficientemente claro
para permitir búsqueda, routing y composición contextual.

02.40_ARTEFACTO_RECTOR

El artefacto rector es el documento principal de un dominio.

Debe evitar la creación de documentos paralelos con el mismo propósito.

04.00_POLITICA_ANTI_PROLIFERACION
==========

04.10_REGLA_GENERAL

No se deben crear nuevos Skills ni GRC (Governance, Risk and Compliance) por microtema
si el contenido puede integrarse en un dominio existente.

04.20_REGLA_DE_BACKLOG

Toda idea nueva debe registrarse primero como candidato en:

SkillsLake\05.BACKLOG\SKILL_GRC.CANDIDATES.ACTIVE.txt

04.30_REGLA_DE_VALIDACION

Antes de crear un nuevo Skill o GRC, se debe revisar:
- si existe dominio relacionado;
- si existe artefacto rector;
- si el cambio es mejora de un artefacto existente;
- si requiere excepción humana explícita.

04.40_REGLA_DE_FAIL_FUTURO

En fase automatizada futura, la detección de duplicidad deberá producir FAIL duro
cuando se intente crear un artefacto redundante sin aprobación humana documentada.

==========
05.00_EXCEPCIONES
==========

05.10_REGLA_DE_EXCEPCION

Solo el humano puede aprobar la creación de un artefacto separado dentro de un dominio existente.

05.20_UMBRAL_DE_TAMANO

Un archivo puede evaluarse para separación si supera 1 MB.

El tamaño por sí solo no autoriza separación automática.

05.30_DOCUMENTACION_OBLIGATORIA

Toda excepción debe documentar:
- dominio afectado;
- artefacto existente;
- motivo;
- riesgo de no separar;
- aprobación humana;
- fecha;
- alcance preciso.

==========
06.00_RELACION_CON_EL_AGENTE_COMPOSITOR
==========

El futuro agente compositor de contexto debe usar este catálogo para:

- detectar dominio de la consulta;
- seleccionar Skills y GRC relevantes;
- evitar cargar material innecesario;
- agrupar contexto útil;
- detectar gaps;
- registrar candidatos en backlog;
- evitar proliferación de archivos.

El agente compositor no crea canon por sí solo.
